为什么 RDMA 的 OpCode 必须先分清三个编码层次？Communication
分类：Communication · 问题描述：Verbs 枚举、厂商 WQE opcode、线上 BTH OpCode 三者的关系与混淆后果
回答要点
  • ① Verbs 层 enum ibv_wr_opcode：软件 API 枚举（IBV_WR_RDMA_WRITE / IBV_WR_RDMA_READ / IBV_WR_SEND_WITH_INV 等），仅对应用程序可见，与线上数值无关。
  • ② WQE ctrl.opcode：厂商 WQE Control Segment 编码，驱动/网卡可见。mlx5 中 0x08=RDMA_WRITE、0x09=WRITE_IMM、0x0A=SEND、0x10=RDMA_READ。
  • ③ BTH OpCode：报文第 1 字节，网卡/交换机/抓包工具可见，是「指令」的默认含义。
  • 经典陷阱：0x08 在 mlx5 WQE 里是 RDMA_WRITE，在 BTH 里是 RDMA WRITE Last；0x0A 在 mlx5 WQE 里是 SEND，在 BTH 里是 RDMA WRITE Only。数值巧合但语义完全不同。
关键结论
BTH OpCode 只能以 IBTA 规范 / Wireshark packet-infiniband.h 常量表为准；绝不可从 verbs 枚举或厂商 WQE opcode 反推，否则抓包解析与驱动调试会整体偏移。

IB 原生 / RoCEv1 / RoCEv2 / iWARP 的承载差异，以及 RoCEv2 的固定开销是多少？Communication
分类：Communication · 问题描述：四种 RDMA 承载的链路层、网络层、传输头、ECMP 熵与校验差异
回答要点
  • RoCEv1 走 EtherType 0x8915 + GRH，不可路由（仅 L2）；RoCEv2 改为 UDP 封装，dport 4791（0x12B7）/ proto 17，可路由并支持 ECMP；iWARP 则是 TCP + MPA + DDP + RDMAP，传输头与 IB 完全不同。
  • RoCEv2 固定开销量化（IPv4 无 VLAN）：Eth 14+4 + IPv4 20 + UDP 8 + BTH 12 + ICRC 4 = 62 B；加 802.1Q VLAN → 66 B；IPv6 → 82 B；首包再加 RETH 16 B。
  • 小消息效率：Payload=64 B 的单包 WRITE Only（含 RETH）有效载荷占比约 45%；Payload=8 B 的 SEND 仅 11%。
  • ECMP 熵：RoCEv1/IB 用 LID/SL，RoCEv2 唯一逐流可变字段是 UDP 源端口（每 QP 固定、按流变化）——因此同一 QP 的报文在多路径下会走不同 plane，接收端必须靠 PSN 重排。
关键结论
RoCEv2 的 UDP 只是封装外壳：连接、PSN、ACK/NAK、重传、QP 状态机全部由 BTH 承担，UDP 本身不提供可靠性。62 B 固定开销正是「内联发送、批量聚合、大 PMTU」对小消息场景具决定性影响的原因。

BTH 12 字节的字段布局是怎样的？哪些位置最容易被记错？Communication
分类：Communication · 问题描述：Base Transport Header 逐字节定义与常见错误
回答要点
  • BTH 为 12 字节（3 个 32-bit word）：字节 0 = OpCode；字节 1 = SE(bit7) / M(bit6) / PadCnt(bit5:4) / TVer(bit3:0)；字节 2–3 = P_Key（RoCE 通常 0xFFFF）。
  • 字节 4 = F(FECN) / B(BECN) / 保留；字节 5–7 = Dest QP（24 bit）；字节 8 = A(AckReq) + 7 bit 保留；字节 9–11 = PSN（24 bit）。
  • 常见错误：把 Dest QP 放在字节 4–6、AckReq 放在字节 7 —— 手工解包会整体偏移 1 字节。
  • 另一个高频错误：认为 OpCode「高 2 bit 为服务类型」，实际是高 3 bit（否则 0x64 UD SEND Only 无法解释）。
关键结论
BTH 结构是「服务类型收敛于首字节、目的 QP 居中、PSN 收尾」；偏移错误会同时污染 QPN 与 AckReq 判定，导致抓包分析得出完全相反的结论。

BTH OpCode 的编码规则与 RC 段全表是什么？Communication
分类：Communication · 问题描述：OpCode 位域构造与 RC/UC/RD/UD 段划分
回答要点
  • 构造规则：OpCode = ServiceType(3b) << 5 | Operation(5b)；RC 段 0x00–0x1F、UC 0x20–0x3F、RD 0x40–0x5F、UD 0x60–0x7F，0x80+ 为 RoCEv2/厂商扩展（CNP = 0x81）。
  • RC 段关键值：SEND 0x00/0x01/0x02（First/Middle/Last）、SEND Only 0x04、WRITE First/Middle/Last 0x06/0x07/0x08、WRITE Only 0x0A、READ Request 0x0C、READ Response 0x0D–0x10、ACK 0x11、AtomicAck 0x12、Cmp&Swap 0x13、Fetch&Add 0x14、SEND Last/Only with Invalidate 0x16/0x17。
  • UC 段无 ACK、无 READ、无 ATOMIC；UD 仅 0x64/0x65（SEND Only ± Imm），带 DETH 8 B + GRH，≤ PMTU、需 Q_Key 校验、无重传。
  • CNP 结构：BTH 后为 16 B 保留字段（通常全 0）+ ICRC + FCS，BECN=1、PSN=0、DestQP 指向应降速的源 QP。
关键结论
RC 段 0x00–0x17 是生产环境主用区间；0x0C=READ Request、0x11=ACK 是两个必须记住的锚点值——交换机 TCAM 计数与抓包过滤都依赖它们。

扩展传输头（ETH）家族各有哪些成员，分别出现在什么场景？Communication
分类：Communication · 问题描述：RETH / AETH / AtomicETH / DETH / ImmDt / IETH / XRCETH 的归属与作用
回答要点
  • RETH（16 B）：VA 64b + R_Key 32b + DMA Length 32b，仅出现在 WRITE First/Only(+Imm) 与 READ Request，仅首包/Only 包携带。
  • AETH（4 B）：Syndrome 8b + MSN 24b，出现在 ACK(0x11)、READ Response First/Only、AtomicAck。
  • AtomicETH（28 B）：VA + R_Key + Swap/Add Data + Compare Data；AtomicAckETH（8 B） 仅返回操作前 64 bit 原值。
  • DETH（8 B）：Q_Key + Source QP，仅 UD SEND Only；ImmDt（4 B）：32 bit 立即数，位于 payload 之后、ICRC 之前；IETH（4 B）：待撤销的 R_Key。
关键结论
RETH 的「仅首包携带」决定了分片的单点失效特性：首包丢失后 Middle/Last 无法独立寻址，整条消息只能整体重传。

AETH Syndrome 的精确编码是什么？如何据此做 NAK 排障定性？Communication
分类：Communication · 问题描述：ACK/RNR NAK/NAK 的位域划分与根因分类
回答要点
  • Syndrome 1 字节：bit[7] 保留为 0；bits[6:5] 是类别，bits[4:0] 是值（不是 bits[7:6]）。00=ACK（Credit Count）、01=RNR NAK（Timer Value）、11=不可重试 NAK（NAK Code）、10=保留。
  • NAK Code：0（0x60）PSN Sequence Error（可重试，重传）；1（0x61）Invalid Request；2（0x62）Remote Access Error；3（0x63）Remote Operational Error；4（0x64）Invalid RD Request；5（0x65）Operation In Progress。
  • 排障定性三分法：0x60 = 网络丢包/乱序（查 PFC、ECN、交换机丢包计数）；0x20–0x3F = 接收端 Recv WQE 不足（查 RQ 深度与消费速度）；0x62 = rkey/权限/MR 生命周期（查应用逻辑）。
  • MSN（24b）负责消息级顺序与完成去重，与 PSN（包级）处于不同层级。
关键结论
若把类别位误判为 bits[7:6]，0x60 会被误读成 RNR NAK，导致「查接收缓冲」而非「查网络丢包」——处置方向完全相反。这是二手资料最常见的排障误导来源。

ICRC 覆盖哪些字段、排除哪些字段？为什么 ICRC 校验失败极难发现？Communication
分类：Communication · 问题描述：端到端校验边界与静默丢弃机制
回答要点
  • ICRC（4 B）覆盖 BTH 起至 Payload 结束，并包含 IP 头源/目的地址等不变字段；排除 TTL/Hop Limit、DSCP/ECN、IP checksum 等逐跳可改字段。
  • 这正是交换机可改写 ECN 位、递减 TTL 而不破坏 RDMA 端到端校验的根本原因——也是「ECN 标记不影响 ICRC」的理论依据。
  • VCRC（2 B）仅 IB 原生，覆盖含 LRH 整包、每跳重算；FCS（4 B）为以太网链路层校验，与 ICRC 独立并存。
  • 排障陷阱：ICRC 失败报文被 RNIC 静默丢弃——不产生 CQE、不产生 NAK，表现为 ACK 超时 → 重试 → 最终 IBV_WC_RETRY_EXC_ERR。
关键结论
看到「包到了但对端毫无反应」时，必须把 ICRC/链路误码纳入排查，而非只查路由。UDP checksum 在 RoCEv2/IPv4 中常置 0，完整性由 ICRC 承担；IPv6 下通常要求计算，须按厂商文档核对。

分片、PadCnt 与 PMTU 之间是什么关系？为什么 RoCEv2 必须禁止 IP 分片？Communication
分类：Communication · 问题描述：WR → First/Middle/Last 切分机制与 MTU 分层
回答要点
  • IB PMTU 取值固定为 256 / 512 / 1024 / 2048 / 4096 B；RNIC 按 PMTU 把一条 WR 切成 First/Middle/Last（或 Only），每包分配独立 PSN。
  • PadCnt 把末包补齐到 4 B 边界以保证 ICRC 对齐，接收端按此裁剪，避免把填充字节写入远端内存。
  • RoCEv2 必须置 DF=1：RNIC 硬件流水线从 UDP 之后按固定偏移解析 BTH，IP 分片会直接破坏 BTH 定位。
  • 以太网 MTU（如 9000 Jumbo）与 IB PMTU 是两个独立概念：链路 MTU 必须 ≥ PMTU + 封装开销，但分段粒度由 path_mtu 决定，不会因为开了 9000 就自动变成 9000。
关键结论
「链路 MTU ≥ PMTU + 62 B 开销」是硬约束；Jumbo Frame 只是承载条件，不是分段依据。误配会导致黑洞式丢包而非显式错误。

SEND 族（含 with Immediate / with Invalidate）最典型的问题有哪些？Communication
分类：Communication · 问题描述：双边语义下 RNR、完成误读与规模扩展性
回答要点
  • RNR NAK / 接收资源饥饿：接收端 RQ 无可用 WQE → 回 0x20–0x3F，发送端退避重试；rnr_retry 耗尽 → IBV_WC_RNR_RETRY_EXC_ERR，QP 进 ERROR。规避：预贴足量 Recv WQE、SRQ 共享、按峰值 in-flight 配置深度。
  • 完成语义误读：发送 CQE 只表示 NIC 已取走数据并收到传输层 ACK，不表示对端应用已读/已处理（T4 ≠ T6）。需要应用层 ACK、版本号或 seqlock。
  • 规模扩展性差：每个对端都要预留 Recv 资源，N 节点全互联下缓冲管理近似 O(N²)。
  • Immediate 仅 32 bit 且为网络字节序：直接当 host 整数读会错（需 ntohl）；只适合传 token/索引/位图。
  • 其他：接收缓冲过小 → IBV_WC_LOC_LEN_ERR；SE 位仅影响 CQ event 产生、不改变数据到达语义；SEND_WITH_INV 撤销的是接收端 rkey 且与在途操作存在竞态。
关键结论
大规模数据面应优先用 WRITE，SEND 只保留给控制面与通知；把 RNR 计数作为一等监控指标，而非事后排障线索。

RDMA WRITE 无远端通知怎么办？「零长度 WRITE_WITH_IMM」为什么是标准答案？Communication
分类：Communication · 问题描述：单边写语义、通知机制与 GDR 可见性三层时点
回答要点
  • 普通 WRITE 不产生远端 CQE，远端无法感知完成。标准做法是两段式：N 个普通 WRITE + 一个零长度 WRITE_WITH_IMM（或 SEND）作为 doorbell——这是 NCCL IB 传输的常用实现。
  • WRITE_WITH_IMM 仍消耗接收端 Recv WQE：立即数要落到 CQE，若无预贴 WQE 同样触发 RNR NAK；零长度通知的 sg_list 可为空，但 Recv WQE 不可省。
  • 「完成」≠「远端可见」：本地 CQE 只保证传输层确认；远端数据可能仍在 PCIe posted-write 缓冲中，未对 CPU/GPU 缓存层次可见。GDR 场景需显式 flush / 读回确认 + GPU 侧 acquire 语义。
  • 顺序语义：RC 同 QP 内 SQ WQE 按序下发，但READ/ATOMIC 之后的后续 WR 可能被提前执行；跨 QP 完全无保序——需 IBV_SEND_FENCE 或应用层屏障。
  • WRITE 不消耗远端 RQ，无接收侧背压，发送端可全速灌入打爆接收内存带宽/PCIe/交换网 → 需应用层信用、DCQCN 限速、chunk 分级流水。
关键结论
三个时点必须分清：本地 CQE / 远端 NIC 完成 / 应用（GPU kernel）可见。禁止把 CQE 当 GPU kernel 就绪信号，否则会出现「带宽达标但结果不确定」的隐蔽故障。

RDMA READ 为什么延迟高、还可能被配额卡住？哪些场景应改用 WRITE？Communication
分类：Communication · 问题描述：READ 的 RTT 成本、双重 outstanding 配额与 fence 依赖
回答要点
  • 0x0C 请求仅带 RETH 无 payload，响应由 0x0D–0x10 送回，至少一次完整 RTT，小消息延迟约为 WRITE 的 2 倍。
  • 受双重配额约束：发起端 max_rd_atomic 与响应端 max_dest_rd_atomic 共同限制，默认值常偏小（1/4/16），需在 QP 创建时按并发度调优并用 ibv_query_qp 复核。
  • 大 READ 被拆成多包响应，与同 QP 的 WRITE 争用 PSN 窗口与重传缓冲 → 控制单次 READ 大小或分离 QP。
  • READ 之后若紧跟依赖读到数据的 WRITE/SEND，必须置 IBV_SEND_FENCE，否则可能被越过先执行。
  • 抓包陷阱：READ 出错时不是普通 0x11 NAK，而是用带 AETH 错误 syndrome 的 READ Response 包返回，过滤规则容易漏。
关键结论
KV Cache 分级访问（HBM → 同 rack DDR → 同 tray SSD → 跨 rack DDR → 共享层）中，热路径应用 WRITE 推送 + 零长度 WRITE_WITH_IMM 通知；只有冷数据/回源才用 READ，且必须核算 RTT 与 max_dest_rd_atomic。

ATOMIC 操作的边界在哪里？为什么不能当作通用一致性原语？Communication
分类：Communication · 问题描述：64 bit 原子语义、对齐/端序约束与原子性作用域
回答要点
  • 仅 RC（及规范中的 RD）支持；UC/UD 不支持；部分 NIC 完全不提供（如 AWS EFA SRD 无原生原子），需用零长度 WRITE_WITH_IMM + 接收端 CPU proxy 模拟。
  • 固定 8 字节且必须自然对齐：非 8 B 对齐 → 0x61 Invalid Request NAK（RC/RD），UC/UD 则静默丢弃。
  • 端序陷阱：操作数在网络上为大端序，responder 按本地内存端序执行；跨端序节点的 CAS 比较值会解读错，需显式 htobe64/be64toh。
  • 原子性作用域有限：只保证同一 CA、同一地址上无其他 QP 插入，不等于跨 CPU / 跨 PCIe 设备 / GPU 显存 / 跨节点的事务一致性。
  • 8 字节原子性鸿沟：多字段结构（如 304 B 哈希项）用 WRITE 更新并非原子，读者可能看到「新版本 + 旧值」→ 需 cache line 尾部版本号 + 末尾 CAS 提交 + 读侧双重校验（FaRM 式）。
关键结论
ATOMIC 只适合计数器/序号/锁字这类 8 B 标量；跨字段一致性必须靠版本号 + 提交位方案在软件层构建，不可依赖硬件原子范围扩展。

为什么抓包看不到「一问一答」的 ACK？重传为何会放大丢包影响？Communication
分类：Communication · 问题描述：ACK 累积合并、Go-Back-N 重传与 PFC/CNP 耦合
回答要点
  • ACK 可累积、可合并，且只对 AckReq=1 的请求回；看不到 1:1 对应属正常，常被误判为丢应答。分析应以消息末包的 AckReq 与 AETH 为准。
  • 重传粒度粗：PSN 不连续 → 0x60 NAK，发送端从 ePSN 起重发后续已发报文（Go-Back-N 语义），丢 1 包可能回退整窗，尾延迟被放大。选择性重传属 IBTA 新版本/厂商实现扩展，不可假定。
  • 不可重试 NAK（0x61/0x62/0x63）通常直接终结 WR，重试无意义；应按 syndrome 分类处置。
  • 重试耗尽是硬失败：IBV_WC_RETRY_EXC_ERR / IBV_WC_RNR_RETRY_EXC_ERR → QP 进 ERROR，其余在途 WR 全部 IBV_WC_WR_FLUSH_ERR，必须重建 QP。
  • CNP 与 ECN/PFC 耦合：交换机标 CE → 接收端发 0x81 CNP → 发送端 DCQCN 降速；CNP 太慢则先触发 PFC 反压。PFC 自身有死锁、pause 风暴、拥塞树扩散等失效模式（SIGCOMM 2016 有生产事故记录）。
关键结论
工程上应把丢包率压到接近 0（PFC + ECN/DCQCN），而不是依赖重传兜底——因为 RoCE 的重传代价是 Go-Back-N 级别的窗口回退。上层必须具备 QP 重建与状态重放能力。

资料库既有 RDMA 材料中有哪些必须纠正的硬性错误？Other
分类：Other（方法论/勘误） · 问题描述：与 IBTA Vol.1、A17、Wireshark dissector 源码逐条核对的结果
回答要点
  • E1：既有材料称「READ Request = 0x0A，Response = 0x0B/0x0C/0x0D」→ 规范为 Request = 0x0C、Response = 0x0D/0x0E/0x0F/0x10；0x0A 实为 WRITE Only、0x0B 为 WRITE Only+Imm。
  • E2：称「ACK = 0x0F」→ 规范为 0x11（0x0F 是 READ Response Last）；按错误值配 TCAM 会漏掉全部 ACK/NAK。
  • E3：把 mlx5 WQE 的 0x08(RDMA_WRITE) 当成传输层编码 → 两者是不同编码空间的巧合，混用会使后续所有 opcode 推导偏移。
  • E4：BTH 字节 4–6 = Dest QP 的错误 → 正确为字节 5–7；字节 8 才是 AckReq。
  • E5：AETH 类别位误作 bits[7:6] → 正确为 bits[6:5]，否则 0x60 会被误判成 RNR。
  • E6：称「BTH 为 8 字节」「OpCode 高 2 bit 为服务类型」→ 正确为 12 字节、高 3 bit。
关键结论
这些偏差不影响架构性论述，但会直接导致抓包解析与排障定性出错。凡涉及线上字段，一律以 IBTA / Wireshark 常量表为准，二手材料仅作架构参考。

2. 抓包与过滤命令

  • udp.port == 4791 —— 只看 RoCEv2 流量
  • udp.port == 4791 && infiniband.bth.opcode == 0x11 —— ACK/NAK（交换机 TCAM 计数同样按此配置）
  • udp.port == 4791 && infiniband.aeth.syndrome == 0x60 —— PSN Sequence Error
  • udp.port == 4791 && infiniband.bth.opcode == 0x81 —— CNP
  • IB 原生用 ibdump，RoCE 用 tcpdump -i <dev> -s 0 -w roce.pcap

3. 计数器三段定位（主机 → 接入交换机 → fabric）

  • 主机侧：perfquery / ibstat / mlx5 ethtool 统计（rx_discards、rx_pause、ecn_marked、cnp_sent、rnr_nak_retry_err、retry_exceeded）。
  • 交换机侧：PFC pause 帧速率、ECN 标记计数、逐优先级丢包计数。

4. 性能验收命令

  • WRITE：ib_write_bw -d mlx5_0 -i 1 -F --report_gbits / ib_write_lat
  • READ：ib_read_bw / ib_read_lat（对比 WRITE 验证 RTT 与 max_rd_atomic）
  • SEND：ib_send_bw / ib_send_lat（验证 RQ 深度与 RNR）
  • ATOMIC：ib_atomic_bw / ib_atomic_lat（验证 8 B 对齐与能力）
  • 集合通信：nccl-tests 的 all_reduce_perf（端到端验证 GDR + 多路径）

5. 配置核查清单

  • PMTU 与链路 MTU 一致、QP path_mtu 协商一致、DF=1 禁止 IP 分片。
  • max_rd_atomic / max_dest_rd_atomic、retry_cnt / rnr_retry、P_Key、GID 类型（RoCEv2 应为 v2 GID）。
  • DSCP/PFC 优先级映射、ECN 门限、MR 权限位（REMOTE_WRITE / READ / ATOMIC）。

6. 与 SUE / AI 集群设计的三个关联结论

  • 多 plane 与报文喷洒：同一 QP 的包走不同路径时，PSN 窗口与接收端重排缓冲是第一瓶颈。要么 fabric 保证 per-flow 保序，要么把乱序容忍上移（UEC / SRD 类方案）——二者不能只做一半。
  • KV Cache 分级访问：热路径用 WRITE 推送 + 零长度 WRITE_WITH_IMM 通知；跨级回源才用 READ，并与 prefix_hash → worker 路由配合减少跨级 READ。
  • GDR 三层时点：本地 CQE / 远端 NIC 完成 / GPU kernel 可见是三个不同时点，必须有显式 flush 与 acquire 语义。

7. Memory Window 与授权生命周期

  • Invalidate 撤销的是 rkey 而非 MW 对象本身；MW 资源仍在，可再生成新 rkey。
  • IBV_WR_LOCAL_INV 是纯本地 WR、不发任何报文；跨节点撤销必须用 SEND_WITH_INV（BTH 0x16/0x17 + IETH）。
  • 撤销前需用 fence + 完成屏障收敛在途操作，否则在途请求会返回 0x62。
  • SEND_WITH_INV 的接收 CQE 通过 IBV_WC_WITH_INV 标志在 imm_data 中带回被撤销 rkey —— 解析 CQE 必须先判 wc_flags。

8. rkey 的安全属性边界

  • rkey 是授权凭证，不是加密密钥：不提供机密性、完整性或身份认证；泄露 rkey + VA 即可在权限范围内任意写。
  • 缓解手段：最小权限/最小范围注册、Type 2 MW 轮换 rkey、PD 隔离、控制面可信通道交换。
