KV Cache 卸载在并发 Agent 上为什么"时灵时不灵"？AI
问题描述：同一编码 Agent 负载，KV 卸载到 CPU host 层在 RTX 3090 提速、H800 变慢（1.08–1.87×）、H20 无效，根因是什么？
回答要点
  • 现有系统按"逐 token 成本比较"决策（载回比重算便宜就载回/写入），在并发 Agent 负载下系统性失效。
  • Agent 等 tool 返回的窗口被其他 Agent 的处理时间拉伸：两轮之间中位间隔 9.0 s，是 Agent 自身间隔的 14 倍。
  • 97.3% 的新写入 KV 确实会在下轮被引用，但 79.2% 在下轮到来之前已被驱逐并被迫重算。
命中率不是逐 token 的成本问题，而是容量与并发竞争问题：缓存写入后必须"活到"下次复用，窗口期被其他 Agent 上下文挤出即告失效。

复用工作集 (Reuse Working Set) 是什么？为什么决定卸载成败？AI
问题描述：论文提出的核心概念量 C_reuse ≈ (A−1)·N̄·β_rank 如何解释命中是否会发生？
回答要点
  • 定义：两次复用之间服务端处理的其他 Agent 上下文总量（backlog 池规模），A 个活跃 Agent、平均上下文 N̄、每 rank 每 token KV 字节 β_rank。
  • 两个压力比：γ_G = A·N̄/K_G（池上下文 / GPU KV 容量），γ_H = C_reuse/C_H（工作集 / host 容量）；γ_G>1 是卸载机会，γ_H>1 是 thrash 区。
  • H20 上 A=16：C_reuse ≈ 15 × 33,234 × 24 KiB ≈ 11.4 GiB/rank；5/10/20 GiB host 对应 γ_H = 2.3 / 1.1 / 0.57，实测容量拐点恰在 γ_H 跨 1 处。
  • 复用工作集决定"命中是否会发生"，与硬件（决定"命中值多少钱"）解耦。
并发改变工作集：A 从 16 减半到 8，工作集从 11.4 降到 5.3 GiB，容量拐点同步左移；即使不配 host 层，减半活跃池本身就省 24.8% makespan。

硬件差异为何概括为一个比值：FLOP/host-byte？AI
问题描述：为什么同一负载在 H800 上卸载必然亏本？
回答要点
  • 峰值算力 / host 链路带宽比决定载回的机会成本：RTX 3090 2.2K、H20 2.3K、H800 15.5K FLOP/byte。
  • H20 实测：LMCache 载回中位速率 26.6 GiB/s，β=24 KiB 下每 token 每 rank 仅 0.86 µs；prefill 至少 5.6 µs/token，长前缀 OBR ≥ 0.84。
  • H800 是 H20/RTX 3090 的 6.7–7.0 倍比值：载回占用的 PCIe 时间折损了远高于此的计算，所有 10 组测量全部减速。
FLOP/host-byte 比值定生死：低比值 GPU（3090/H20）卸载可提速，高比值 GPU（H800）卸载必然亏本——硬件决定恢复前缀的价值。

栈距离容量模型如何做到实验前定位容量拐点？AI
问题描述：Mattson 1970 经典栈距离分析如何迁移到 KV 分层场景？
回答要点
  • 式 4：全相联 LRU 下，chunk k 存活当且仅当复用距离 D(k) < ⌊C/(b·β_rank)⌋（容量可容纳的 chunk 数）。
  • KV 特有结构约束：host 覆盖只能取"从首 chunk 起的连续存活 run"，还需减去 GPU 已驻留部分（式 9：R = max{0, H−G}）；把 chunk 当独立对象统计会高估有效载回量。
  • 预测精度：实验前预测 20 GiB 下 prefill 5.19–5.78M tokens，实测 5.28M；拐点定位准确，仅在 γ_H≈1 过渡区略保守。
同一栈距离模型既服务部署前定容（找 γ_H=1 拐点容量），又以轻量在线形式（滑动窗口 A_t·N̄_t）进入运行时准入前馈项——规划与门控共用一个模型。

容量条件化写准入如何工作？开销多大？AI
问题描述：运行时核心机制——压力信号 p_t 与写规则 save(r) = ¬(p_t ∧ u>κ) 的设计。
回答要点
  • 前馈项：滑动窗口估计活跃任务数 A_t 与平均 prompt 长度 N̄_t，代入式 5 与 host 容量比较；反馈项：host 遥测报告"占用率 ≥0.95 且窗口内有容量驱逐"，防估计误报。
  • 写规则：新满 chunk 数 u 小（延伸仍驻留的前缀）照写，u 大（回填已被驱逐的上下文）拒写；κ=8 时 5 GiB 下拒掉 95.3% 新 chunk 写入，κ∈[2,16] 均稳健。
  • 开销：每请求一次 O(1) 常数检查；拷贝前还有去重（drop tier 已持有的 chunk）。
  • 压力信号 p_t≡0 退化为 native offload，p_t≡1 即 fixed 准入——两个端点被统一。
设计源自 Denning 工作集模型（1968）：host 层低于池的复用工作集时以完全相同的方式 thrash，负载控制让子集驻留——准入即 KV 版的内存过载控制。

Proposition 1：哪些写入可以"拒而不丢命中"？AI
问题描述：LRU 命中保持性证明如何为拒写提供理论保障？
回答要点
  • 命题：若 LRU 层仅在"下次引用的复用距离 D ≥ K_H（或不再引用）"的 miss 上拒绝插入，则全准入下的命中在此策略下仍命中。
  • 证明要点：命中要求自上次引用以来被提升的不同 chunk 数 < K_H；被拒插入永远不会把这个计数推过 D。
  • 实测验证：5 GiB 下 84.4–85.5% 被拒 chunk 满足 D≥K_H 条件；fixed 准入在 40 GiB 下被拒 chunk 中 95.2% 复用距离 < K_H（违反命题条件，故造成伤害）。
该命题把处理器缓存领域的 bypass / dead-block prediction / RRIP 原理形式化到了"精确前缀 + 连续覆盖"的 KV 分层场景。

实测收益有多大？依赖保持回放是什么方法论亮点？AI
问题描述：8×H20 全量 SWE-bench Verified 回放的核心数字与可复现性设计。
回答要点
  • 按工作集定容（11.4 GiB/rank 量级）：重算 prompt tokens −93.1%，makespan −38.7%（209→128 min）；4,427 次调用、147.1M prompt tokens。
  • 容量拐点对应：5→10→20 GiB，计算 prefill 76.7M→23.5M→5.3M；抢占从 1,808 降到 46。
  • 回放方法：提交精确 prompt token ID + logits processor 强制输出与录制逐 token 一致——固定 token 工作量，只让调度决策变化；任务下一调用须等前序响应并经过录制 tool 间隔（闭环时序保持）。
makespan 与计算 prefill 跨所有 17 组干预单调关联——"计算 prefill"是 KV 分层调度的第一性代理指标。

缓存稳定 prompt 长度为何约束 Agent 上下文管理设计？AI
问题描述：可复用状态沿"上一次处理后序列与当前 prompt 的最长公共前缀"延伸，历史改写有何代价？
回答要点
  • vLLM 前缀缓存的 key 对整个前缀做哈希：改写历史早期内容会使之后所有 chunk 的 key 失效——即使后续文本一字未改。
  • 实测：把早期历史折叠成摘要的"历史压缩器"把前缀命中率从 96.5% 砍到 51–61%。
  • 编码 Agent 的 prompt token 中 98.1% 已在上轮处理过，输出仅 23K、输入 33K 量级——输入的负担是纯 prompt。
Agent 侧上下文管理必须保持前缀稳定：任何早期历史改写（摘要/重排）都会以 KV 前缀缓存大面积失效为代价，与"压缩省 token"的收益严重对冲。

工程落地路径与局限是什么？AI
问题描述：开源仓库（Apache-2.0）如何映射论文概念？相关工作的定位边界？
回答要点
  • 实现极薄：全部运行时增量仅 connector.py 约 400 行（EfficientAgentConnector），基于 vLLM KV connector 接口 + LMCache host 分层；policies.py 做配置映射。
  • 纯 CPU 分析工具（capacity_model.py 等）支持部署前定容，无需 GPU 即可预测容量曲线。
  • 与 KVFlow/Continuum/TOPAS 等"决定什么驻留/何时调度"的系统正交：EfficientAgent 决定"host 层是否装得下池的工作集、以及哪些新状态准入"。
  • 局限：压力信号依赖活跃任务数与 prompt 长度估计（60s 窗口/256 条 deque）；γ_H≈1 过渡区预测略保守；结论基于编码 Agent 负载外推需谨慎。
结论一句话：硬件决定恢复前缀的价值，并发工作集决定它能否活到复用——按工作集定容 + 压力感知准入，复用工作集应成为 KV 分层与调度的一等输入。

📚 知识点沉淀

1. Denning 工作集模型 → KV 分层的直接迁移

  • 多道程序内存：活跃程序工作集总和超过内存时 thrash，负载控制让子集驻留（1968/1980）。
  • KV 分层对应：host 层低于池的复用工作集 (A−1)·N̄·β_rank 时以完全相同的方式 thrash；写准入即负载控制。
  • 三个新量：排队拉伸的复用距离、连续前缀覆盖 + GPU 驻留扣减、(A−1)·N̄·β_rank 准入门控尺度。

2. KV 足迹公式（式 1）与 TP 放大效应

  • β_rank = 2·L·d·s·max(1, ⌈H_kv/TP⌉)：Qwen3-Coder-30B（MoE, L=48, H_kv=4）为 24 KiB/token/rank @TP8；Qwen2.5-Coder-32B 为 32 KiB @TP8、128 KiB @TP2。
  • KV 头复制（TP>头数）会显著放大足迹——MoE 模型在 TP8 时恰好触及，是容量规划容易漏掉的坑。

3. 服务成本守恒式（式 3）的通用判据价值

  • ΔT ≈ −(省下的重算) + (付出的载回流量)：只把复用从 GPU 层平移到 host 层、而不增加总覆盖的卸载，只会增加搬运、不省计算。
  • 该"省下 vs 付出"的守恒视角可迁移到任何分层缓存（SSD 层、跨节点 KV 池）的方案评估。
