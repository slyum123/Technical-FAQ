git push 报 "Failed to connect to github.com port 443: Could not connect to server"，如何判断是网络故障还是本地劫持？Computer
关键词：Git / HTTPS 传输 / 错误语义 / 分层定位
问题描述
  • 自动化任务推送 GitHub 仓库时连续失败，报错为 fatal: unable to access 'https://github.com/...': Failed to connect to github.com port 443 after 2089 ms: Could not connect to server。
  • 此前多轮经验把该类故障一律当作「GitHub 502，重试即可」，但本次重试数十轮完全无效。
回答要点
  • 502 Bad Gateway：请求已到达 GitHub 边缘节点，属服务端瞬时故障，重试可恢复。
  • Connection timed out：SYN 无响应，通常是链路中断、防火墙丢包或代理不可达。
  • Could not connect to server：TCP 连接被立即拒绝（RST）。若耗时仅 2 s 左右且稳定复现，说明目标地址在本机——即域名被解析到 127.0.0.1，而本机 443 端口无监听。
关键结论
「Could not connect」+ 毫秒级返回 = 名称解析层异常，而非网络层故障。判据是耗时特征：链路故障会等到超时上限（数十秒），本地拒绝则在 2 s 内返回。把这类错误归类为 502 并盲目重试，是本次浪费数十分钟的根因。

如何用一条对照命令确认域名被 hosts 劫持？Computer
关键词：hosts / DNS / ping / nslookup
问题描述
  • 需要区分「DNS 服务器返回了错误结果」与「本机 hosts 覆盖了正确结果」。
回答要点
  • ping github.com → 显示 正在 Ping github.com [127.0.0.1]，且 TTL=128（本机回环）。
  • nslookup github.com → 返回 Address: 20.205.243.166（真实 GitHub IP），DNS 服务器 192.168.1.1 正常应答。
  • 两者结果不一致即证明：hosts 文件的优先级高于 DNS，且当前存在覆盖条目。
关键结论
ping 走操作系统解析器（先查 hosts），nslookup 直连 DNS 服务器（不查 hosts）。这一对命令构成最廉价、最可靠的 hosts 劫持判定工具，无需任何额外软件。

Windows 的域名解析顺序是什么？为什么 nslookup 不受 hosts 影响？Computer
关键词：DNS Client / dnscache / 解析优先级
回答要点
  • Windows DNS Client 服务（dnscache）的解析顺序：① hosts 静态表 → ② 本地 DNS 缓存 → ③ DNS 服务器 → ④ NetBIOS/LLMNR。hosts 命中即直接返回，不再外查。
  • hosts 路径：C:\Windows\System32\drivers\etc\hosts，无扩展名，IPv4 在前、主机名在后，# 开头为注释。
  • nslookup / dig 是专用 DNS 查询工具，它们自行构造 DNS 报文发给指定服务器，完全绕开操作系统解析器，因此不会读取 hosts。
  • ipconfig /flushdns 只清空第 ② 层缓存，对 hosts 无效；ipconfig /displaydns 可查看当前缓存。
关键结论
「清 DNS 缓存」治不了 hosts 劫持——hosts 在缓存之前生效。排查时必须单独检查 hosts 文件本身，而不是反复 flushdns。

如何证明到 GitHub 的网络链路本身是通的？Computer
关键词：curl --resolve / SNI / 证书校验
回答要点
  • 用 DNS 拿到的真实 IP 手动建连：curl --resolve github.com:443:20.205.243.166 https://github.com → 返回 HTTP 200。
  • --resolve 把「主机名:端口 → IP」预置进 curl 的地址表，跳过名称解析，但 HTTP 层请求的 Host 头、TLS 握手的 SNI 仍是 github.com，因此证书校验正常通过（未关闭 -k）。
  • 同法验证 api.github.com 返回 301（重定向，同样证明可达）。
关键结论
拿到 HTTP 200 即完成「链路可达」的闭环证明：物理网络、路由、TLS、服务端全部正常，故障点 100% 收敛到本机的名称解析层。这一步是后续选择绕行方案的决策依据。

根因是什么？Steam++ / Watt Toolkit 的 hosts 加速残留Other
关键词：Steam++ / hosts 加速 / 残留条目
问题描述
  • hosts 文件中存在一段处于生效状态的 # Steam++ Start ... # Steam++ End 区块，把 40+ 个域名映射到 127.0.0.1。
  • 上方另有两份已注释的历史副本，分别标记 [disabled 2026-10-18] 与 [disabled 2026-10-19]。
回答要点
  • 此类加速器的原理之一：把目标域名指向 127.0.0.1，由本机监听的加速进程接管连接并转发；加速器未运行时，127.0.0.1:443 无监听 → 连接立即被拒，表现为「GitHub 突然不可达」。
  • 两份 [disabled] 副本说明该段被手工禁用过，但软件重启后重新写入了生效区块——即 hosts 被程序反复重写。
  • 本机同时存在备份文件 hosts.backup-2026-10-18，可用于比对与回滚。
关键结论
故障根因不是网络、不是 GitHub、也不是凭据，而是加速器遗留的 hosts 黑洞条目。改 hosts 只能治标：只要 Steam++ 仍在运行，它会把区块写回去；根治需要在软件内关闭对应加速项。

不改系统文件如何恢复 git 推送？本地 CONNECT 代理 + http.proxyComputer
关键词：CONNECT 隧道 / git http.proxy / 无管理员权限
回答要点
  • 在 127.0.0.1 起一个最小 CONNECT 代理：收到 CONNECT github.com:443 后，用 nslookup（绕过 hosts）自行解析真实 IP，再与目标建 TCP 连接并双向转发字节流。
  • 推送命令不带全局配置、即用即走：
    git -c http.proxy=http://127.0.0.1:8889 -c https.proxy=http://127.0.0.1:8889 push origin main
  • 关键点：代理只是转发 TCP，TLS 仍由 git 与真实 github.com 端到端完成，SNI 与证书校验完整保留。
关键结论
remote URL 保持不变，Git Credential Manager 仍按 github.com 匹配缓存凭据，无需管理员权限、不触碰系统文件、不降低 TLS 安全性。本次两个仓库（Technical-FAQ 86b0351、slyum123.github.io 36dfd20）均一次推送成功。

为什么不能直接把 IP 写进 remote URL，或关闭证书校验？Computer
关键词：证书 SAN / sslVerify / 安全折中
回答要点
  • https://20.205.243.166/slyum123/Technical-FAQ.git：TLS 证书只签发了 github.com 等域名，IP 不在 SAN 列表 → 证书校验失败。
  • 配套「解法」git -c http.sslVerify=false 会放弃服务端身份认证，等同向中间人敞开，且污染操作习惯。
  • 「域名 + 自定义端口」（https://github.com:8443/...）看似可行，但要求本机 8443 上有转发器，本质上仍是代理方案，且会在凭据匹配上引入额外变量。
关键结论
评估绕行方案的三条底线：域名不变（保凭据与证书）、校验不关（保安全）、不写系统文件（保可逆性）。CONNECT 代理是唯一同时满足三条的方案。

根治方案：清理 hosts 中的加速区块Computer
关键词：系统 hosts / 管理员权限 / 备份回滚
回答要点
  • 编辑 C:\Windows\System32\drivers\etc\hosts 需管理员权限；修改前先复制一份备份（如 hosts.backup-YYYY-MM-DD）。
  • 推荐做法是整段注释（行首加 #）而非删除，保留可回滚痕迹，也便于识别是哪款软件写入。
  • 顺序很重要：先在 Steam++ 内关闭 GitHub 加速 / 退出软件，再改 hosts，否则会被立即重写。
  • 验证：ping github.com 应返回真实 IP（非 127.0.0.1），随后 git push 直连成功。
关键结论
治本路径 = 「软件内关闭加速 → 注释 hosts 段 → ping 验证 → 直连推送」。在自动化场景里，更稳妥的策略是本地先提交落盘、网络恢复后补推，避免把任务成败绑定在外部环境上。

复盘：自动化推送的重试策略应该怎么写？Other
关键词：重试判据 / 分层诊断 / 提交落盘
回答要点
  • 昨日的处理：检测到推送失败后启动 20~30 轮定时重试（累计数十分钟），全程认为「GitHub 502，等一会就好」，结果是无效功。
  • 正确的三步定位法：① 解析层（ping vs nslookup 对照）→ ② 链路层（curl --resolve 拿到 200）→ ③ 应用层（选择绕行通道推送）。每一步都有明确的二分判据，总耗时应在 2 分钟内。
  • 提交与推送解耦：本地 commit 先落盘保证不丢内容，push 作为可延迟补偿动作。
关键结论
重试只对瞬时性故障有效（502/限流/超时抖动）；对确定性故障（本机配置错误）重试一万次也不会成功。经验规则：同类错误连续 3 次完全一致 → 停止重试，转入根因定位。本次 10-18 的本地提交 86b0351 与部署提交 36dfd20 已在 10-19 用代理方案一次性补推。

知识点沉淀

1. Windows 名称解析链路与 hosts 优先级

  • 顺序：hosts 静态表 → DNS Client 缓存（dnscache）→ DNS 服务器 → NetBIOS/LLMNR；hosts 命中即短路返回。
  • 诊断工具对照：ping/curl/git 走系统解析器（受 hosts 影响）；nslookup/dig 直查 DNS（不受影响）。这一差异正是定位 hosts 劫持的抓手。
  • ipconfig /displaydns 查看缓存、/flushdns 清缓存，均不影响 hosts。

2. curl --resolve 与 TLS SNI/证书校验的关系

  • --resolve host:port:ip 只替换地址解析结果，Host 头与 SNI 仍使用原主机名，因此证书校验可正常通过，无需 -k。
  • 同理，--connect-to 可同时改写目标主机与端口，适合做「域名不变、路径变」的验证。
  • 这是验证「链路是否真的通」最干净的探针：返回值若为 200/301，即可排除网络、路由、防火墙与服务端因素。

3. HTTP CONNECT 隧道与 git 代理配置

  • HTTPS 走代理时，客户端发送 CONNECT host:443 HTTP/1.1，代理回 200 Connection established 后转为纯字节转发；代理不参与 TLS，因此看不到明文，也不会破坏证书校验。
  • git 用法：git -c http.proxy=http://127.0.0.1:PORT -c https.proxy=http://127.0.0.1:PORT push origin main；临时传参优于写全局配置。
  • 诊断开关：GIT_CURL_VERBOSE=1 或 GIT_TRACE=1 可打印完整的 HTTP 交互，判断卡在 DNS、TCP 还是 TLS。

5. Steam++ 类加速工具的 hosts 改写机制与残留风险

  • 机制：将目标域名写入 hosts 指向 127.0.0.1，由本机加速进程监听并代理转发；软件异常退出或未清理时留下「黑洞条目」。
  • 特征：hosts 中成对出现 # <工具名> Start / # <工具名> End 标记段，易于识别与整段禁用。
  • 运维建议：修改前备份（hosts.backup-<日期>）、整段注释而非删除、先在软件内关闭加速再改文件；自动化任务应假设该文件可能被随时重写，优先采用不依赖 hosts 的绕行通道。
