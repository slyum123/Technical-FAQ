REACT 要解决的核心问题是什么？Communication
来源：论文解读 REACT（arXiv:2609.04417，UIUC / Meta / IBM Research）
问题描述

在共享 AI 集群（多租户云或学术共享集群）中，单个训练作业的集合通信流会被外部作业或后台流量阻塞。现有方案要么依赖交换机/路由层支持，要么需要全局调度权限，无法在租户侧单边部署。

回答要点
  • 传统拥塞控制分三类：网络层自适应路由、全局调度协调、传输层降速，都需要基础设施或全局控制权。
  • REACT 的观察：AllReduce/AllGather 等集合操作存在多种语义等价的实现模式。
  • 当某条入链路拥塞时，把聚合/收发节点换到不拥塞的位置，即可在不改路由、不降速的前提下绕过瓶颈。
关键结论：REACT 在 CCL 层通过改写集合模式的源/目的节点绕开拥塞，保留集合语义，无需网络层或调度层支持，适合共享集群单边部署。

Collective Operation 与 Collective Pattern 有何区别？Communication
来源：论文解读 REACT §2
问题描述

NCCL、Gloo 等集合通信库中常把"集合操作"与"集合模式"混为一谈，导致难以理解 REACT 的优化空间。

回答要点
  • Collective Operation：高层语义，如 AllReduce、AllGather、ReduceScatter，只规定输入输出语义。
  • Collective Pattern：CCL 内部实现该操作的具体数据交换序列，包括哪些 rank 在哪些时步与谁通信、消息大小与聚合顺序。
  • 主流 CCL 在作业启动时根据节点数、消息大小、传输协议静态选择模式并复用，无法响应动态变化的网络状态。
关键结论：REACT 在不变的 Collective Operation 语义之上，对 Collective Pattern 做运行时在线微调，从而在不改应用代码的前提下适应网络变化。

Time-Expanded Network（TEN）在 REACT 中起什么作用？Communication
来源：论文解读 REACT §5.1
问题描述

REACT 需要对集合模式做节点交换并保证语义正确，需要一个形式化模型来描述"哪些 rank 在哪些时步通信"。

回答要点
  • TEN 把模式建模为有向图 G = {⟨V_c, E_c⟩ | c ∈ C}，每个顶点 (t, r) 表示 rank r 在逻辑时步 t 的状态。
  • 边 ((t,r) → (t+1, r')) 表示两个连续时步之间的数据流。
  • C 表示消息分成的 chunk 子图集合，例如 NCCL 双树 AllReduce 有两个 chunk 子图。
  • TEN 让 REACT 独立于底层拓扑，仅从 rank-时步通信关系层面做变换。
关键结论：TEN 将动态网络问题抽象为"时序图上的节点置换问题"，使 REACT 可以在不依赖拓扑信息的情况下安全改写集合模式。

REACT 如何仅通过 FCT 检测拥塞？Communication
来源：论文解读 REACT §5.2
问题描述

REACT 无法访问链路利用率、拓扑或其他租户信息，只能看到本作业各流的完成时间。

回答要点
  • 稳态拥塞 Steady：流 f 的 p90 吞吐量低于同度数其他流均值 20% 以上，即 p90(b_f) < mean(b_F(k_f)) · (1 − δ_1)，δ_1 = 0.2。
  • 间歇拥塞 Erratic：流吞吐量的归一化标准差超过阈值，即 normalizedSTD(b_f) > δ_2，δ_2 = 0.15。
  • 检测仅使用 CCL 内部可获取的 FCT 向量，无需链路状态或拓扑信息。
关键结论：REACT 用 FCT 的统计分布（稳态偏低、间歇高波动）识别拥塞流，把"网络层不可见"约束转化为"端侧可观测"约束。

REACT 的三种安全变换各有什么特点？Communication
来源：论文解读 REACT §5.3
问题描述

REACT 需要在保持集合语义的前提下对 TEN 做节点交换，不同变换粒度对应不同适用场景。

回答要点
  • 全局置换 Global Permutation：交换两个 rank 在所有 chunk 和时步中的全部出现；适用于 All 集合，但对 Server-ToR 稳态拥塞帮助有限（整体度数不变）。
  • 块内置换 Chunk-local Permutation：仅在受影响的单个 chunk 子图内交换两个 rank；更精细，适合 Tree AllReduce。
  • 位置等价交换 Position-equivalent：仅交换 chunk 子图中语义等价的位置；适合 Tree / Recursive Doubling，可针对关键路径上特定时步精确替换。
  • 三种变换按粒度优先使用 ③→②→①，并做度数剪枝：交换后若 rank 度数高于原位置则剔除。
关键结论：三种变换从细到粗覆盖不同集合模式，配合度数剪枝保证语义正确并限制搜索空间。

REACT 运行时闭环的关键阈值与开销如何控制？Communication
来源：论文解读 REACT §4 / §5.4
问题描述

在线调优需要在收敛速度、开销和避免局部最优之间取得平衡。

回答要点
  • 每批 B = 6 个 epoch 收集 FCT 并做一次决策；历史 FCT 保留长度 H = 60 epoch。
  • ε 检查：候选模式相对旧模式关键路径耗时提升 ≥ 5% 才接受。
  • τ_r 检查：新模式跑完后若实际通信时间未比旧模式好 5%，则回退。
  • 设置 E_max = 5 轮探索周期，每轮 B 个 epoch；连续 5 轮无探索则强制触发一次探索，避免局部最优。
  • 控制消息走独立管理网口 eth1，避免污染 RDMA 数据路径 hsn0。
关键结论：REACT 通过 ε/τ_r 双阈值、历史 FCT 估计和强制探索机制，在数百毫秒到数秒内完成收敛，并将控制面与数据面物理隔离。

REACT 的实验收益与局限是什么？Communication
来源：论文解读 REACT §7 / §8
问题描述

评估 REACT 时既要看到加速收益，也要明确它不能解决哪些问题。

回答要点
  • 真实 4/8 节点 A100 + Cray Slingshot 200 Gbps 集群：拥塞场景算法带宽提升 13%–38%，随拥塞度增加而提升。
  • ns-3 仿真中最高提升 75%，覆盖 Tree/Ring AllReduce 与 Recursive Doubling AllGather。
  • 无拥塞时性能下降约 4%，来自探索和 PyTorch P2P shim 开销，处于工程可接受范围。
  • 局限：仅适用于少量节点/链路拥塞；大部分链路都拥塞时无优化空间；无法处理微秒级单流突发拥塞；多作业同时启用可能出现振荡。
关键结论：REACT 在共享集群持久/慢变拥塞场景下收益显著，但与 NCCL 原生集成、多作业协调仍是生产化需要补的课。

RDMA 验收为什么要坚持"分层切断干扰"原则？Communication
来源：交付件《RDMA 验收测试用例清单与 NCCL 映射》
问题描述

在 AI 集群中，NCCL 训练性能差时，如何区分是 RDMA 链路、Fabric 配置、NCCL 参数还是训练框架本身的问题？

回答要点
  • 验收分五层：① 裸 RDMA 基线（perftest 单机打流）→ ② 跨主机 RDMA 基线 → ③ Fabric 无损/拥塞面（PFC/ECN/DCQCN）→ ④ NCCL 端到端（nccl-test）→ ⑤ 训练框架级。
  • 每一步只引入一个新变量，出现劣化时才能归因到具体层。
  • 跳过某一层会导致"NCCL 慢"无法定位到根因，例如把 PCIe 瓶颈误判为网络带宽不足。
关键结论：分层验收是 RDMA 问题定位的底线：裸链路基线 → Fabric → NCCL → 训练，每一步必须单独验证，否则无法做有效归因。

RDMA 指标如何映射到 NCCL 集合通信性能？Communication
来源：交付件《RDMA 验收测试用例清单与 NCCL 映射》§02
问题描述

perftest 测出的带宽、时延、消息率、GDR 能力等，如何对应到 nccl-test 的 algbw / busbw / latency？

回答要点
  • 单连接带宽 → ring/tree 每通道吞吐，决定 algbw / busbw 上限；ring 每卡流量 = 2(N−1)/N × S。
  • 单消息时延 → 集合通信 step time；ring 时延主导场景 T_lat ≈ 2(N−1) × lat，N=1024 时单跳 +1 μs ≈ 全集群 +2 ms。
  • 消息率 Mpps → 小 size 集合通信的 algbw 天花板；当 size/B < 1/MTT 时，algbw ≈ Mpps × size。
  • GDR 能力 → 决定 NCCL 实际落点；非 GDR 路径下需要约 2 × 网络带宽 的 PCIe 余量。
关键结论：RDMA 指标不是孤立数字，必须换算成 NCCL 的理论边界：大消息看 busbw ≤ 2(N−1)/N × RDMA 基线，小消息看 2(N−1)×lat，小消息还要看 Mpps 上限。

为什么 GDR 路径在 ≥400G 网络中几乎是必选项？Communication
来源：交付件《RDMA 验收测试用例清单与 NCCL 映射》§00 / §D
问题描述

非 GDR 路径下，为什么即使 RDMA 测速达标，NCCL 训练仍可能跑不满？

回答要点
  • 非 GDR 路径：数据走 设备内存 → 主机内存 → 网卡 和 网卡 → 主机内存 → 设备内存，共两段 PCIe。
  • 单向总需求约 2 × 网络带宽：400 GbE ≈ 50 GB/s → 非 GDR 需 100 GB/s PCIe；Gen4 x16 实际约 28–32 GB/s，会先于网络打满。
  • 800 GbE = 100 GB/s → 非 GDR 需 ~200 GB/s，只有 Gen5 x16（≈ 250 GB/s）才勉强够。
  • GDR 让 NIC 直接 DMA 读写设备内存，省掉主机内存中转和一段 PCIe，是小包时延降 15–30%、带宽提升 10–30% 的关键。
关键结论：≥ 400G 端口必须启用 GDR 或 NPU-DPU 同 switch 直连高带宽总线，否则 RDMA 验收达标也落不到 NCCL 训练吞吐上。

今日技术知识点沉淀

1. REACT 与网络层/调度层优化的关系

  • 路由优化解决"流走哪条路径"，REACT 解决"谁来发/收这条流"，两者互补。
  • REACT 特别擅长规避 unavoidable link 拥塞（如服务器-ToR 被外部流量持续占用），而自适应路由对此无能为力。

2. RDMA → NCCL 反向推导四步法

  • ① 看 NCCL_DEBUG=INFO 实际选 ring/tree、用几条 rail；
  • ② 大消息慢：用 busbw_理论 = 2(N−1)/N × RDMA 基线 比对实测 busbw；
  • ③ 小消息慢：用 2(N−1) × lat_RDMA 估算，超出部分多为 CPU 轮询或 GPU copy 未并行；
  • ④ 带宽"正常但时间飘"：直接查 PFC/ECN 与抖动，而不是继续加 QP。

3. RDMA 验收的四大典型坑

  • 只测 ib_write_bw 大包不看 ib_write_lat → 小集合通信全线失守；
  • 只测 host bounce 不测 GDR → 无法证明 NCCL 拿到设备内存直访收益；
  • 用峰值而不是稳定态中位数 + p99 → 掩盖抖动，训练先炸；
  • 把"switch 无丢包"当成"无损" → PFC/ECN 未配好时统计上丢 0，但吞吐已在震荡。

4. REACT 生产化集成锚点

  • 最自然入口：扩展 PyTorch ProcessGroupNCCL 或 NCCL src/graph/search.cc 的运行时重搜索接口。
  • FCT 采集：在 NCCL src/transport.cc 或 ext-net profiler 钩子插入测量。
  • 新模式分发：复用 NCCL bootstrap（src/bootstrap.cc）或 Gloo 控制面。
