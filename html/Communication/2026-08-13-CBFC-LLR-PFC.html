Overview

概述：无损以太网的三层防线

问题背景

在 AI/HPC 大规模集群中，RDMA/RoCE 等内存语义操作要求微秒级延迟和零丢包。传统以太网在缓冲区溢出时直接丢包，依靠 TCP 端到端重传，延迟高达毫秒级，无法满足 AI 训练中 All-Reduce 等同步操作的严苛要求。为此，业界定义了三类链路层机制来构建无损以太网：

机制 全称 标准 核心作用 解决的问题
PFC Priority-based Flow Control IEEE 802.1Qbb 按优先级暂停上游发送 缓冲区溢出丢包
CBFC Credit-Based Flow Control UEC v1.0 基于信用额度控制发送 缓冲区溢出丢包（PFC 的进化版）
LLR Link Layer Retry UEC v1.0 链路层本地重传 物理层误码/FCS 错误丢包

三者的关系

  • PFC / CBFC 解决的是拥塞丢包——通过流控防止接收端缓冲区溢出。CBFC 是 PFC 的进化替代方案，两者可互换使用。
  • LLR 解决的是误码丢包——通过链路层重传恢复物理层错误导致的丢包。LLR 与 PFC/CBFC 正交，可组合使用。
  • 三者共同构成：流控防溢出 + 重传防误码 = 完整无损链路。

Part 1

PFC — 基于优先级的流量控制 IEEE 802.1Qbb

1.1 功能原理

核心机制

PFC 是对传统 IEEE 802.3x PAUSE 帧的增强。传统 PAUSE 帧会暂停链路上所有流量，而 PFC 将流量按 802.1Q VLAN 标签中的 PCP 字段分为 8 个优先级（Priority 0~7），每个优先级独立控制暂停与恢复，互不干扰。

工作逻辑：

  1. 接收端监控每个优先级队列的缓冲区占用率
  2. 当某优先级队列达到 XOFF 阈值时，向发送端发送 PFC PAUSE 帧
  3. PAUSE 帧携带 8 位优先级使能向量和各优先级的暂停时间
  4. 发送端收到后，停止对应优先级的发送，其他优先级不受影响
  5. 缓冲区占用降至 XON 阈值以下时，发送 PFC RESUME 帧（Time=0），恢复发送

关键特征：

  • 纯链路层（L2）机制，MAC 控制帧，不涉及上层协议
  • 单跳（one-hop）帧，不会被转发到其他链路
  • 硬件实现，响应延迟 < 1μs
  • 目的 MAC 为专用组播地址 01-80-C2-00-00-01，链路层终止

1.3 DCBx 协商机制

DCBx 协议概述

PFC 的自动协商通过 DCBx（Data Center Bridging eXchange） 完成，定义于 IEEE 802.1Qaz。DCBx 基于 LLDP（Link Layer Discovery Protocol） 扩展，通过 TLV（Type-Length-Value）在直连邻居间交换 DCB 配置信息。

DCBx 状态机（5 个状态）

状态处理逻辑转移条件
Init 初始化本地配置、能力与一致性 邻居存在 → Advertisement
Advertisement 向邻居通告本地 DCB 配置 邻居存在且本地 willing → Collection
Collection 收集邻居配置信息 无条件 → Update
Update 根据协商规则将邻居配置与本地配置比对，更新本地配置 无条件 → Monitoring
Monitoring 监控本地和邻居配置变化 检测到变化 → Init

PFC Configuration TLV (SubType = 0x0B)

字段长度说明
TLV Header (Type=127)2B固定 127，标识组织特定 TLV
OUI3B0x0080C2（IEEE）
SubType1B0x0B（PFC Configuration）
SubType Length1B6 字节
PFC Enable1B8-bit bitmap，每 bit 对应一个优先级是否启用 PFC

协商规则：
  • 双方必须配置相同的 DCBx 版本（IEEE 802.1Qaz 或 CEE）
  • PFC 使用对称属性传递（symmetric），双方配置必须一致
  • 如果一方 willing=1，则接受另一方推荐的配置
  • 如果双方都 willing=0（unwilling），则各自使用本地配置，仅检测不一致
  • 协商结果不一致时，DCBx 设置 Error 标志位，触发告警

1.4 参数配置机制

核心参数

参数 含义 典型值 配置原则
XOFF 阈值 触发 PFC 暂停的缓冲区占用上限 缓冲区容量的 80%~90% 需预留足够余量吸收 PAUSE 生效前到达的数据
XON 阈值 触发 PFC 恢复的缓冲区占用下限 比 XOFF 低 10%~20% 迟滞设计，避免频繁触发 ON/OFF 振荡
Headroom 缓冲区 发送端收到 PAUSE 后到实际停止发送期间，已发出但未到达的数据量 ≥ RTT × 链路带宽 + MTU 不足会导致缓冲区溢出丢包；过大浪费缓冲区资源
Pause Time PAUSE 帧中指定的暂停时长 65535 quanta（持续暂停） 设为最大值表示持续暂停，由 RESUME 帧（Time=0）解除
PFC 优先级映射 哪些优先级启用 PFC P3 (RoCEv2)、P4 (FCoE) 等 仅对需要无损传输的流量启用

Headroom 计算公式

Headroom 必须满足以下条件才能保证零丢包：

Headroom = B_dp + B_d + B_r + B_p B_dp = Downstream Pause Delay 下游发送 PAUSE 帧的处理延迟 B_d = PAUSE Frame Transit Delay PAUSE 帧在链路上的传输延迟 (= RTT/2) B_r = Upstream Reaction Delay 上游收到 PAUSE 后停止发送的响应延迟 B_p = Packets In Flight PAUSE 生效前已在链路上飞行中的数据包 简化估算: Headroom ≥ (RTT × Link_Bandwidth) + MTU 示例 (100Gbps 链路, RTT = 2μs, MTU = 9000B): Headroom ≥ (2×10⁻⁶ × 100×10⁹ / 8) + 9000 ≥ 25000 + 9000 ≥ 34000 Bytes ≈ 34 KB

1.6 异常场景与响应机制

异常场景 1：PFC 死锁（Deadlock）

死锁成因

PFC 暂停形成循环依赖：设备 A 暂停 B，B 暂停 C，C 暂停 A。所有方向的流量都被暂停，无人能释放缓冲区，网络永久阻塞。

响应机制

  • PFC Watchdog：监控每个优先级的 PFC 暂停持续时间，超过阈值则强制丢弃该优先级报文，释放缓冲区
  • 拓扑设计：规划无环拓扑或使用 DCBx 检测环路
  • 多路径路由：ECMP/包喷射避免所有流量走同一路径
异常场景 2：PFC 风暴（PFC Storm）

风暴成因

多跳 PFC 级联触发：下游拥塞 → 暂停上游 → 上游缓冲区满 → 暂停更上游 → 全网流量停滞。微秒级延迟突增。

响应机制

  • PFC Watchdog 速率限制：限制 PFC 帧发送速率
  • ECN + DCQCN：在 PFC 触发前通过 ECN 降速，减少 PFC 触发频率
  • 缓冲区 watermark 监控：设置 PFC 触发告警阈值
异常场景 3：Head-of-Line Blocking（队头阻塞）

队头阻塞成因

PFC 暂停的是整个优先级队列。即使队列中只有一条流导致拥塞，该优先级的所有流都被暂停，包括无关流。

响应机制

  • 多优先级隔离：将不同业务映射到不同 PFC 优先级
  • 包喷射（Packet Spraying）：将同一流分散到多路径，降低单点拥塞概率
异常场景 4：Headroom 不足导致丢包

成因

Headroom 缓冲区不足以吸收 PAUSE 生效前到达的数据，导致缓冲区溢出丢包。常见于长距离链路（RTT 大）或高带宽链路。

响应机制

  • 动态 Headroom 调整：根据链路速率和距离计算所需 Headroom
  • buffer-extended 模式：Cisco 8000 等设备支持长距离 PFC 的扩展缓冲模式
  • 降低 XOFF 阈值：提前触发 PFC，留更多余量
异常场景 5：DCBx 协商失败

成因

两端 DCBx 版本不一致、LLDP 未启用、PFC 配置不匹配（一端启用 P3，另一端未启用）。

响应机制

  • DCBx 设置 Error 标志位并触发 Syslog 告警
  • 如果本地 willing=0，保持本地配置不变，仅告警
  • 如果本地 willing=1，回退到默认配置（通常 PFC 全部关闭）

1.7 PFC Watchdog 死锁防护

PFC Watchdog 机制

PFC Watchdog 是 PFC 的安全网，监控每个优先级的 PFC 暂停持续时间。当某个优先级被持续暂停超过预设阈值时，Watchdog 会强制丢弃该优先级的报文，打破死锁。

Part 2

CBFC — 基于信用的流量控制 UEC v1.0

2.1 功能原理

核心机制

CBFC（Credit-Based Flow Control）是 Ultra Ethernet Consortium (UEC) v1.0 规范定义的新型链路层流控机制，旨在替代或与 PFC 配合使用。

与 PFC 的本质区别：

  • PFC 是反应式（reactive）：缓冲区满了才发 PAUSE，上游必须预留 Headroom 吸收飞行中的数据
  • CBFC 是预防式（proactive）：发送端先检查信用额度，有额度才发，保证接收端不会溢出

工作逻辑：

  1. 接收端为每个虚拟通道（VC）分配缓冲区，并初始发放信用额度给发送端
  2. 发送端发送数据前，检查本地可用信用是否 ≥ 包大小
  3. 满足则发送，并从本地信用中扣除包大小
  4. 接收端消费数据包（从缓冲区移出）后，通过更新消息将信用返还给发送端
  5. 发送端定期向接收端发送信用计数器同步消息，防止信用泄漏

核心保证：只有在接收端有足够缓冲区空间时才发送数据包，从根本上消除缓冲区溢出丢包。

2.2 信用机制与计数器设计

双计数器架构

CBFC 在发送端和接收端各维护两个 20 位循环计数器，按虚拟通道（VC）独立维护：

计数器位置含义位数
Credits Consumed (CC) 发送端 已消耗的信用总量（已发送的数据量） 20-bit
Credits Available (CA) 发送端 可用信用 = 初始信用分配 + 接收端累计释放信用 - 本地累计消耗信用 20-bit
Credits Freed (CF) 接收端 已释放的信用总量（已消费的数据量） 20-bit
Credits Granted (CG) 接收端 已授予的信用总量（初始分配 + 后续返还） 20-bit

信用计算公式

发送端可用信用计算 (核心公式): ┌──────────────────────────────────────────────────────────────┐ │ Credits_Granted = Initial_Credit_Grant + Credits_Freed │ │ (初始分配) (接收端累计释放) │ │ │ │ Available_Credit = Credits_Granted - Credits_Consumed │ │ = Initial_Credit_Grant │ │ + Credits_Freed (remote) │ │ - Credits_Consumed (local) │ └──────────────────────────────────────────────────────────────┘ ⚠️ 关键理解：Credits_Granted 和 Credits_Consumed 都是【累计计数器】 - Credits_Granted 不是"接收端本次返回的信用增量" 而是初始分配 + 所有历史释放信用的累加总和 - Credits_Consumed 不是"当前已用信用" 而是从链路建立以来发送的所有数据量的累加总和 - 两者相减得到的差值才是"当前可用信用" 发送决策: ┌─────────────────────────────────────────────┐ │ if (Available_Credit >= Packet_Size) │ │ -> send packet │ │ -> Credits_Consumed += Packet_Size │ │ else │ │ -> pause this VC, wait for credit upd │ └─────────────────────────────────────────────┘ 接收端信用返还: ┌─────────────────────────────────────────────────────────┐ │ When packet leaves Rx buffer (consumed): │ │ -> Credits_Freed += Packet_Size (cumulative) │ │ -> send update msg(Credits_Freed) to sender │ │ -> sender: Credits_Granted = Initial_Grant + CF │ │ (NOT overwrite; recompute CG from cumulative CF) │ └─────────────────────────────────────────────────────────┘ 数值推演示例 (初始信用 = 100 字节): Time Event CF CC CG=Init+CF Avail=CG-CC ---- ------------------------- -- -- ----------- ------------ T0 Init, grant=100 0 0 100+0=100 100-0 = 100 T1 Send 10 bytes 0 10 100 100-10 = 90 T2 Rx 10B (buffered) 0 10 100 90 (no chg) T3 Rx consume, free 10 10 10 100+10=110 110-10 = 100 -> send CF=10 to Tx T4 Send 20 bytes 10 30 110 110-30 = 80 T5 Rx consume, free 20 30 30 100+30=130 130-30 = 100 -> send CF=30 to Tx → 可见: 只要接收端消费速度 ≥ 发送速度, 可用信用会持续恢复 → 如果接收端消费慢, CF 增长慢, Available 下降, 发送端自动减速 20-bit 循环计数器: ┌─────────────────────────────────────────────┐ │ 计数范围: 0 ~ 1,048,575 (2²⁰ - 1) │ │ 回绕处理: 模 2²⁰ 运算 │ │ 最大可追踪: 1MB 信用 (以字节为单位) │ │ 足以覆盖 MTU=9000B 的多包场景 │ └─────────────────────────────────────────────┘

为什么用累计计数器而不是增量？

  • 幂等性：接收端发送的 CF 是累计值，即使同一消息重复到达，发送端覆盖 CG 也不会出错
  • 抗丢包：如果某次 CF 更新丢失，下一次 CF（更大的累计值）到达后直接覆盖，丢失的信用自动补回
  • 回绕安全：20-bit 模运算天然支持回绕，只要 Available ≥ 0（模运算意义上）即可发送
  • 同步机制：发送端定期发送本地 CC 给接收端，接收端可验证 CG - CC 是否等于实际缓冲区占用，发现不一致即补偿
信用泄漏防护：
  • 由于 CF 是累计值，单次信用更新消息丢失不会造成永久泄漏——下一次 CF（更大的累计值）到达后自动补回
  • 但如果连续多次信用更新消息都丢失，发送端的 Available 会持续下降（虽然实际缓冲区已空），导致发送端误以为信用不足而停发——这就是"信用泄漏"
  • 防护机制：发送端定期（低频）向接收端发送 Credits_Consumed 计数器同步消息（64B Sync Packet）
  • 接收端比对：CG(local) - CC(reported) 应等于当前缓冲区实际占用；若不一致，说明有更新消息丢失，接收端主动发送修正后的 CG 值补偿
  • 这与 InfiniBand 的信用机制类似，确保长期运行下信用不丢失

2.4 虚拟通道（VC）架构

VC 设计

CBFC 支持多达 32 个虚拟通道（VC0~VC31），每个 VC 独立维护信用计数器，独立控制流量。这比 PFC 的 8 个优先级更精细。

每个 VC 可以独立配置：

  • 缓冲区大小：低吞吐 VC 分配更少缓冲区
  • 初始信用额度：决定该 VC 的突发吸收能力
  • 优先级：调度器中的调度优先级
  • 无损/有损模式：可以选择是否启用 CBFC（有损 VC 不需要信用控制）

2.5 LLDP 协商

CBFC 协商机制

CBFC 通过 LLDP 扩展进行链路级协商，与 LLR 共享同一协商框架：

  1. 链路建立后，两端通过 LLDP 交换能力信息
  2. LLDP TLV 携带 CBFC 能力描述：支持的 VC 数量、每个 VC 的缓冲区大小、初始信用额度
  3. 双方比对能力，选择共同支持的配置
  4. 协商成功后，初始化各 VC 的信用计数器，开始正常数据传输
  5. 如果协商失败，CBFC 不启用，回退到 PFC 或无流控模式

协商参数：

  • 支持的 VC 数量（1~32）
  • 每个 VC 的缓冲区大小（字节数）
  • 初始信用额度
  • 信用更新消息频率（高频消息间隔、低频同步消息间隔）
  • 是否与 PFC 共存（可配置为 CBFC-only 或 CBFC+PFC）

场景：CBFC 信用流转完整周期
初始状态: 接收端 VC[0] 缓冲区大小 = 64KB, 初始信用分配 = 64KB 发送端: Initial_Grant=64KB, Credits_Freed=0, Credits_Consumed=0 Credits_Granted = 64KB + 0 = 64KB Available_Credit = 64KB - 0 = 64KB Step 1: 发送端要发 9KB 包 Available_Credit(64KB) ≥ 9KB → 允许发送 Credits_Consumed = 9KB Available_Credit = 64KB - 9KB = 55KB Step 2: 接收端收到 9KB 包，放入缓冲区 缓冲区占用 = 9KB, 剩余 = 55KB (信用已在发送端扣除，接收端不需额外操作) Step 3: 接收端消费(转发)该包，缓冲区释放 9KB Credits_Freed += 9KB → CF = 9KB (累计) → 发送高频信用更新消息 (8B Ordered Set): VC=0, Credits_Freed = 9KB (累计值) Step 4: 发送端收到更新 Credits_Granted = Initial_Grant + CF = 64KB + 9KB = 73KB Available_Credit = 73KB - 9KB = 64KB (恢复) Step 5: 发送端再发 9KB 包 Credits_Consumed = 18KB Available_Credit = 73KB - 18KB = 55KB Step 6: 接收端消费第二个包, 释放 9KB Credits_Freed = 18KB (累计) Credits_Granted = 64KB + 18KB = 82KB Available_Credit = 82KB - 18KB = 64KB (再次恢复) Step 7: 定期同步 (低频, 如每100μs) 发送端 → 接收端: 发送 64B Sync Packet 携带 VC[0] Credits_Consumed = 18KB 接收端比对: CG(local) - CC(reported) = 82KB - 18KB = 64KB vs 实际缓冲区占用 (应为0, 因都已消费) → 64KB ≠ 0KB → 不一致! 说明有信用更新消息丢失 → 接收端补偿: 直接发送 CG = 64KB (重置为正确值) 稳态运行: 信用在发送端和接收端之间循环流转 发送 → 消费 → 返还信用 → 再发送 缓冲区永远不会溢出 (因为有信用才发)

2.7 异常场景与响应机制

异常场景 1：信用更新消息丢失

成因

高频信用更新消息（8B Ordered Set）因物理层错误丢失，发送端可用信用逐渐减少（信用泄漏）。

响应机制

  • 低频同步消息：发送端定期发送 CC 计数器值给接收端，接收端比对后补偿丢失的信用
  • 计数器回绕保护：20-bit 循环计数器设计确保即使多条更新消息丢失，同步后仍能正确恢复
  • 降级而非丢包：信用不足时发送端只是暂停发送，不会丢包。缓冲区不会溢出
异常场景 2：接收端缓冲区异常（如故障）

成因

接收端缓冲区硬件故障导致无法消费数据，信用不再返还。发送端可用信用耗尽后永久暂停。

响应机制

  • 信用超时检测：发送端监控信用长时间不增长的情况，触发告警
  • 链路重置：通过 LLDP 重新协商，重新初始化信用计数器
  • 故障隔离：将该链路标记为不可用，流量切换到备用路径
异常场景 3：VC 配置不匹配

成因

LLDP 协商中两端 VC 数量、缓冲区大小或信用额度配置不一致。

响应机制

  • LLDP 协商失败，CBFC 不启用
  • 回退到 PFC（如果 PFC 也已配置）或无流控模式
  • 触发 Syslog 告警，提示管理员检查配置
异常场景 4：与 LLR 交互时的信用处理

成因

当 LLR 重传一个数据包时，该包的信用已在第一次发送时扣除。重传时不应再次扣除信用，否则会导致可用信用虚减。

响应机制

  • 重传不扣信用：LLR 重传是同一包的重发，信用已在首次发送时扣除
  • 接收端去重：接收端收到重传包后，不重复计入缓冲区占用
  • CBFC + LLR 协同设计：UEC 规范明确规定了两者交互时的信用处理规则

Part 3

LLR — 链路层重试 UEC v1.0

3.1 功能原理

核心机制

LLR（Link Layer Retry）是 UEC v1.0 定义的链路层重传机制，用于在点到点链路上本地恢复物理层错误导致的丢包。

与 PFC/CBFC 的区别：PFC/CBFC 解决拥塞丢包，LLR 解决误码丢包。两者正交，可组合使用。

与 TCP 重传的区别：

  • TCP 重传是端到端的，涉及整个协议栈，延迟可达毫秒级
  • LLR 是逐跳的，仅涉及链路层，重传超时可绑定到链路 RTT（≈1μs），远快于 TCP
  • LLR 不处理拥塞丢包，只处理物理层错误（FCS 错误、不可纠正的 FEC 错误）

工作逻辑：

  1. 发送端为每个 LLR 合格帧分配序列号（Sequence Number），编码在以太网帧前导码中
  2. 发送端将帧存入重放缓冲区（Replay Buffer）
  3. 接收端检查 FCS 和序列号连续性，正确则发送 ACK，错误则发送 NACK
  4. 发送端收到 ACK 后释放重放缓冲区中的对应帧
  5. 收到 NACK 或超时未收到 ACK，从重放缓冲区重传

重传策略：Go-back-N

  • 接收端检测到错误后，丢弃该帧及之后所有帧（即使后续帧 FCS 正确）
  • 发送 NACK 指示缺失的序列号
  • 发送端从缺失序列号开始重传所有后续帧
  • 选择 Go-back-N 而非选择性重传的原因：链路层无需理解上层排序需求，实现更简单

  • 并非所有帧都启用 LLR——MAC 客户端可以标记帧是否需要 LLR
  • 非 LLR 帧作为标准以太网帧发送，不分配序列号，不存入重放缓冲区
  • LLR 帧分配序列号并存入重放缓冲区，直到收到 ACK
  • 这种设计允许 LLR 与非 LLR 流量在同一链路上共存

3.3 ACK/NACK 机制

ACK（确认）

  • 累积式（cumulative）：ACK 携带最近成功接收的序列号，表示该序列号及之前的所有帧都已正确接收
  • 不需要每帧一个 ACK：ACK 是定频发送的（paced），减少控制消息开销
  • 重发机制：ACK 在指定间隔内重复发送，以应对 ACK 本身丢失的情况
  • 发送端收到 ACK 后，释放重放缓冲区中对应序列号及之前的所有帧

NACK（否定确认）

  • 立即发送：接收端检测到错误后尽快发送 NACK，不等待下一个 ACK 周期
  • 触发条件 1：FCS 校验失败——帧在传输中被损坏
  • 触发条件 2：序列号不连续（跳号）——检测到丢帧
  • 只发一次：NACK 只发送一次，避免发送端误解多个 NACK 为需要多次重传
  • NACK 携带期望的序列号（即缺失的第一个序列号）

3.4 重放缓冲区与 Go-back-N

重放缓冲区（Replay Buffer）

发送端维护一个重放缓冲区，存储所有已发送但未收到 ACK 的 LLR 帧。缓冲区大小决定了 LLR 的可达距离（Reach）：

Replay Buffer Structure: ┌─────────────────────────────────────────────┐ │ Replay Buffer (FIFO) │ ├──────────┬──────────┬──────────┬───────────┤ │ Frame │ Frame │ Frame │ Frame │ │ SN=3 │ SN=4 │ SN=5 │ SN=6 │ │ (pending)│ (pending)│ (pending)│ (pending) │ └──────────┴──────────┴──────────┴───────────┘ ↑ ↑ Oldest unacked Latest sent On ACK(SN=5): → Release SN=3, 4, 5 → Buffer keeps SN=6 only On NACK(SN=4): → Retransmit from SN=4 → Resend SN=4, 5, 6... Reach (buffer size for full bandwidth): ┌─────────────────────────────────────────────┐ │ Replay_Buffer_Size >= RTT * Bandwidth │ │ + ACK_Interval * Bandwidth │ │ + MTU │ │ │ │ Example (400G, RTT=2us, ACK=1us, MTU=9KB) │ │ Buffer >= (2+1)us * 400G/8 + 9KB │ │ >= 150KB + 9KB ~ 159KB │ └─────────────────────────────────────────────┘
Go-back-N 的选择理由：
  • 链路层重传超时可绑定到链路 RTT（≈1μs），远小于端到端 RTT
  • 链路层丢包只由物理层错误引起，不涉及拥塞，丢包率极低（<10⁻¹²）
  • Go-back-N 实现简单，不需要接收端缓存乱序帧
  • 偶发的多余重传（已正确接收的帧被重传）在低误码率下开销可忽略

3.5 控制有序集

控制消息类型

LLR 使用物理层 PCS 子系统的 Control Ordered Sets 传输控制消息，格式与 Sequence Ordered Set（LF/RF）相同，为 8 字节消息，通过唯一的 4-bit O 码区分：

消息类型功能触发时机
INIT 初始化序列号，建立 LLR 会话 链路建立后，LLDP 协商成功时
INIT_ECHO 确认 INIT，完成握手 收到 INIT 后
ACK 累积确认已接收的序列号 定频发送（paced）
NACK 否定确认，请求重传 检测到 FCS 错误或序列号跳变时立即发送

发送时机：控制有序集几乎可以在任意时刻发送——可在 IPG（帧间间隙）中发送，也允许抢占数据帧传输。

3.6 定时器重传机制

定时器的作用

定时器重传提供协议鲁棒性，应对以下场景：

  • NACK 丢失：接收端发送的 NACK 本身因链路错误丢失
  • 帧完全丢失：发送的帧从未到达接收端，接收端无感知（无法发 NACK）
  • ACK 重复丢失：多条 ACK 都丢失，发送端无法确认
  • Tail Loss（尾部丢包）：最后几个帧丢失，接收端没有后续帧触发序列号跳变检测

定时器参数

参数含义典型值
Retransmission Timeout (RTO)未收到 ACK 的超时时间≥ 2×RTT（约 2~5μs）
ACK Interval定频 ACK 发送间隔≈ RTT（约 1μs）

RTO 设置原则：RTO 必须 > 2×RTT，确保至少一个 ACK 周期内有重传机会。由于链路层 RTT 可精确测量（约 1μs），RTO 可设置得很紧凑。

3.7 CRC 毒化机制

CRC 毒化（CRC Poisoning）— 防止 Livelock

问题场景

如果一个数据包在发送端内部就已经损坏（例如 MAC 层以上的数据在写入发送缓冲区时发生位翻转），那么：

  1. 发送端发送损坏的帧，接收端 FCS 校验失败，发送 NACK
  2. 发送端从重放缓冲区重传同一帧（缓冲区中的副本也是损坏的）
  3. 接收端再次 FCS 失败，再发 NACK
  4. 无限循环 → Livelock（活锁）

CRC 毒化解决方案

  • 发送端对 LLR 合格帧设置重传次数计数器
  • 当重传次数超过阈值（如 3 次），发送端认为该帧在重放缓冲区中的副本已损坏
  • 发送端对该帧施加毒化 CRC（故意将 CRC 设为错误值）
  • 接收端收到毒化帧后 FCS 失败，但识别出这是被毒化的帧
  • 接收端将毒化帧作为不可恢复错误上报上层，而不是继续请求重传
  • 上层协议（如 UET Transport）通过端到端重传处理该丢包

3.8 LLDP 协商

LLR 协商流程

LLR 通过 LLDP 扩展进行链路级协商，是逐跳（hop-by-hop）技术：

  1. 链路建立后，两端通过 LLDP 交换 LLR 能力信息
  2. LLDP TLV 携带：是否支持 LLR、序列号空间大小、重放缓冲区大小、ACK 间隔、RTO 等
  3. 如果双方都支持且参数匹配，协商成功
  4. 执行 LLR 初始化握手：INIT → INIT_ECHO，同步序列号
  5. 进入正常 LLR 操作模式

3.10 异常场景与响应机制

异常场景 1：帧损坏（FCS 错误）

响应流程

  1. 接收端 FCS 校验失败
  2. 立即发送 NACK（期望 SN = 当前缺失的 SN）
  3. 丢弃该帧及之后所有帧（Go-back-N）
  4. 发送端收到 NACK，从重放缓冲区重传
  5. 重传帧 FCS 正确 → 恢复正常
异常场景 2：帧完全丢失（未到达接收端）

响应流程

  1. 接收端未收到帧，但下一个帧的 SN 跳变（如期望 SN=3，收到 SN=4）
  2. 检测到序列号不连续 → 发送 NACK(SN=3)
  3. 丢弃 SN=4 及之后所有帧
  4. 发送端从 SN=3 开始重传

如果丢失的是最后一个帧（tail loss）：接收端没有后续帧触发跳变检测 → 依靠发送端定时器超时重传。

异常场景 3：NACK 丢失

响应流程

  1. 接收端发送 NACK，但 NACK 本身因链路错误丢失
  2. 发送端未收到 NACK，继续发送新帧
  3. 接收端收到新帧但 SN 不连续，再次发送 NACK（但 NACK 只发一次！）
  4. 如果第二个 NACK 也丢失 → 依靠发送端 RTO 定时器超时
  5. RTO 超时后，发送端从最早未确认的 SN 开始重传
异常场景 4：ACK 丢失

响应流程

  1. ACK 是定频重发的，丢失一条 ACK 不影响
  2. 下一条 ACK 会累积确认更多帧
  3. 如果所有 ACK 都丢失 → RTO 超时触发重传
  4. 重传后接收端回复 ACK，恢复正常
异常场景 5：CRC 毒化（Livelock）

响应流程

  1. 同一帧重传超过阈值（如 3 次）仍 FCS 失败
  2. 发送端判定重放缓冲区中的副本已损坏
  3. 对该帧施加毒化 CRC 后发送
  4. 接收端识别毒化帧，上报不可恢复错误
  5. 上层协议处理丢包（端到端重传）
  6. LLR 从下一个 SN 继续，不影响后续帧
异常场景 6：链路断开与恢复

响应流程

  1. 物理层检测到链路断开（Loss of Signal）
  2. LLR 会话终止，重放缓冲区中的帧全部丢失
  3. 上层协议负责端到端重传这些帧
  4. 链路恢复后，重新通过 LLDP 协商 LLR 参数
  5. 执行 INIT → INIT_ECHO 握手，重新初始化序列号
  6. 从 SN=1 重新开始正常传输

五、一句话总结

PFC 用"红灯停"（PAUSE）防止缓冲区溢出，CBFC 用"预算制"（信用额度）更精细地预防溢出，LLR 用"本地重传"（Go-back-N + ACK/NACK）快速恢复误码丢包。三者组合构成 UEC 无损以太网的完整防线：CBFC/PFC 保证不丢、LLR 保证恢复、UET Transport 保证端到端可靠。
