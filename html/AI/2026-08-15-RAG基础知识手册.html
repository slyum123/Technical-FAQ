RAG手册/01-基础概念/

第一章 基础概念

1.1 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是一种把"外部知识检索"与"大模型生成"结合的技术范式： 在模型回答问题之前，先从外部知识库中检索出与问题相关的资料片段，把这些片段注入模型的上下文窗口， 让模型基于给定的资料生成回答，而不是仅依赖训练时记住的参数化知识。

+-----------------+ User Query -->| Retriever |--> Top-K relevant chunks | (检索器) | (向量库/BM25/知识图谱) +-----------------+ | | inject into context v +-----------------+ Answer <-- | LLM (生成器) |<-- "参考资料 + 问题" Prompt | DeepSeek/GPT.. | +-----------------+

可以把 RAG 理解为"开卷考试"：大模型本身的参数知识是"闭卷"记忆，会过时、会记错、会编造； RAG 相当于考试时临时递给它几页相关资料，让它照着资料答题并标注出处。

一句话定义：RAG = 非参数化知识（外部知识库）+ 参数化知识（大模型）的运行时融合， 通过检索把正确答案的"证据"送进上下文，把生成约束在证据范围内。

1.2 为什么需要 RAG：四大痛点

大模型固有问题表现RAG 如何解决
知识截止模型只认识训练截止日期之前的世界，问新发布的产品规格、新政策一无所知知识库可随时增量更新，重新索引即可，模型无需重训
幻觉一本正经地编造不存在的 API、参数、数据提示词强制"只依据参考资料回答"，无依据时明确拒答
私有知识缺失企业内部文档、代码库、工单从未进入训练集私有数据本地向量化，检索后送模型，数据不出域
不可溯源无法验证答案从哪来，金融/医疗/法律场景不可接受答案附带引用来源（文档名+页码+块编号）

成本视角：为什么不是"直接微调"或"塞满上下文"

  • 微调（Fine-tuning）：一次全参微调 7B 模型需要数十万元算力；知识更新一次就要重训一次；且微调擅长改行为风格而非注入事实——事实类知识用微调效果差且易灾难性遗忘
  • 长上下文（Long Context）：把 100 万 token 全塞进窗口技术上可行，但每次请求的成本是检索的几十倍；且存在"lost in the middle"——模型对窗口中部内容注意力显著下降
  • RAG：只检索最相关的 3~5 个块（几千 token）送入模型，成本可控、精度可控、知识可随时更新

1.3 RAG vs 微调 vs 长上下文

维度RAG微调 Fine-tuning长上下文 Long Context
注入知识类型事实/知识（文档、手册、数据库）行为/风格（格式、语气、领域话术）临时上下文（本次会话相关材料）
知识更新重新索引即可，分钟级需重训，天~周级换一份上下文即可
单次成本低（只送 top-k 块，约 2k token）一次性高（训练算力）高（每次送全量，10k~1M token）
可溯源✅ 天然支持引用❌ 知识熔入参数，无法溯源✅ 可溯源
数据隐私✅ 向量库可完全本地化训练数据集需专门保管数据需随请求发送
典型场景企业知识库问答、客服、文档助手领域风格适配、结构化输出训练单本书/单仓库分析
实践结论：三者不是互斥关系。生产系统的常见组合是 RAG 注入事实 + 少量微调（或 prompt 约束）统一输出风格 + 长上下文兜底长文档。 知识频繁变化 → RAG；行为需要改变 → 微调；单文档深度分析 → 长上下文。

1.4 RAG 的三阶段演进

阶段时间核心思想代表技术
Naive RAG2020-2023索引 → 检索 → 生成 三步流水线，一次检索一次生成原论文（Lewis et al., 2020）、LangChain QA chain
Advanced RAG2023-2024检索前后优化：查询改写、混合检索、重排、上下文压缩HyDE、Multi-Query、BM25+向量融合、Cross-Encoder Rerank
Modular/Agentic RAG2024-至今模块化编排，Agent 自主决定是否检索、检索什么、迭代几轮Self-RAG、CRAG、GraphRAG、LangGraph 多智能体
Naive: Query ---> Retrieve ---> Generate ---> Answer (one-shot) Advanced: Query --> Rewrite --> Hybrid Retrieve --> Rerank --> Generate (HyDE/MultiQuery) (BM25+Dense) (CrossEncoder) Agentic: Query --> [Agent: plan] --> retrieve? --yes--> evaluate ^ | |____ refine query <--- low confidence | v multi-hop / graph / tool calls --> Generate

本手册第 2、3 章覆盖 Naive + Advanced 的完整工程实现（这也是当前生产系统的主体）， 第 5 章介绍 GraphRAG 与 Agentic RAG 前沿方向。

RAG手册/02-核心组件与流程/

第二章 核心组件与流程

2.1 总体架构：离线 + 在线两条流水线

任何 RAG 系统都由两条流水线组成：离线索引流水线（构建知识库，数据更新时执行）和在线问答流水线（用户每次提问时执行）。

========== OFFLINE: Indexing Pipeline (run on data update) ========== Raw Docs Loader Splitter Embedder Vector DB (pdf/md/txt) --> (parse+meta) --> (chunk+overlap) --> (text->vector) --> (FAISS/Milvus) | | | v v v {source,page} {chunk_id,idx} 512-dim float32 metadata metadata normalized ========== ONLINE: Query Pipeline (per question) ========== User Query --> [Query Transform] --> [Hybrid Retrieve] --> [Rerank] (rewrite/expand) (BM25 + Vector) (CrossEncoder) | v Answer <-- [LLM Generate] <-- [Prompt Assemble] (+citations) (stream) (context+question)

2.2 文档加载与分块（Chunking）

分块是 RAG 中对检索质量影响最大的单一环节。检索的最小单位是"块"， 块的粒度直接决定了向量语义的纯度和上下文的完整性。

为什么必须分块

  • Embedding 模型输入长度有限（BGE 512 token、BGE-M3 8192 token）
  • 块太大 → 一个向量要表达多个主题，语义稀释，检索不精准
  • 块太小 → 命中的块缺乏上下文，LLM 拿到的是碎片，答不完整
  • 经验区间：300~800 token，重叠 10%~20%

主流分块策略对比

策略原理优点缺点适用
固定长度按字符/token 滑窗切割，带重叠实现最简单，块大小均匀可能切断句子/表格快速原型
递归分隔符优先按 \n\n 切，超长降级到 \n、句号、字符块边界落在自然语义边界块大小不均默认首选（LangChain 默认）
结构感知按 Markdown 标题/HTML 标签/代码函数切保留文档结构语义依赖文档规范技术文档、代码库
语义分块计算相邻句向量距离，在语义突变处切块内语义最纯需额外 embedding 计算高质量问答
父子块小块用于检索命中，命中后返回所属大块兼顾检索精度与上下文完整索引结构复杂生产系统常用
工程要点：元数据（source 文件名、page 页码、heading 章节）必须随块保存， 否则检索命中后无法生成引用来源；表格和代码不要用通用分块器硬切， 应整块保留或走专门的多模态索引通道。

2.3 Embedding 向量化

Embedding 模型是双塔架构（Bi-Encoder）：查询和文档分别独立编码为定长向量， 向量间的余弦相似度代表语义相关度。因为两塔独立，文档向量可以离线预计算， 在线只需编码一次查询 + 一次近邻搜索，代价极低——这是 RAG 可扩展到亿级文档的根基。

Bi-Encoder (dual tower) "What is NVLink bandwidth?" "NVLink 4.0 provides 900GB/s..." | | v Query Encoder Doc Encoder v [Transformer] [Transformer] (weights shared) | | v v q_vec (512-d) ---- cosine(q,d) ---- d_vec (512-d) | v similarity score
模型来源维度最大长度特点
bge-small-zh-v1.5智源 BAAI512512中文小模型，CPU 可跑，适合演示
bge-m3智源 BAAI10248192多语言+多粒度（稠密/稀疏/多向量三合一），当前开源主流
text-embedding-3-largeOpenAI30728191商用 API，支持降维
jina-embeddings-v3Jina10248192多任务 LoRA 适配
BGE 系列使用细节：中文检索任务中，查询端需加指令前缀 为这个句子生成表示以用于检索相关文章：，文档端不加； 向量使用前应 L2 归一化，归一化后内积 = 余弦相似度。

2.5 检索策略：稠密 / 稀疏 / 混合

方式原理擅长弱项
稠密检索 DenseEmbedding 向量近邻（语义匹配）同义改写、跨语言、模糊语义精确术语/型号/缩写易漏
稀疏检索 Sparse/BM25词频统计打分（关键词匹配）专有名词、错误代码、版本号不懂同义词
混合检索 Hybrid双路召回 + 融合两者取长补短，生产主流需要融合策略

BM25 核心公式

score(q, d) = Σ IDF(qi) · f(qi,d)·(k1+1) / ( f(qi,d) + k1·(1-b+b·|d|/avgdl) ) IDF(qi) : rare term -> high idf (discriminative) f(qi,d) : term frequency in doc, saturating via k1 b : length normalization (0.75 typical) No training needed. Pure statistics.

两路结果如何融合：RRF（Reciprocal Rank Fusion）

BM25 分值（无界）和余弦相似度（0~1）量纲不同，直接加权需要精细调参。 RRF 只看每路的排名，天然免调参：

RRF_score(doc) = Σ_routes 1 / (k + rank_route(doc)) (k=60 default) Example: doc A ranked #1 in BM25, #4 in vector doc B ranked #3 in BM25, #2 in vector A: 1/61 + 1/64 = 0.01639 + 0.01563 = 0.03202 B: 1/63 + 1/62 = 0.01587 + 0.01613 = 0.03200 -> A wins (appears high in both routes)

2.6 Rerank 重排序

Embedding（双塔）为了效率牺牲了精度：query 和 doc 从未见过彼此，各自独立编码。 Reranker（Cross-Encoder 单塔）把 query 和 doc 拼接后一起送入模型， 在注意力层做深度交互，精度显著更高——但每个 (q,d) 对都要跑一次前向，无法预计算，只能用在小候选集上。

Bi-Encoder (recall stage) Cross-Encoder (rerank stage) q --> [Enc] --> q_vec q + [SEP] + d --> [Transformer] --> score d --> [Enc] --> d_vec | | v v precise relevance score cosine(q_vec, d_vec) slow: one forward pass PER PAIR fast: precompute d_vec offline usage: rerank top-20 -> keep top-5 | v coarse relevance
阶段模型类型代表候选量延迟量级
粗召回 RecallBi-Encoderbge-m3全库 → top-20/50毫秒级
精排 RerankCross-Encoderbge-reranker-v2-m320 → 5百毫秒级

2.7 生成阶段与 Prompt 组装

生成阶段的核心是把检索结果结构化地注入 Prompt，并通过系统提示词约束模型行为：

# RAG Prompt 的三个要素
1. 系统约束: 只依据参考资料回答 / 无依据时明确拒答 / 标注引用编号
2. 上下文区: [1] (来源: xxx.pdf, p.3) \n 检索块文本...  [2] ...
3. 问题区: 用户原始问题（或改写后的问题）
防幻觉关键设置：① temperature 调低（0~0.3），RAG 要"忠实"不要"创意"； ② 显式给出拒答出口（"知识库中未找到相关内容"是合法答案）； ③ 要求标注引用编号，让幻觉无处藏身——没有来源编号的论断即可疑。

2.8 组件对接关系全景

上游组件→ 下游组件传递的数据结构失败会怎样
Loader→ Splitter[(text, {source, page})]元数据丢失 → 无法溯源
Splitter→ Embedder[(chunk, {chunk_id, ...})]切断语义 → 检索命中但答不完整
Embedder→ VectorStorefloat32[dim] 归一化向量维度/归一化不一致 → 相似度全错
VectorStore→ Retriever[(score, text, meta)]索引与原文错位 → 张冠李戴
Retriever(BM25)→ RRF 融合排名列表单路故障 → 召回率下降
Retriever→ Prompt 组装top-k 块 + 来源混入噪声块 → 干扰模型判断
Prompt 组装→ LLM APImessages=[system, user]超长 → 截断/报错；无约束 → 幻觉
LLM→ 用户/前端流式 token + 引用映射无引用展示 → 不可信

3.2 config.py：配置中心

所有超参数集中在一个 dataclass 里，这是工程上最重要的习惯——分块大小、top_k、温度这些参数需要反复实验调优，集中管理才能快速迭代。

@dataclass
class RAGConfig:
    # ---------- 分块参数 ----------
    chunk_size: int = 512          # 每块目标 token 数
    chunk_overlap: int = 64        # 相邻块重叠，避免语义被切断
    separators: list = field(default_factory=lambda: [
        "\n\n", "\n", "。", "！", "？", ".", "!", "?", " ", ""
    ])                             # 递归分块层级分隔符（从粗到细）

    # ---------- 检索参数 ----------
    top_k: int = 5                 # 最终送入 LLM 的块数
    recall_k: int = 20             # 粗召回数量（rerank 前）
    rrf_k: int = 60                # RRF 融合常数

    # ---------- LLM 参数 ----------
    llm_api_base: str = os.getenv("LLM_API_BASE", "https://api.deepseek.com")
    llm_model: str = os.getenv("LLM_MODEL", "deepseek-chat")
    temperature: float = 0.1       # RAG 要"忠实"，温度调低

    # ---------- Prompt 模板 ----------
    system_prompt: str = (
        "你是一个严谨的知识库问答助手。请只根据下面提供的【参考资料】回答问题。"
        "如果参考资料中没有相关信息，请直接回答'知识库中未找到相关内容'，"
        "禁止编造。回答时请标注信息来源编号，例如 [1]。"
    )
    user_prompt_template: str = (
        "【参考资料】\n{context}\n\n【问题】\n{question}\n\n请基于参考资料回答。"
    )

还有两个辅助细节：format_context() 把检索块拼成带 [1] (来源: xxx.pdf) 编号的上下文——编号供模型引用、来源供前端展示；环境变量读取让切换模型/密钥不需要改代码。

3.3 document_loader.py：加载器（注册表模式）

# 装饰器注册表：新格式只需加一个函数，不改主流程（开闭原则）
LOADERS = {}

def register(suffix):
    def deco(fn):
        LOADERS[suffix] = fn
        return fn
    return deco

@register(".txt")
@register(".md")
def load_text(path):                          # 整篇读入
    text = Path(path).read_text(encoding="utf-8")
    return [(text, {"source": path, "page": 0})]

@register(".pdf")
def load_pdf(path):                           # 逐页提取 + 压缩空白
    import fitz
    doc = fitz.open(path)
    return [(" ".join(p.get_text().split()),
             {"source": path, "page": i + 1})
            for i, p in enumerate(doc)]
设计意图：加载器的输出统一为 [(text, metadata)]—— 元数据从第一站就跟着内容走，一直流到最后生成引用，这是可溯源 RAG 的前提。

3.4 text_splitter.py：递归分块

核心是 recursive_split：用第 1 层分隔符（段落）切 → 相邻片段合并到不超上限 → 单片段仍超长就递归降级到下一层分隔符（句子→字符）。

def recursive_split(text, cfg, separators=None):
    seps = separators if separators is not None else cfg.separators
    final_chunks = []
    sep, rest = seps[0], seps[1:]
    pieces = text.split(sep) if sep else list(text)

    buf = ""
    for piece in pieces:                       # 1. 贪心合并小片段
        candidate = buf + sep + piece if buf else piece
        if _len(candidate) <= cfg.chunk_size:
            buf = candidate
        else:
            if buf: final_chunks.append(buf)
            if _len(piece) > cfg.chunk_size and rest:
                final_chunks.extend(recursive_split(piece, cfg, rest))  # 2. 降级递归
            else:
                buf = piece
    if buf: final_chunks.append(buf)

    # 3. 加重叠：每块开头拼上一块的尾部
    for i in range(1, len(final_chunks)):
        tail = final_chunks[i-1][-cfg.chunk_overlap:]
        final_chunks[i] = tail + final_chunks[i]
    return final_chunks
Example: chunk_size=10, overlap=3, seps = ["\n\n", "\n", "。", ""] Step1 split by "\n\n": [P1(6) P2(25) P3(8)] Step2 merge: P1 ok | P2 > 10 -> split by "\n" -> still >10 -> split by "。" -> sentences (4,9,7,5) -> merge Step3 overlap: chunk1 = "AAAAAA" chunk2 = "AAA" + "BBBBB" <- tail of chunk1 prepended chunk3 = "BBB" + "CCCCC"

为什么要重叠：一个关键句子恰好跨块边界时，重叠保证它至少完整地出现在一个块里，检索才能命中。

3.5 embedder.py：双模式向量化

class Embedder:
    QUERY_PREFIX = "为这个句子生成表示以用于检索相关文章："  # BGE 查询端指令

    def embed_documents(self, texts):          # 文档端：批量、不加前缀
        vecs = self.model.encode(texts, batch_size=32,
                                 normalize_embeddings=True)  # L2 归一化
        return vecs.tolist()

    def embed_query(self, text):                # 查询端：加指令前缀
        vec = self.model.encode([self.QUERY_PREFIX + text],
                                normalize_embeddings=True)
        return vec[0].tolist()
接口调用时机前缀批量
embed_documents离线建索引（一次）不加✅ batch=32
embed_query在线每次提问加 QUERY_PREFIX单条
常见坑：查询和文档必须用同一个模型编码（不同模型的向量空间不兼容）； 归一化必须两端一致，否则相似度计算失真。

3.6 vector_store.py：FAISS 向量库

class VectorStore:
    def build(self, chunks, vectors):
        mat = np.array(vectors, dtype=np.float32)
        faiss.normalize_L2(mat)                     # 双保险归一化
        self.index = faiss.IndexFlatIP(mat.shape[1])  # 内积索引
        self.index.add(mat)                         # 归一化后 IP == cosine
        self.chunks = chunks                        # 旁路存原文，序号对齐

    def search(self, query_vec, top_k):
        q = np.array([query_vec], dtype=np.float32)
        faiss.normalize_L2(q)
        scores, ids = self.index.search(q, top_k)
        return [(float(scores[0][i]), *self.chunks[ids[0][i]])
                for i in range(len(ids[0])) if ids[0][i] != -1]

FAISS 只存向量不存原文，所以原文和元数据放在旁路列表 self.chunks 里，靠序号一一对应（第 i 条向量 ↔ chunks[i]）。 IndexFlatIP 是暴力精确检索，100 万条以内延迟毫秒级；规模再大换 IndexIVFFlat 或 IndexHNSWFlat。

3.7 retriever.py：BM25 + RRF 混合检索 + 重排

BM25 纯手写实现（30 行）

class BM25:
    def __init__(self, docs, k1=1.5, b=0.75):
        self.doc_tokens = [self._tokenize(d) for d in docs]  # 中文按字+英文按词
        self.avgdl = sum(self.doc_len) / max(len(docs), 1)
        df = Counter(tok for toks in self.doc_tokens for tok in set(toks))
        self.idf = {t: math.log((len(docs) - n + 0.5) / (n + 0.5) + 1)
                    for t, n in df.items()}                # 稀有词 IDF 高

    def score(self, query, doc_idx):
        tf = Counter(self.doc_tokens[doc_idx])
        s = 0.0
        for q in self._tokenize(query):
            # IDF · tf·(k1+1) / (tf + k1·(1-b+b·|d|/avgdl))
            s += self.idf[q] * tf[q] * (self.k1+1) / (
                 tf[q] + self.k1*(1-self.b + self.b*self.doc_len[doc_idx]/self.avgdl))
        return s

两阶段检索主流程

def retrieve(self, query):
    # ---- 阶段1: 双路召回 ----
    q_vec = self.embedder.embed_query(query)
    vec_hits = self.store.search(q_vec, self.cfg.recall_k)       # 向量 top-20
    bm25_rank = sorted(range(len(...)), key=..., reverse=True)[:recall_k]

    # ---- RRF 融合: score(d) = Σ 1/(k + rank(d)) ----
    rrf = {}
    for rank, hit in enumerate(vec_hits):
        rrf.setdefault(hit_id, [0, hit])[0] += 1 / (rrf_k + rank + 1)
    for rank, doc_idx in enumerate(bm25_rank):
        rrf[doc_id][0] += 1 / (rrf_k + rank + 1)
    candidates = sorted(rrf.values(), key=lambda x: x[0], reverse=True)

    # ---- 阶段2: 可选 CrossEncoder 精排, 20 -> 5 ----
    if self.cfg.use_rerank:
        ranked = self.reranker.rerank(query, [c[1] for c in candidates], top_k)
        candidates = [candidates[i] for _, i in ranked]
    return candidates[:self.cfg.top_k]
recall_k=20 top_k=5 Vector top-20 --\ /--> [1] score=0.94 \-- RRF merge --(rerank?)--/ --> [2] score=0.91 BM25 top-20 --/ \--> [3] score=0.87 ... rerank off : RRF order kept (fast, ~ms) rerank on : CrossEncoder re-scores 20 (+~200ms, higher precision)

3.8 llm_client.py：OpenAI 兼容客户端

class LLMClient:
    def chat_stream(self, system, user):
        # OpenAI 兼容协议: POST {base}/chat/completions
        with self.http.stream("POST",
            f"{self.cfg.llm_api_base}/chat/completions",
            headers={"Authorization": f"Bearer {self.cfg.llm_api_key}"},
            json={"model": self.cfg.llm_model,
                  "messages": [
                      {"role": "system", "content": system},
                      {"role": "user",   "content": user}],
                  "temperature": self.cfg.temperature,
                  "stream": True}) as resp:   # SSE 流式
            for line in resp.iter_lines():
                if not line.startswith("data: "): continue
                payload = line[6:]
                if payload == "[DONE]": break
                delta = json.loads(payload)["choices"][0]["delta"]
                if content := delta.get("content"):
                    yield content              # 逐 token 吐给上层

4.4 Prompt 全文还原

把 format_context() + 模板 format 之后的完整 user message 展开如下——这就是大模型实际"看到"的全部：

【参考资料】 [1] (来源: ./docs/sample-knowledge.txt) NVLink 是 NVIDIA 的 GPU 专用互连协议。NVLink 4.0（H100）单向带宽 450 GB/s， 双向 900 GB/s，由 18 条 link 组成，每条 link 含 4 条 SerDes，共 72 条 SerDes， 单 SerDes 速率 112 Gbps（PAM4 调制）。 [2] (来源: ./docs/sample-knowledge.txt) PCIe 5.0 x16 单向带宽 64 GB/s，使用 16 条 SerDes，单 SerDes 速率 32 GT/s （NRZ 调制）。 [3] (来源: ./docs/sample-knowledge.txt) 两者的差距来源可以分解为两个因子：单 SerDes 速率差约 3.2 倍（PAM4 vs NRZ）， SerDes 数量差 4.5 倍（72 vs 16），合计约 7 倍的双向带宽差距。 【问题】 NVLink 和 PCIe 的带宽差距是怎么来的？ 请基于参考资料回答。

DeepSeek 的实际回答（示例）：

根据参考资料 [3]，带宽差距来自两个因子的乘积： 1. 单 SerDes 速率差距：NVLink 4.0 为 112 Gbps（PAM4 调制）， PCIe 5.0 为 32 GT/s（NRZ 调制），相差约 3.2 倍 [1][2]； 2. SerDes 数量差距：NVLink 部署 72 条（18 link x 4）[1]， PCIe x16 只有 16 条 [2]，相差 4.5 倍。 两者相乘即得到约 7 倍的双向带宽差距（900 GB/s vs 128 GB/s）。来源：[1][2][3]
对照实验：把同样的问题直接问裸模型（不注入上下文），模型只能靠参数记忆回答， 细节（SerDes 数量、调制方式）极易出错或编造；而注入上下文后，所有数字都可以在资料中找到出处—— 这就是 RAG 对接大模型的价值：把"记忆题"变成"阅读理解题"。

第五章 进阶方向与评估体系

5.1 高级分块与上下文化检索（Contextual Retrieval）

  • Contextual Retrieval（Anthropic, 2024）：分块时先用 LLM 给每个块生成一句"该块在全文中的位置说明"（如"本块出自《NVLink 手册》第 3 章，讨论 SerDes 配置"）拼在块前再向量化。块脱离原文后语义不自足的问题被显著缓解，检索失败率下降约 35%（配合 BM25+Rerank 可达 67%）
  • 父子块（Small-to-Big）：用 128 token 小块做检索（语义纯），命中后返回其所属的 1024 token 父块给 LLM（上下文全）
  • 多模态索引：表格、图片、代码各自走专门通道——表格用 LLM 生成自然语言摘要后入库，图片用多模态 embedding 或 VLM 生成描述

5.2 查询改写技术（检索前优化）

5.3 GraphRAG：图增强检索

向量检索只能回答"局部事实查询"，无法回答全局性问题（"这个数据集里所有实体之间的共性是什么"）。 Microsoft GraphRAG（2024）的思路：索引阶段用 LLM 抽取实体关系构建知识图谱，再做社区聚类（Leiden 算法）并为每个社区生成摘要；查询时既可以走局部（实体邻域）也可以走全局（社区摘要 map-reduce）。

Indexing: docs -> LLM entity/relation extraction -> knowledge graph -> Leiden community clustering -> community summaries (hierarchical) Query: local : entity neighborhood subgraph -> context global : "what are the main themes?" -> map-reduce over community summaries -> context -> LLM vs plain vector RAG: answers questions needing cross-doc synthesis (relationships, trends, global themes)

国内实践案例：蚂蚁集团将 GraphRAG 思路用于金融风控，跨文档证据链整合使风控问答准确率从约 60% 提升到 95%+（来源：公开技术分享）。代价：索引成本高（每篇文档都要过 LLM 抽取），适合高价值静态语料。

5.4 Agentic RAG：从流水线到智能体

传统 RAG 是固定流水线（无论问题难易都走一遍检索），Agentic RAG 让 LLM 自己决策：

  • 是否需要检索——闲聊/常识问题直接回答，省时省钱
  • 检索什么——自主生成搜索词、选择工具（向量库/图谱/搜索引擎/SQL）
  • 何时停止——评估检索结果置信度，不足则改写 query 再来一轮（Self-RAG / CRAG 思想）
+------------------+ query -->| LLM as Planner | +------------------+ | | | no need vague multi-hop | | | v v v answer rewrite decompose --> retrieve #1 --> evaluate | low conf v retrieve #2 (refined) +------------------------------------+ v synthesize answer with citations
范式代表适用
Naive RAG基础 QA 链简单事实问答，成本敏感
Advanced RAG混合检索 + Rerank + 查询改写生产主力，性价比最优

5.5 评估体系：RAGAS 四指标

RAG 优化不能靠体感，需要量化指标。RAGAS 框架定义了四个维度（用 LLM 评审）：

指标衡量通俗解释理想值

Context Precision 上下文精确率检索到的块中有多少真正相关、排序是否合理检索有没有捞进噪声> 0.8
Context Recall 上下文召回率回答所需的信息有多少被检索到了该捞的是不是都捞到了> 0.85
诊断路由：Context Recall 低 → 检索侧问题（分块/Embedding/召回策略）； Faithfulness 低 → 生成侧问题（Prompt 约束/温度/模型能力）； 两者都高但 Answer Relevance 低 → 查询理解问题（改写/分解）。 先用评估定位瓶颈，再针对性优化，避免盲目堆技术。

5.6 生产化检查清单

类别检查项
数据治理✅ 文档有版本管理与增量更新机制（避免全量重建索引）
✅ 敏感数据脱敏后才入库；权限隔离（不同用户检索范围不同）
✅ 元数据完整（来源/时间/作者），支持时间衰减与失效标注
检索质量✅ 混合检索 + Rerank 两阶段架构
✅ 相似度阈值过滤低置信块；拒答出口真实可用
✅ 建立评估集（100+ 真实问题），每次改动跑 RAGAS 回归
服务工程✅ 检索/生成分段打点延迟；流式输出；超时与重试
✅ 语义缓存（相似问题命中缓存直接返回）；并发限流
✅ 引用来源前端可点击跳转到原文位置
运营闭环✅ 记录拒答/低分 query，定期分析知识缺口并补文档
✅ 监控线上 Faithfulness 抽样评审，模型/索引变更灰度发布
总结：RAG = 把大模型从"闭卷考试"变成"开卷考试"。工程链条上， 分块质量决定检索上限，混合检索+Rerank决定召回精度， Prompt 约束决定生成忠实度，评估体系决定迭代方向。 本手册的 rag_demo/ 用 500 行原生代码覆盖了前三个环节，可直接作为二次开发的起点。
