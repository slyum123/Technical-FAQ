第一章 · CXL 概述

1.1 什么是 CXL

Compute Express Link（CXL）是一种开放标准的互连技术，旨在为数据中心提供 CPU 与设备（加速器、内存扩展器、智能 I/O 设备等）之间高带宽、低延迟 的缓存一致性连接。CXL 构建于 PCI Express（PCIe）物理层和电气接口之上，在此基础之上增加了缓存一致性协议（CXL.cache）和内存语义协议（CXL.mem），使主机处理器和附加设备能够共享统一的内存空间。

核心价值 CXL 使 CPU 和设备可以共享同一内存区域，在硬件层面维护缓存一致性，从而减少数据拷贝、降低软件栈复杂度、提高资源利用率，并最终降低系统总体拥有成本（TCO）。

1.2 为什么需要 CXL

数据中心面临三大内存挑战，CXL 正是为解决这些问题而生：

  • 内存层级延迟鸿沟： 直接附加 DRAM 与 SSD 之间存在约三个数量级的延迟差距。当处理器耗尽本地内存容量时，必须降级到 SSD，性能急剧下降。
  • 内存带宽增长滞后于核心数： 多核处理器的核心数量增长远快于内存通道数量，导致大量核心面临"内存带宽饥荒"。
  • 加速器内存孤岛： GPU、FPGA 等加速器各自拥有专用内存（HBM/GDDR），这些内存资源彼此隔离、利用率低下，造成"搁浅内存"（Stranded Memory）。

1.3 CXL 联盟

CXL 技术最初由 Intel 开发。CXL 联盟于 2019 年 3 月由阿里巴巴、思科、Dell EMC、Meta、Google、HPE、华为、Intel 和微软等九家创始成员成立，并于 2019 年 9 月正式注册成立。截至 2022 年初，AMD、NVIDIA、三星电子和赛灵思加入董事会，ARM、博通、IBM、Marvell、Micron、Rambus、SK hynix 等超过 180 家企业成为贡献成员。

CXL 联盟还整合了多个此前竞争的互连标准：

  • 2021 年 11 月： Gen-Z 联盟将规范和资产转移至 CXL 联盟
  • 2022 年 8 月： OpenCAPI 规范和资产转移至 CXL 联盟

这意味着 CXL 如今整合了 Gen-Z（HPE）、OpenCAPI（IBM）、CCIX（Xilinx）等开放标准的资产，成为数据中心缓存一致性互连领域事实上的唯一开放标准。

第二章 · CXL 协议架构与分层详解

2.1 三大子协议

CXL 的事务层由三个子协议组成，它们在单一物理链路上进行动态多路复用 （根据需求按比例分配带宽）：

子协议 功能 详细说明
CXL.io I/O 语义 功能上等价于 PCIe 协议，负责设备发现、枚举、配置、链路初始化、中断、DMA 和寄存器 I/O 访问。提供非一致性加载/存储接口。所有 CXL 设备必须支持 CXL.io ，确保与 PCIe 生态的即插即用兼容性。
CXL.cache 缓存一致性 定义主机与设备之间的交互，允许设备（如加速器）以极低延迟高效地缓存主机 CPU 内存 中的数据。主机通过 snoop 消息管理设备端缓存的数据一致性。
CXL.mem 内存语义 允许主机 CPU 使用加载/存储命令访问设备附加内存 （Device-Attached Memory）。主机 CPU 为主设备，CXL 设备为从设备。支持易失性（DRAM）和持久性（非易失性）存储器。

2.2 协议栈结构

CXL 采用双栈架构 ，这是其实现低延迟的关键设计决策：

CXL 协议栈架构（双栈设计） CXL.cache / CXL.mem 事务层 专用链路层（低延迟优化） 基于固定大小 Flit 传输 68B（1.x/2.0）或 256B（3.0+） CXL.io 事务层（≈ PCIe TLP/DLLP） PCIe 链路层 TLP/DLLP 封装在 CXL Flit 中 ARB/MUX（仲裁与多路复用） — 加权轮询 CXL 逻辑 PHY（Flit 打包/解包、CRC、流控） PCIe PHY（物理层 & 电气接口）

这种双栈设计的核心优势在于：

  • 低延迟路径： CXL.cache 和 CXL.mem 使用专用的、从底层优化的事务/链路层，使用固定大小的 Flit（流控单元），简化硬件解码逻辑，减少流水线停顿。CXL 1.0 规范定义了这些延迟敏感协议的引脚到引脚响应时间上限，确保平台性能不受设备实现差异影响。
  • PCIe 兼容性： CXL.io 流量使用与标准 PCIe 几乎相同的 TLP/DLLP，封装在 CXL Flit 的负载部分中传输，保持与 PCIe 生态的完全兼容。
  • 动态带宽分配： ARB/MUX 块在 CXL.cache/mem 链路层和 CXL.io 链路层之间进行加权轮询仲裁，权重由主机设置，可按需动态调整。

2.3 Flit 格式

68 字节 Flit（CXL 1.x / 2.0）

CXL 1.x 和 2.0 使用固定宽度的 528 位（66 字节）Flit 进行传输。每个 Flit 由 4 个 16 字节数据时隙 + 2 字节 CRC 组成（4×16 + 2 = 66 字节 = 528 位）。Flit 头部定义了时隙格式，携带将事务正确路由到目标协议的路由信息。实际实现中通常加上 2 字节前导码，总计 68 字节 。

256 字节 Flit（CXL 3.0+）

CXL 3.0 基于 PCIe 6.0 的 PAM-4 信令引入了 256 字节 Flit 格式，结合轻量级前向纠错（FEC）和强 CRC 实现无误传输。更大的 Flit 提供了更多协议头部空间，支持增强一致性、内存共享和 Fabric 功能。CXL 3.0 还引入了延迟优化 Flit 变体 （Latency-Optimized Flit），将 CRC 分解为 128 字节子 Flit 粒度，减少物理层的存储转发开销，额外降低 2-5ns 延迟。

向后兼容性 256B Flit 格式完全向后兼容 8 GT/s、16 GT/s 和 32 GT/s 速率，简化了从 CXL 2.0 到 CXL 3.0 的过渡。

2.4 物理层与速率

CXL 复用 PCIe 物理层，各版本对应的 PCIe 代际和速率如下：

CXL 版本 PCIe 代际 编码方式 单通道速率 x1 带宽 x16 带宽
1.0 / 1.1 / 2.0 PCIe 5.0 NRZ 32 GT/s 3.94 GB/s 63.0 GB/s
3.0 / 3.1 / 3.2 PCIe 6.0 PAM-4 64 GT/s 7.56 GB/s 121.0 GB/s
4.0 PCIe 7.0 PAM-4 128 GT/s 15.13 GB/s 242.0 GB/s

Flex Bus 技术 CXL 使用 Flex Bus 端口技术，允许同一高速端口静态配置为支持 PCIe 或 CXL。当 CXL 设备插入 PCIe x16 插槽时，设备与主机处理器协商，将链路从 PCIe 模式切换到 CXL 模式。这使得 CXL 系统能够利用现有的 PCIe 重定时器（Retimer）基础设施。

2.5 协议分层详解

2.5.1 物理层（Physical Layer）

CXL 的物理层直接复用 PCIe 物理层规范，这是 CXL 能够利用 PCIe 生态基础设施的基础。物理层负责以下核心功能：

电气子层（Electrical Sub-block）

  • 信号编码： CXL 1.x/2.0 使用 NRZ（Non-Return-to-Zero）编码（PCIe 5.0，32 GT/s）；CXL 3.0+/4.0 使用 PAM-4（四电平脉冲幅度调制）编码（PCIe 6.0: 64 GT/s，PCIe 7.0: 128 GT/s）。PAM-4 每次传输 2 位数据，在相同波特率下实现带宽翻倍。
  • 通道宽度： 支持 x1, x2, x4, x8, x16 通道配置。CXL 4.0 引入原生 x2 宽度以支持更大扇出。BNF（Bifurcation）可将 x16 分叉为多个独立通道。
  • 链路训练与状态机（LTSSM）： 设备上电后首先进行标准的 PCIe 链路训练，协商速率、宽度和链路状态。训练成功后通过 CXL 协议协商（ALT Protocol Negotiation）进入 CXL 模式。
  • 扩展能力： CXL 4.0 支持最多 4 个重定时器，信道损耗预算保持 -36dB @ 128 GT/s，显著增加传输距离（支持机架级部署）。

逻辑子层（Logical Sub-block）

  • Flex Bus 逻辑： 同一高速 SerDes 端口可静态配置为 PCIe 模式或 CXL 模式。CXL 模式下，逻辑 PHY 完成 Flit 的成帧/去帧、字节条带化、加扰、极性反转和通道反转检测。
  • Flit 打包/解包： CXL.cache/mem 和 CXL.io 的链路层包被 ARB/MUX 汇聚后，由逻辑 PHY 打包为固定宽度的 Flit 发送。接收端反向操作。
  • NULL Flit 插入： 当无有效数据传输时，物理层自动插入 NULL Flit 以维持链路活动和时钟恢复。
  • ALMP (Arb/Mux Link Management Packet)： 物理层可区分 CXL.io、CXL.cache-mem、ALMP 和 NULL Flits 四种流量类型。

2.5.2 链路层（Link Layer / Data Link Layer）

链路层负责在物理层之上提供可靠的数据传输 。CXL 采用双链路层设计，分别服务于 CXL.cache/mem 和 CXL.io。

CXL.cache/mem 链路层（低延迟优化链路层）

这是 CXL 实现低延迟的关键。它使用专用的、从底层优化的链路层协议，处理 CXL.cache 和 CXL.mem 的 Flit：

  • Flit 格式与打包规则： 68B Flit 含 4 个 16B 数据时隙 + 2B CRC，256B Flit 含更大负载和更强 FEC。打包遵循六大规则：Rollover（超 Flit 数据延续到下一 Flit）、Tightly Packed（有效消息紧挨放置）、Empty Slots 可与其它类型混合、MDH BE=0 时用于全 Cacheline、Control flits 不与 All-Data 交错、每个方向的消息数受限（如 D2H Rsp ≤2，S2M NDR ≤2，M2S Req ≤2）。
  • 链路信用机制（Credit）： 接收方向发送方通告可用缓冲区空间，防止溢出。每个通道（请求/响应/数据）独立维护信用计数。
  • 链路层重传（LLR — Link Layer Retry）： 发送方将每个可重试 Flit 缓存到 LLRB（Link Layer Retry Buffer）。接收方使用 CRC-16 校验每个 Flit，每 8 个 Flit 通过 Ak（Acknowledge）位批量确认无错接收。Flit 通过序列号（ESeq）而非每 Flit 携带序列号来识别，减少协议开销。
  • 链路层控制 Flit 类型：
    • LLCRD — 携带 ACK 和 Credit 返回信息（可重试）
    • RETRY — Idle/Req/Ack/Frame，控制重传过程
    • IDE — Idle/Start/TMAC/Stop/MAC，完整性数据加密（CXL 2.0+）
    • INIT.Param — 链路初始化参数交换（LLR Wrap Value、版本号）
  • 链路层初始化流程： 物理层链路 Up → 发送 Control-RETRY flits → 收到 CRC 干净的 flit → 发送 INIT.Param flit → 使用 LLCRD 格式交换 Credits → 收到第二个 INIT.Param → 初始化完成。
  • CRC 错误处理： 检测到 CRC 错误时立即标记病毒位（Viral）或毒化位（Poison），触发重传或错误传播。

CXL.io 链路层（PCIe 兼容链路层）

功能上等同于 PCIe 数据链路层（Data Link Layer），处理 CXL.io 的 TLP/DLLP：

  • TLP 封装： 将 PCIe TLP（事务层包）封装在 CXL Flit 的负载时隙中传输。接收端解封装后按标准 PCIe TLP 处理。
  • ACK/NAK 协议： 对每条 TLP 使用序列号确认机制，与标准 PCIe 数据链路层的 ACK/NAK 行为一致。
  • DLLP 支持： 标准 PCIe DLLP（Data Link Layer Packet）的生成与处理，包括流控更新（InitFC/UpdateFC）、电源管理等。
  • 与 CXL.cache/mem 链路层的区别： CXL.io 链路层不需要专用的 LLRB，因为它复用了 PCIe 的重传机制（Replay Buffer + ACK/NAK）。

2.5.3 仲裁/多路复用层（ARB/MUX）

ARB/MUX 是 CXL 协议栈中独特的中间层 ，位于链路层和物理层之间，负责将两个独立的链路层（CXL.cache/mem 和 CXL.io）的流量合并到单一物理链路上 。

  • 加权轮询仲裁： ARB/MUX 使用可编程的加权轮询算法在两个链路层之间调度 Flit 传输。权重由主机通过配置寄存器动态设置，实现按需分配带宽。
  • 优先级机制： CXL.cache 和 CXL.mem 流量通常被赋予更高优先级，以维持低延迟语义。CXL.io 流量（控制、枚举等管理操作）在低优先级通道传输。
  • ALMP（Arb/Mux Link Management Packet）： ARB/MUX 可以发送专用的链路管理包，用于链路状态同步、功耗管理和错误报告。ALMP 不携带用户数据，仅用于控制目的。
  • 动态带宽分配： 系统管理员或 Fabric Manager 可以根据工作负载特征调整权重。例如，在大量 I/O 流量的场景下可以给 CXL.io 分配更多权重；在纯内存访问场景下给 CXL.mem 分配接近 100% 的带宽。
  • 反压处理： 当某一链路层无法跟上传输速率时，ARB/MUX 将相应通道的反压信号传递给发送方，防止数据丢失。

2.5.4 事务层（Transaction Layer）

事务层是 CXL 协议栈的最顶层 ，定义了三种子协议的语义、事务类型、数据包格式和排序规则。

CXL.io 事务层

完全基于 PCIe 事务层规范，负责所有非缓存/非内存语义的通信：

  • 事务类型： 内存读写（Memory Read/Write）、I/O 读写、配置读写（Configuration Read/Write）、消息事务（Message）— 包括中断（MSI/MSI-X）、错误报告、电源管理。
  • CXL 特有增强：
    • VDM（Vendor Defined Messages）用于 CXL 复位和电源管理
    • 修改 PCIe ATS（Address Translation Services）请求/完成格式以支持加速器
    • Deferred Write 指令定义
    • 记忆体类型指示（Memory Type Indication on ATS）
  • 排序规则： 继承 PCIe 的生产者-消费者排序模型（PCIe Transaction Ordering），保证 I/O 操作的正确顺序。
  • 信用管理： 继承 PCIe 的流控信用机制（Posted/Non-Posted/Completion），防止事务层缓冲区溢出。

CXL.cache 事务层

定义设备缓存主机内存的协议，主要面向 Type 1 和 Type 2 设备：

  • 三通道架构： 方向分为 D2H（Device to Host）和 H2D（Host to Device），每个方向有三个独立通道：
    • 请求通道（Request — D2H_REQ / H2D_REQ）： 缓存行读取/写入请求、Snoop 请求
    • 响应通道（Response — D2H_RSP / H2D_RSP）： 请求的完成响应，携带状态（命中/未命中）
    • 数据通道（Data — D2H_DATA / H2D_DATA）： 实际缓存行数据传输
  • 缓存状态： 遵循 MESI/MESIF 协议变体，支持 Modified（已修改）、Exclusive（独占）、Shared（共享）、Invalid（无效）等缓存状态。
  • Snoop 机制： 主机 Home Agent 通过 H2D_REQ 通道向设备发送 Snoop 请求（SnpInv、SnpData 等），确保设备缓存与主机缓存一致。
  • 信用管理： 每个通道独立维护信用计数。设备必须在初始化时向主机通告可接收的事务数上限。

CXL.mem 事务层

定义主机访问设备附加内存的协议，主要面向 Type 2 和 Type 3 设备：

  • 消息类别： 方向分为 M2S（Master to Subordinate — 主机到设备）和 S2M（Subordinate to Master — 设备到主机）：
    • M2S 请求（MemRd, MemWr, MemSpecRd, MemSpecWr）： 内存读（Read）、内存写（Write）、特殊读/写
    • S2M 响应（MemData, Cmp）： 读数据返回和写完成确认
    • S2M 无数据响应（NDR — No Data Response）： 写操作完成确认、错误报告
    • S2M 后向失效（Back-Invalidation，CXL 3.0+）： 设备通知主机使缓存行无效
  • 地址类型： 支持 HDM（Host-Managed Device Memory — 主机按字节寻址设备内存）和 HDM-DB（Host-Managed Device Memory with Device Bias — 设备偏置内存，CXL 3.1+）。64 位物理地址空间映射。
  • 内存访问粒度： 缓存行粒度（64 字节），与 CPU 缓存体系一致，确保缓存一致性协议的精确工作。
  • 持久性内存支持（CXL 2.0+）： 通过全局持久刷新（GPF — Global Persistent Flush）确保数据非易失性。CXL.mem 持久性写入语义确保数据在设备持久域中安全落地。

2.5.5 网络层 / Fabric 路由层（CXL 3.0+）

从 CXL 3.0 开始，由于引入了多级交换和 Fabric 概念，CXL 增加了等效于网络层的路由功能 ：

  • HBR（Hierarchy-Based Routing — 层次化路由）： CXL 3.0 引入的传统树形路由。交换机基于目标设备在 CXL 层次结构中的位置转发包。类似于 PCIe 总线/设备/功能（BDF）层级路由，适用于主机-设备的主从架构。
  • PBR（Port-Based Routing — 基于端口的路由，CXL 3.1+）：
    • 交换机之间支持点对点连接，不再局限于树形拓扑
    • 支持胖树（Fat Tree）、CLOS 等非树形拓扑
    • 支持链路聚合（Link Aggregation），多条链路绑定为逻辑通道
    • 支持 P2P DMA 直接跨交换机传输，无需主机 CPU 介入
    • HBR 和 PBR 交换机可混合使用，构建混合拓扑
  • Fabric Manager（FM）路由表管理： FM 负责配置和维护所有交换机的路由表。Fabric Manager API（基于 MCTP 协议）实现路由的动态更新。
  • 地址空间管理： Fabric 地址空间（Fabric Address Space）与主机物理地址空间通过 HDM 解码器（HDM Decoder）进行映射，实现全局统一地址视图。

2.6 Flit 格式演进与传输层

2.6.1 68B Flit（CXL 1.x / 2.0）

528 位（66 字节）固定宽度，这是 CXL 的原始传输格式：

  • 4 个 16B 数据时隙： 每个时隙可承载 CXL.cache/mem 协议头、协议数据或 CXL.io TLP 片段
  • 2B CRC（16 位 CRC-16）： 对整个 Flit 进行错误检测
  • 实际封装： 通常加上 2B 前导码（Preamble），最终物理传输为 68B
  • 时隙格式编码： Flit 头部（Header）使用 CTL_FMT 字段（Control Format）编码每个时隙的内容类型（协议头/数据/空），CXL 1.1 使用 000b
  • 协议头开销： CXL.cache 协议头约 4B-16B，CXL.mem 协议头约 2B-8B

2.6.2 256B Flit（CXL 3.0+）

基于 PCIe 6.0 Flit 模式，CXL 3.0 引入的 256B 超大 Flit：

  • 内部结构： 256B Flit = 236B TLP/协议负载 + 6B DLP（Data Link Payload）+ 8B FEC CRC + 6B Flit 控制信息
  • 协议头部空间扩大： 更大的负载空间支持 CXL 3.0 新增的增强一致性、内存共享、Fabric 路由等协议头部扩展
  • 轻量级 FEC（前向纠错）： 结合 PAM-4 信令的 BER 特性，在 256B Flit 中嵌入 FEC，实现误码纠正而非仅检测，减少重传概率
  • Latency-Optimized Flit（延迟优化 Flit）： 将 CRC 检查分解为 128B 子 Flit 粒度，减少物理层的"存储转发"（Store-and-Forward）开销，额外降低 2-5ns 延迟
  • 向后兼容： 256B Flit 格式支持所有速率的物理层（8 GT/s 到 128 GT/s），CXL 3.x/4.0 设备可降级使用 68B Flit 以兼容旧版

2.6.3 传输层视角

CXL 没有独立定义的 OSI 式"传输层"（如 TCP/UDP），但其端到端可靠传输 功能由链路层和事务层的信用/重传机制联合实现：

  • 端到端信用流控： CXL.cache 和 CXL.mem 协议在事务层实现端到端信用管理，确保接收方有足够缓冲来处理发送方的事务请求
  • 可靠交付保证： 链路层 LLR 确保点到点（Hop-by-Hop）的可靠传输，事务层排序规则和确认机制确保端到端语义正确性
  • Flit 路由： 在多级交换拓扑中，Flit 通过 HBR/PBR 交换机逐跳转发，等效于传输层的分段路由。
  • 端到端安全（CXL 2.0+）： CXL IDE 在链路层提供端到端加密和完整性保护，确保数据在多跳 Fabric 中传输的机密性和完整性

第三章 · CXL 设备类型与一致性模型

3.1 三种设备类型

CXL 定义了三种设备类型，由其支持的子协议组合决定：

类型 支持协议 典型设备 特征
Type 1 CXL.io + CXL.cache 智能网卡（SmartNIC）、原子操作加速器 无本地内存或不对主机暴露本地内存的加速器。通过 CXL.cache 协议利用主机 CPU 内存作为其缓存。例如 SmartNIC 可直接将网络数据包处理结果写入主机内存的接收队列。
Type 2 CXL.io + CXL.cache + CXL.mem GPU、FPGA、AI ASIC 拥有自身高性能内存（HBM/GDDR）的加速器。CPU 可通过 CXL.mem 推送数据到加速器内存，加速器可通过 CXL.cache 访问系统内存。设备与主机双向缓存一致。
Type 3 CXL.io + CXL.mem 内存扩展卡、持久性内存模块 目前最广泛部署的类型。主机 CPU 通过 CXL.mem 将设备附加内存作为主内存扩展使用（HDM — Host-Managed Device Memory）。OS 将其视为"无 CPU 的 NUMA 节点"。不支持 CXL.cache，设备不缓存主机内存。

3.2 一致性模型

3.2.1 非对称一致性架构

CXL 的一个重要设计特征是其一致性协议是非对称的 ：Home 缓存代理（Home Agent）仅存在于主机处理器中。主机控制内存的缓存，负责处理连接的 CXL 设备请求的整个系统一致性问题。

这与 CPU 到 CPU 的对称一致性协议（如 Intel QPI/UPI、AMD Infinity Fabric）截然不同——对称协议中所有互连设备都是对等的，必须各自处理一致性的复杂性。CXL 的非对称方法使得不同架构的 CPU 和加速器可以轻松纳入 CXL 生态系统，降低了设备端实现门槛。

3.2.2 偏置模式（Bias Mode）— CXL 1.x / 2.0

对于 Type 2 设备，CXL 1.x/2.0 定义了两种内存一致性"偏置"模式，控制主机与设备附加内存之间的一致性数据处理方式。偏置模式可以 4KB 页面粒度进行更改，通过 Type 2 设备中的偏置表跟踪。

偏置模式 说明
主机偏置
(Host Bias) 主机 CPU 的缓存控制器管理所有对设备内存的访问。设备内存对于设备而言就像主机内存，如需访问则通过请求主机处理。适用于工作提交阶段（主机向设备内存写入数据）和工作完成后导出数据。默认模式。
设备偏置
(Device Bias) 设备直接访问本地内存，CPU 不进行缓存。确保设备无需与主机一致性引擎通信即可访问本地内存，为设备提供最优延迟。加速器执行工作时的主要操作模式。主机仍可访问设备内存但性能非最优。

3.2.3 增强一致性（Enhanced Coherency）— CXL 3.0+

CXL 3.0 引入了增强一致性模型 ，替代了之前的偏置模式。核心改进包括：

  • 硬件反向失效（Back-Invalidation）： Type 2 设备可以直接反向失效主机缓存中的缓存行，实现对称一致性管理。
  • Snoop Filter 支持： Type 2 设备可为 HDM 地址范围实现 Snoop Filter，以更高效地映射和管理大量内存。
  • 内存共享（Memory Sharing）： 多台主机可同时一致性访问同一内存区域，突破了 CXL 2.0 仅能通过软件实现内存共享的限制。

7.3 Fabric Manager 架构与工作流程

Fabric Manager（FM）是 CXL 内存池化的核心管理软件 ，通常运行在 BMC 或专用管理节点上。

7.3.1 FM 三大核心职责

  • 设备发现与枚举（Discovery）： FM 通过 MCTP（Management Component Transport Protocol）协议遍历整个 CXL Fabric，发现所有交换机、主机、内存设备，构建完整拓扑图。执行 Virtual-to-Physical Binding（虚拟到物理绑定），将物理端口抽象为逻辑设备（LD）供上层使用。
  • 资源池化与分配（Allocation）： FM 根据策略（按需分配、负载均衡、优先级）将内存池中的物理内存块动态分配给申请的主机。配置 HDM Decoder 的地址映射关系，建立从设备物理地址（DPA）到主机物理地址（HPA）的映射。
  • 事件监控与管理（Monitoring）： FM 监听来自设备的事件（错误、热插拔、容量变化），并采取响应措施（隔离故障设备、重新分配内存、通知 Orchestrator）。

7.3.2 FM 管理命令接口

  • FM API over MCTP： CXL 规范定义了基于 MCTP 的标准 Fabric Manager API 命令集，包括设备查询（Identify Device）、绑定/解绑（Bind/Unbind）、HDM Decoder 编程（Set HDM Decoder）、事件通知（Event Notification）等。
  • CCI（Component Command Interface）over MCTP： 针对 Type 3 设备的标准化管理命令接口，通过 MCTP 传输。支持设备发现（Identify Memory Device）、容量查询（Get Partition Info）、事件通知（Event Record）等。
  • 同步/异步事件通知： FM 支持同步请求-响应模式和异步事件推送（如设备热移除通知、错误事件）。CXL 2.0 勘误表（ECN）对异步 MCTP 事件通知进行了关键修正。

7.4 全局地址映射与绑定机制

CXL 内存池的全局统一编址是实现"池化"的核心技术，涉及三层地址空间的映射 ：

7.4.1 三层地址空间

地址空间 缩写 说明
主机物理地址 HPA Host Physical Address — 主机 CPU 视角的物理地址空间。CFMWS 为 CXL 保留固定窗口（如 HPA 0x8800000000 - 0x8FFFFFFFFF）。
设备物理地址 DPA Device Physical Address — CXL 设备内存控制器的内部地址空间。Type 3 设备将 DRAM 物理空间暴露为 DPA 范围。可能被划分为多个分区（Partition），经由不同 HDM Decoder 映射到不同 HPA 窗口。

7.4.2 HDM Decoder 编程（地址映射核心）

HDM (Host-Managed Device Memory) Decoder 是 CXL 内存映射的核心硬件单元 ，位于 CXL 主机桥和 Type 3 设备中：

  • 主机侧解码器： CXL 主机桥中的 HDM Decoder 将 HPA 窗中的访存请求路由到正确的 CXL 根端口（Root Port）。每个 Decoder 对应一个 CFMWS 定义的内存窗口，指定交错方式（Interleave Granularity、Interleave Ways）、目标列表（Target List）和地址范围。
  • 设备侧解码器： Type 3 设备中的 HDM Decoder 将来自主机的 CXL.mem 请求解码到设备内部 DPA 空间。每个 Decoder 映射一个 DPA 范围到一个 HPA 窗口，支持锁定（Lock）配置防止运行时意外修改。
  • 解码器编程流程（内核侧）：
    # 1. 枚举 CXL 设备
cxl list -M    # 列出所有 memdev (mem0, mem1, ...)
cxl list -D -d decoder0.0   # 查看 decoder 状态

# 2. 创建区域 (Region) — 多个 memdev 可交错
cxl create-region -m -d decoder0.0 -w 2 mem0 mem1

# 3. 启用区域
cxl enable-region region0

# 4. 绑定为系统内存
daxctl reconfigure-device --mode=system-ram dax0.0

7.4.3 虚拟到物理绑定（Virtual-to-Physical Binding）

FM 通过 Virtual-to-Physical Binding 机制简化上层管理：

  • 逻辑设备（LD）抽象： FM 将复杂的物理端口映射（Port X → Switch Y → Device Z）抽象为简单的逻辑标识符（LD-ID），操作系统只需要与逻辑设备交互。
  • 多路径支持： 在多级交换拓扑中，一个 LD 可能通过多条物理路径可达（链路聚合/冗余）。FM 维护路径映射，实现故障切换。
  • 动态重绑定： CXL 3.0 的 DCD（Dynamic Capacity Device）允许在不重启主机的情况下动态改变 LD 到主机的绑定关系，实现弹性内存分配。

7.5.2 多主机共享内存交互（CXL 3.0+ FAM）

在 CXL 3.0+ 的多主机共享内存场景中，关键区别在于缓存一致性维护 ：

步骤 操作 说明
1 Host A 读取 FAM 地址 (Shared) Host A 发出 CXL.mem MemRd 请求 → 交换机路由到 Type 3 设备 → 返回数据。Type 3 设备记录 Host A 持有一份 Shared 副本。
2 Host B 写入 FAM 地址 (Modified) Host B 发出 CXL.mem MemWr 请求 → Type 3 设备检测到 Host A 持有 Shared 副本 → Type 3 设备通过 Back-Invalidation 机制向 Host A 发出 Snoop-Invalidate → Host A 失效其缓存行 → Type 3 确认后允许 Host B 写入。
3 Host A 再次读取 FAM 地址 Host A 发出 MemRd → 由于其缓存行已失效 → Type 3 返回最新数据（Host B 写入的值）→ 缓存一致性得以维护。

关键设计差异 — CXL 2.0 池化 vs CXL 3.0 共享 CXL 2.0 的 MLD 池化将设备容量划分为独立分区，分配给不同主机，不需要硬件缓存一致性维护 （各分区互不干扰）。CXL 3.0 的 FAM 共享允许多主机访问同一物理内存区域，必须依赖硬件 Back-Invalidation 机制 来维护缓存一致性。这是两者最根本的架构差异。

7.6 内存分级（Memory Tiering）与动态容量管理

7.6.1 Linux 内存分级框架

Linux 内核将 CXL 内存视为比本地 DRAM 慢的第二级内存 ，通过内存分级框架实现透明的冷热数据迁移：

  • 自动降级（Demotion）： 当本地 DRAM 面临内存压力（kswapd 触发回收），内核将冷页（访问频率低的页面）从 Tier 0（本地 DRAM）迁移到 Tier 1（CXL 内存）。通过 pgdemote_kswapd 和 pgdemote_khugepaged 计数器监控。
  • 自动提升（Promotion）： NUMA 平衡器（NUMA Balancing）定期扫描内存页面访问模式，将热页（频繁访问的页面）从 CXL 内存提升回本地 DRAM。通过 pgpromote_success 计数器监控。
  • DAMON 辅助： DAMON（Data Access Monitor）和 DAMOS（DAMON-based Operation Schemes）可在内存压力发生前主动将冷页降级到 CXL。
  • 监控命令：
    # 查看内存分级信息
cat /sys/devices/virtual/memory_tiering/memory_tier*/nodelist

# 实时监控分级活动
watch -n 1 'grep -E "pgdemote|pgpromote" /proc/vmstat'

# 手动设置内存策略
numactl --membind=2 ./capacity_job   # 强制分配到 CXL 节点
numactl --preferred=0 ./mixed_job    # 优先 DRAM，溢出到 CXL

7.6.2 DCD 动态容量设备（CXL 3.0+）

DCD（Dynamic Capacity Device）是 CXL 3.0 引入的一项革命性能力，允许主机在运行时动态增减内存容量，无需重启 ：

  • Extent 概念： 内存以 Extent（容量块）为单位进行分配和释放。每个 Extent 有独立的设备地址范围和长度。
  • 交互流程中的五个角色： Orchestrator（编排器）→ Fabric Manager（结构管理器）→ MLD 设备（逻辑设备）→ Host Kernel（内核 DCD 驱动）→ Host Userspace（用户空间工具）。
  • 添加流程： Orchestrator → FM → MLD 发送 Add-DC-Request（分配 Extent X）→ MLD 向 Host 发送 Extent 事件 → Host 内核接收并创建新 DAX 区域/内存块 → 上线为可用内存。
  • 释放流程： Orchestrator → FM → MLD 发送 Release-DC-Request（释放 Extent X）→ Host 内核将对应内存块下线 → 移除 DAX 区域 → 归还 Extent 到共享池。
  • 实时演示验证： 2025 年底，Montage Technology 使用其 CXL 3.2 MXC Gen3 控制器完成了双主机 DCD 功能演示——8GB Extent 在两台主机间动态分配和释放，整个过程无需任何系统重启。

DCD 的重要意义 DCD 将 CXL 内存池从"静态配置"升级为"弹性资源"。AI 训练集群可以在不同训练阶段按需分配不同容量的内存（如数据加载阶段需要大内存、训练阶段需要少内存），内存利用率接近 100%，相比传统静态分配可节省 30-50% 的内存成本。

7.8.2 HPA→DPA 地址翻译数学公式

Endpoint 端 HPA → DPA 翻译算法 假设一个 interleave set 有 IW 个设备、交织粒度为 IG 字节、本设备在交织集中的位置为 ISP（Interleave Set Position）：

Step 1: 检查 HPA 是否在本 Decoder 的 [Base, Base+Size) 范围内
Step 2: 计算交织偏移:
  HPA_OFFSET = HPA - Base                          // 窗口内偏移
  Chunk_Index = HPA_OFFSET >> lg(IG)               // 所属 IG 块编号
  Device_Chunk = Chunk_Index / IW                   // 本设备的 IG 块序号
  Chunk_Offset = HPA_OFFSET & (IG - 1)             // IG 块内偏移
  HPA_DEVICE = (Device_Chunk << lg(IG)) | Chunk_Offset  // 去交织后的地址
Step 3: 转换为设备内部 DPA:
  DPA = HPA_DEVICE + Decoder_DPA_Base

示例： IW=4, IG=256B, ISP=2, Base=0x880_0000_0000
HPA = 0x880_0000_0200 (偏移 0x200 = 512 字节)
→ Chunk_Index = 512 >> 8 = 2
→ Device_Chunk = 2 / 4 = 0
→ Chunk_Offset = 512 & 255 = 0
→ HPA_DEVICE = (0 × 256) + 0 = 0x0
→ 如果 IW×IG = 1024B，等效为 HPA_DEVICE = (512 / 1024) × 256 + (512 % 256) = 0
→ 即：HPA=0x880_0000_0200 在 ISP=2 设备上命中 DPA=0x0

7.8.3 多级交织（Cross-Link-First）模型

CXL 支持跨多级 进行交织，在 Linux 内核 CXL 驱动中称为 Cross-Link-First Interleave 。以 "4 Host Bridge × 4 Endpoint = 16 路交织" 为例：

配置:
  Root Decoder:  IW=4, IG=256B,  Targets=[HB0, HB1, HB2, HB3]
  HB Decoder:    IW=4, IG=1024B, Targets=[EP0, EP1, EP2, EP3]
  EP Decoder:    IW=16, IG=256B (每个 EP 感知全局 16 路交织)

地址路由过程 (以 HPA 为例):
  Root 层:  target_HB = (HPA >> 8) % 4         → 选 Host Bridge
  HB 层:    target_EP = (HPA >> 10) % 4        → 选 Endpoint
  EP 层:    根据 IW=16, IG=256B 完成最终 HPA→DPA 翻译

交织粒度倍增规则：每向下游一级，IG 乘以该级的 IW。
  即：下游 IG = 上游 IG × 上游 IW
  本例：IG(HB) = 256B × 4 = 1024B ✓

7.8.4 CFMWS — BIOS 定义的全局地址窗口

CFMWS (CXL Fixed Memory Window Structure) 是 ACPI CEDT 表中的核心条目，由 BIOS/UEFI 在启动时填充。它在 Host PA 空间中为 CXL 内存"预留"了地址窗口 ，OS 根据这些条目创建 CXL Decoder 和 Region。

CFMWS 条目结构
struct CFMWS_Entry {
    uint8_t  subtable_type;       // 0x01 = CFMWS
    uint16_t length;              // 条目长度
    uint64_t window_base_hpa;     // Host PA 基地址 (必须 256MB 对齐)
    uint64_t window_size;         // 窗口大小 (必须为 256MB 的整数倍)
    uint8_t  interleave_members;  // 交织成员数 (2^n, 0 = 1 路, 即无交织)
    uint8_t  interleave_arith;    // 交织算法 (0 = 模运算)
    uint16_t interleave_granularity;
    uint16_t restrictions;        // Bit[1]=Type3 Volatile, Bit[2]=Type3 PMem, 等
    uint16_t qtg_id;              // QoS Telemetry Group ID
    // Target Host Bridge _UID 列表
    uint16_t target_host_bridge_uids[];  // 最多 8 个 Host Bridge
};
CFMWS 多窗口分配示例

一台配备 4 个 CXL Host Bridge 的服务器，BIOS 可能创建如下 CFMWS：

CFMWS 0 (非交织 — 给 Volatile RAM，1 个设备直通):
  Base_HPA: 0x880_0000_0000, Size: 256 GB
  IW: 1 (无交织), Restrictions: Volatile (Bit[1])
  Targets: [HB0]

CFMWS 1 (非交织 — 给 Persistent Memory，1 个设备直通):
  Base_HPA: 0x8C0_0000_0000, Size: 256 GB
  IW: 1, Restrictions: Persistent (Bit[2])
  Targets: [HB0]

CFMWS 2 (4 路交织 — 4 个 Host Bridge 交织):
  Base_HPA: 0x900_0000_0000, Size: 1 TB
  IW: 4, IG: 256B, Restrictions: Type3
  Targets: [HB0, HB1, HB2, HB3]

这三个 CFMWS 使 OS 有灵活选择：
  · 可以将同一个 256GB 设备作为 Volatile RAM 或 PMem 使用（CFMWS 0 或 1）
  · 可以将 4 个 256GB 设备交织为 1TB 统一地址空间（CFMWS 2）
  · OS 选择使用哪个 CFMWS 通过 cxl create-region 工具实现
HDM Decoder 编程规则

编程约束 (Commit Flow)

  1. 地址递增： Decoder[m+1].Base >= Decoder[m].Base + Decoder[m].Size。不允许地址重叠。
  2. 无回绕： Decoder[m].Base + Decoder[m].Size 不可超过 64 位地址空间。
  3. 3/6/12 路规则 (CXL 3.0+)： 如果 IW >= 8 且为 3 的倍数，Size 必须是 3 的倍数。
  4. 目标唯一性： Decoder[m] 中 IW 个 Target Port ID 必须互不相同。
  5. 前序提交： Commit Decoder[m] 之前，Decoder[m-1] 必须已 Commit 且通过检查。
  6. Endpoint 顺序提交： DPA 空间必须从地址 0 开始按序提交（Dec[0] at DPA=0, Dec[1] at DPA=Dec[0].Size, ...）。

FM 完整绑定流程 — 10 步序列

1

FM 发现拓扑
通过 MCTP 带外通道向所有交换机和设备发送 Identify 命令。收集每个组件的端口连接关系、设备类型、内存容量。

2

FM 创建 MLD/分区
对 MLD 设备发送 Set LD Allocations 命令，将物理内存划分为 N 个 LD。例如：512GB 设备 → 4 个 128GB LD (LD-ID 0~3)。

3

FM 建立 VCS 实例
为每台主机创建独立的 VCS 实例。每个 VCS 包含若干 VPPB 节点，形成虚拟树结构。

4

FM 绑定 LD 到 VPPB (虚拟到物理映射)

5

FM 配置 Switch HDM Decoder（路由表）
为交换机 USP 和 DSP 的 HDM Decoder 写入路由表。例如：{HPA_Range=0x900_0000_0000-0x900_3FFF_FFFF, Target_Port=DSP2, LD-ID=5}。

6

FM 配置 Device DPA Decoder
通过 CCI 命令配置设备端的 DPA Decoder：{DPA_Base, DPA_Size, HPA_Window_Info, Interleave_Params}。

7

FM 解锁绑定端口
发送 Unlock VPPB 命令，使主机可见绑定后的设备。此时主机在 PCIe 枚举时会"发现"新的 CXL 设备。

8

主机 PCIe 枚举 + CXL 探测
主机 OS 启动或热插拔检测到新设备。PCIe 子系统枚举，CXL 驱动接管，解析 CEDT/CFMWS，创建 Decoder 和 Region。

9

OS 创建内存 Region + 上线
通过 cxl-cli 创建 Region、启用 kmem/daxdev 驱动，内存上线为 NUMA 节点。

10

FM 监控与事件处理
FM 持续监听设备热插拔、错误、容量变更事件。当 Orchestrator 发出重新分配请求时，FM 执行解除绑定→重新绑定流程。

7.8.6 DCD 动态容量分配 — 无停机弹性伸缩

DCD (Dynamic Capacity Device) 是 CXL 3.1 引入的革命性特性，允许内存容量在主机之间秒级 动态迁移，无需重启或重置。

概念 说明
Extent DCD 分配的最小单元。典型大小为 8 GB。每个设备可支持数百个 Extent。
Region 若干连续 Extent 的集合。Host 看到的是一个连续的 DAX Region。
Tag 每个 Extent 带一个 Tag（0-99），Host 通过 Tag 识别和释放特定 Extent。
待处理上限 最多 100 个待处理 Extent（防止无限刷新）。超过上限时 FM 必须等待确认。 
DCD 容量迁移典型时序 (以 Montage Technology 公开演示为参考):

Step 1: Host 1 初始配置 = 64 GB DDR (基线), Host 0 = 32 GB DDR

Step 2: FM → Device 1: Add-DC-Request {Region=2, Extent_Count=1}
  Device 1 → FM: Add-DC-Response {Accepted}
  FM → Host 1: 通知添加 8 GB DC Extent
  Host 1 OS: 热添加 8 GB → 总内存 = 72 GB

Step 3: FM → Device 1: Add-DC-Request {Region=2, Extent_Count=1}
  → Host 1: 80 GB

Step 4: FM → Host 1: 请求释放 Extent Tag=1
  Host 1 OS: 页面迁移 (migrate) Extent 上的数据 → Extent 置空
  FM → Device 1: Release-DC-Request {Extent_Tag=1}
  Device 1 → FM: Release-DC-Response

Step 5: FM 将释放的 Extent 分配给 Host 0
  FM → Device 1: Add-DC-Request {Region=0, Extent_Count=1}
  → Host 0: 40 GB

关键机制:
  · Extent 每次分配/释放前后，Host 必须确保数据一致性
  · Host 通过 CXL.io mailbox 发送 Add/Release DC 命令
  · 设备侧 DPA Decoder 动态更新：添加 Extent = 扩展 DPA 范围，释放 = 收缩
  · 原子性保证：同一 Tag Group 内的 Extent 分配/释放是事务性的

第六章 · CXL 核心应用场景

6.1 内存扩展（Memory Expansion）

适用版本： CXL 1.1+（Type 3 设备）

最基础也是最广泛部署的应用。通过 CXL Type 3 内存扩展器为服务器增加 TB 级内存容量和额外带宽。CXL 内存以字节寻址、缓存一致性的方式被 CPU 通过标准加载/存储指令访问，OS 将其视为无 CPU 的 NUMA 节点。

  • 延迟特性：相比本地 DRAM 增加约 70-250ns，但仍比 NVMe SSD 快 20-50 倍
  • 典型形态：E3.S 模块或 PCIe AIC 板卡
  • 应用：内存数据库、AI 推理（KV Cache）、实时分析

6.2 内存池化（Memory Pooling）

适用版本： CXL 2.0+（需 CXL 交换机 + MLD）

通过 CXL 交换机将多个内存设备组成池，动态分配给不同主机。当某台服务器内存不足时，可从池中获取；不需要时归还。大幅提高内存利用率，减少搁浅内存，降低 TCO。

  • 核心组件：CXL 交换机、Fabric Manager、MLD 设备
  • 每个内存切片在同一时间仅分配给一台主机
  • 应用：云基础设施弹性内存、虚拟化内存超分

6.3 内存共享（Memory Sharing）

适用版本： CXL 3.0+（需硬件增强一致性）

多台主机可同时一致性访问同一内存区域，在硬件层面实现真正的多机共享内存。突破 CXL 2.0 池化模式下"一切片一主机"的限制。CXL 3.1 进一步通过 GIM 支持主机间本地内存直接共享。

  • 关键技术：硬件反向失效、FAM、GIM
  • 应用：MPI 并行计算、图数据库加速、分布式共享内存

6.4 可组合基础设施（Composable Infrastructure）

适用版本： CXL 2.0+（完整 Fabric 需 CXL 3.0+）

将 CPU、内存、GPU、FPGA 等资源解耦为独立池，按工作负载需求动态组合虚拟服务器。使用完毕后解构，资源归还池中供复用。CXL 是实现真正软件定义、完全可组合数据中心的关键使能技术。

6.5 AI 工作负载加速

CXL 在 AI 领域的关键应用：

  • KV Cache 卸载： 将 AI 推理中的 KV Cache 从 GPU 显存卸载到 CXL 内存池，突破"内存墙"，性能较 SSD 提升 5 倍以上
  • Prefill/Decode 分离： Prefill GPU 和 Decode GPU 通过 CXL 内存池同步交换 KV Cache
  • GPU 内存扩展： 通过 CXL 为 GPU 扩展外部内存，形成统一虚拟内存空间
  • 大规模推理： 2025 年已可实现 100 TiB 级别的 CXL 内存池部署

场景 Host CPU 从直连的 CXL Type 3 内存扩展器（256GB DDR5）读取一个 64 字节 Cache Line。
拓扑 Host CPU → CXL Root Port (Flex Bus x16) → Type 3 Device (HDM-H 模式)
目标地址 HPA = 0x880_0000_1000（已在 CFMWS 定义的 HDM 窗口内）
协议 CXL.mem only（Type 3 无 CXL.cache）。M2S MemRd + S2M MemData。

端到端完整流程（12 步）

1

CPU 核发出 Load 指令
MOV RAX, [0x880_0000_1000] → MMU 将 VA 转换为 HPA 0x880_0000_1000。LLC Miss。请求进入 CPU 的 Home Agent。

2

事务层 — CXL.mem: M2S MemRd 请求构造
Home Agent 识别 HPA 在 HDM Decoder 范围内 → 创建 M2S MemRd 事务包：
MemOpcode| 0001b (MemRd)
---|---
Address[51:6]| 0x880_0000_1000 >> 6 = 0x220_0000_0040
Tag[15:0]| 0x0042（用于匹配响应）
MetaField[1:0]| 00b（HDM-H 无元数据更新）
SnpType| 000b（HDM-H 不需要 Snoop）
→ 从 M2S Req Credit 池消耗 1 个信用。

3

事务层 — MemRd 事务进入发送队列
事务层根据 Tag 分配事务表条目（Transaction Table Entry, TTE）。TTE 记录 Tag=0x0042 等待 S2M DRS 响应。若信用不足则阻塞等待。

4

ARB/MUX — 仲裁通过
ARB/MUX 从 CXL.io / CXL.cache / CXL.mem 三个协议队列中按加权轮询选择。当前 CXL.mem 获得 85% 带宽权重 → MemRd 事务获得 Flit 时隙。

5

链路层 — Flit 打包（68B Flit 格式）

Flit Header (528-bit = 66 Byte):
  Byte 0:  CTL_FMT[7:0] = 0x08  (001b = CXL 2.0+ 模式, H3 编码)
  Byte 1:  H0[7:0]    = Slot 0 类型: H3 (M2S Req Header, 4B)
  Byte 1:  H1[7:0]    = Slot 1 类型: G5 (S2M NDR) — 本 Flit 中用不到，填充 G5
  Slot 0  (Byte 2-17):  M2S MemRd Header (16B)
    - Byte 2-5:  4B Header (MemOpcode, Address[51:12], MetaField, SnpType, Tag)
    - Byte 6-17: Address[11:0]扩展 + Reserved 填充至 16B
  Slot 1  (Byte 18-33): 未使用 (Empty Slot, G5 编码)
  Slot 2  (Byte 34-49): 未使用
  Slot 3  (Byte 50-65): 未使用
  CRC     (Byte 66-67): CRC-16 覆盖前 66 字节

打包规则检查： ✓ 单 M2S Req ≤ 2 条、✓ 紧密打包、✓ 无 Rollover（64B 数据部分未使用）、✓ 无 Control/Data 交错。

6

链路层 — 发送并写入 LLRB
Flit 被赋予当前发送序列号（例如 ESeq=0x0103）→ 完整 Flit 写入 LLRB (Link Layer Retry Buffer) （缓存最多 N 个已发送但未确认的 Flit）。→ 通过 ARB/MUX 交给逻辑 PHY。

7

物理层 — 扰码、8b/10b 编码、串行化
逻辑 PHY 对 528-bit Flit 进行扰码（LFSR）→ 分段为 16 条 Lane → 每条 Lane 通过 SERDES 进行 NRZ 编码（32 GT/s）→ 差分信号经 PCB 走线和连接器传输 ~5 ns。

8

设备端物理层 — 解串 → 解扰 → Flit 重组
设备 SERDES 接收差分信号 → CDR (Clock Data Recovery) 恢复时钟 → NRZ 解码 → Lane Deskew（去偏斜）→ 扰码解除 → 528-bit Flit 重组完成 (~7 ns)。CRC 校验通过 ✓。

9

设备端链路层 — ACK 返回 + Flit 解包
接收方每 8 个正确 Flit 后将 Ak bit 置位，通过 LLCRD Flit 返回 ACK 和更新的 Credit。→ 当前 Flit 解包：Slot 0 = M2S MemRd Header → 提交给设备事务层。

10

设备端事务层 — DPA Decoder 翻译 + DRAM 访问
DPA Decoder: HPA 0x880_0000_1000 → DPA 0x0_0000_1000（假设无交织，直映射）。→ 内存控制器发出 DDR5 ACTIVATE + READ 命令 → ~45 ns 后从 DRAM 阵列读取 64B Cache Line 数据。

11

响应封装 — S2M DRS (MemData)
设备事务层构造 S2M MemData 响应：
Header (H5, Slot 0)| 4B: Tag=0x0042, 无错误 (Cmp=0)
---|---
Data (Slot 1-4)| 4 × 16B = 64B Cache Line 数据
→ 需要 2 个 Flit：Flit A (H5 Header + 16B Data 开始 Rollover) → Flit B (All-Data, 剩余 48B)。链路层打包、LLRB、物理层传输均与请求方向相同。

12

Host 端接收 + 事务匹配
Host 链路层接收 S2M DRS Flit → ACK → 解包 → 事务层根据 Tag=0x0042 查找 TTE → 匹配原始 MemRd → 释放 TTE 条目 → 数据交付给 CPU 的 Load 缓冲区 → Load 指令完成。总延迟 ≈ 120-150 ns（含 DRAM 访问）。

8.2 案例二：CXL 2.0 穿越交换机的 MLD 内存写入（68B Flit, LD-ID 路由）

项目 内容
场景 Host A 通过 CXL 2.0 交换机向 MLD 设备的 LD-3（256GB 分区）写入一个 64B Cache Line。
拓扑 Host A → CXL Switch (单级) → MLD Type 3 Device (4 LD, each 256GB)。LD-3 已由 FM 绑定给 Host A。
目标地址 HPA = 0x900_0000_2000（LD-3 的 HDM 窗口内）
新增特性 MLD 多逻辑设备、LD-ID 路由、CXL Switch HBR 路由、IDE 链路加密

案例二拓扑: CXL 2.0 MLD 内存写入 Host ACXL 2.0 RP x16 CXL SwitchHBR 路由表 MLD Type 3 Device LD-0 | LD-1 | LD-3 (目标) 4 × 256GB DDR5, FM 已绑定 LD-3 给 Host A Fabric Manager Switch HDM Decoder 路由表 Decoder[2]: HPA=0x900_0000_0000, Size=256GB IW=1 → Target=DSP3, LD-ID=3 IDE Stream: Active (AES-GCM-256)

端到端完整流程（11 步）

1

CPU 发出 Store 指令
MOV [0x900_0000_2000], RBX → MMU 转换 → HPA 0x900_0000_2000。地址在 CFMWS 定义的 LD-3 窗口内（由 FM 预配置）。

2

事务层 — CXL.mem: M2S MemWr (RwD) 构造
M2S RwD (Request with Data) 消息：
MemOpcode| 0010b (MemWr)
---|---
Address| 0x900_0000_2000
Tag| 0x00A1
LD-ID| 0x03（CXL 2.0 MLD 新增字段，4-bit）
Data| 64B Cache Line
→ 消耗 1 M2S RwD Credit + Data Credit。

3

事务层 — 事务记录 + ARB/MUX 仲裁
TTE 记录 Tag=0x00A1，等待 S2M NDR (Cmp) 响应。ARB/MUX 加权轮询通过（CXL.mem 获得 80% 权重）。

4

链路层 + IDE 安全 — Flit 打包与加密

M2S RwD 需要 5 个 68B Flit (Header + 64B Data):
  Flit 0: CTL_FMT=0x08, Slot0=H4 (M2S RwD Header, 4B)
          Slot1-3 = Data[0:47]  (48B 数据)
  Flit 1: All-Data Flit, Data[48:63] (最后 16B)
  注意: CXL 2.0 的 CTL_FMT=001b 支持区分 96b/64b payload 模式。

IDE 处理 (插入在链路层和物理层之间):
  对承载 CXL.mem 数据的 Flit 进行 AES-GCM-256 加密。
  IDE_KM (Key Management) 已通过带外 MCTP 交换密钥。
  IDE MAC (Message Authentication Code) 附加在 IDE 控制 Flit 中。

5

物理层 → 交换机物理层
NRZ @ 32GT/s ×16 传输 → CXL Switch USP 接收。CRC 校验通过。

6

交换机网络层 — HBR 路由决策
Switch 从 CXL.mem Flit 头中提取 HPA[63:28] 和 LD-ID=3 → 查询 USP HDM Decoder[2] 路由表：
{HPA_Range=[0x900_0000_0000, 0x900_FFFF_FFFF], Target=DSP3, LD-ID=3} → 匹配 ✓。
→ Flit 转发到 DSP3 端口。仲裁：DSP3 当前无拥塞 → 立即转发。若多个源竞争同一 DSP，使用虚拟通道仲裁。

7

交换机链路层 — Flit 重新打包 + 转发
68B Flit 在交换内部穿过 Crossbar 交换矩阵 → DSP3 的链路层重新发送（新 ESeq、新 CRC-16）。在出口端可能重新进行 IDE 加密（若设备支持逐跳 IDE）。

8

MLD 设备端 — LD-ID 分发 + DPA 翻译
设备链路层解包 → 事务层提取 LD-ID=3 → LD-ID Decoder 将请求路由到 LD-3 的资源域。→ DPA Decoder: HPA 0x900_0000_2000 → LD-3 内部 DPA 0x0_0200（LD-3 基地址 = DPA 空间的第 3 个 256GB 区域）。→ DDR5 Write 命令 → DRAM 写入完成。

9

S2M NDR 完成响应
设备构造 S2M NDR (No Data Response) — 仅 4B Header (Tag=0x00A1, Cmp=0 表示成功)。→ 通过交换机路由回 Host A（沿原路由反向）。

10

Host 端接收 + 事务匹配
Host 链路层接收 S2M NDR → 事务层 Tag=0x00A1 匹配 TTE → 写入完成确认 → 释放 TTE 和 Credit。写入完成总延迟 ≈ 100-110ns（写入比读取快，无需等待 DRAM 读取延迟）。

11

LLCRD Credit 回收
Host 链路层接收到来自设备的 LLCRD 控制 Flit → 解析 Ak bit + Credit 字段 → 释放链路层和事务层信用 → LLRB 中已确认的 Flit 可以被回收（ESeq ≤ Acknowledged_Seq）。

案例二新增要素（vs CXL 1.1）

  • LD-ID 路由： CXL.mem 事务头新增 4-bit LD-ID 字段，设备通过 LD-ID Decoder 分发到正确的逻辑设备。FM 确保隔离性（一个 LD 同时只绑定一个主机）。
  • HBR 路由： 交换机根据 HPA 范围 + LD-ID 查询路由表，决定转发到哪个 DSP。路由表由 FM 通过 MCTP 编程。
  • IDE 链路加密： AES-GCM-256 在链路层对 Flit 进行加密和完整性校验。IDE_KM Flit 在初始化时协商密钥。
  • 额外延迟： 交换机引入的 Store-and-Forward 延迟（~20-30ns/crossbar hop），单级交换机总延迟增加约 25ns。

8.3 案例三：CXL 3.0 P2P DMA — 设备间直接内存访问 + Back-Invalidate（256B Flit, PAM-4, 64GT/s）

项目 内容
场景 加速器 A（Type 2 GPU）通过 CXL Fabric 直接读取 Memory Device B（Type 3 内存扩展器）上的数据，不经过 Host CPU。同时数据在 Host CPU 缓存中有脏副本。
拓扑 Host → Spine SW → Leaf SW1 → GPU A
核心特性 256B Flit, P2P DMA, UIO (Unordered I/O), Back-Invalidate (BI), PBR 路由

案例三拓扑: CXL 3.0 P2P DMA + Back-Invalidate Host CPU + LLC | CXL 3.0 Cache Line X in Dirty (M) state Spine SW (PBR 路由) Leaf SW1 — DSP0: GPU A Type 2 GPU A (UIO) 发起 P2P DMA Read Leaf SW2 — DSP1: Mem Dev B Type 3 Mem Dev B HDM-DB, Back-Invalidate UIO P2P Read: GPU A → Mem Dev B (绕过 Host CPU)

端到端完整流程（14 步 — 含一致性解冲突）

1

GPU A 事务层 — UIO Read 请求构造
GPU A 需要读取 Mem Dev B 上的地址 HPA_X = 0x900_0000_5000。GPU 使用 CXL.io UIO Flow （Unordered I/O，VC1 通道）而非传统有序 CXL.io（VC0）。
UIO MemRd: Address=0x900_0000_5000, TC=VC1, Attr=Unordered。
不使用 CXL.cache 通道，因为目标 Type 3 设备不监听 CXL.cache。

2

GPU 端链路层 — 256B Flit 打包

256B Flit 格式 (CXL 3.0):
  Flit Header (8B):
    - Flit Type = Protocol (CXL.io UIO)
    - Sequence Number = 0x0501
    - Credit Info (嵌入在 Protocol Flit 中, 不再需要单独的 LLCRD Flit)

  Slot[0..7], each 32B:
    G-Slots: 用于通用 Header/Data (CXL.io/CXL.cache/CXL.mem)
    H-Slots: 用于 CXL.cache 数据 (本例不涉及)
    Slot 0:  CXL.io UIO MemRd Header (UIO TLP, ~16B)
    Slot 1-2: 未使用 (Read 请求无数据)

  FEC (6B) + CRC (8B) = 270B 物理帧
  PAM-4 编码: 2 bits/symbol @ 64 GT/s

Credit 回收: CXL 3.0 不再使用独立的 LLCRD Flit。
  Credit 值嵌入在正常 Protocol Flit 的字节 240-241 中。

3

PBR 路由 — 多跳转发到 Mem Dev B

UIO Read 请求从 GPU A 发出 → Leaf SW1 → Spine SW → Leaf SW2 → Mem Dev B

每跳使用 PBR (Port-Based Routing):
  Flit 头部携带 Port Path = [DSP1(Leaf1), USP2(Spine), DSP2(Spine), USP1(Leaf2), DSP1(Leaf2)]
  每跳处理当前端口号并前进到下一个端口号。

延迟: 每级交换机 ~10ns × 3 跳 = ~30ns 额外延迟

4

Mem Dev B 接收 — DPA Decoder 翻译
设备链路层解包 → 事务层接收 UIO MemRd → DPA Decoder 翻译 → 准备 DRAM Read。

5

⚠ 一致性冲突检测 — BI 触发
Mem Dev B 的内存控制器检查 HPA_X 的目录状态 → 发现 Host CPU 缓存中有 Dirty (M) 状态 的副本。
→ CXL 3.0 内存控制器 不 将请求转发到 Host，而是触发 Back-Invalidate (S2M BI) 流程：

S2M BI 通道 (CXL 3.0 新增):
  S2M BI Req: {Address=HPA_X, BI_Type=SnpInv, Tag=0xBI_01}
  → 通过 CXL.mem S2M 通道发送到 Host CPU
  → Host Home Agent 收到 BI SnpInv → 向 LLC 发出 Snoop →
    LLC 返回 Dirty Data (WriteBack) + 缓存行置为 Invalid
  → Host 通过 M2S 通道返回 BI-Rsp: {Tag=0xBI_01, Data=64B Dirty, Status=Complete}
  → Mem Dev B 接收 BI-Rsp，获得最新 Dirty 数据

与传统 CXL 2.0 方式对比:
  CXL 2.0: Host 需要代理所有 P2P 请求 → Host 访问 Mem Dev →
           Host 回写 Dirty → Host 转发给 GPU A → 3 次穿越 Fabric
  CXL 3.0 BI: Mem Dev 直接获取 Host dirty 数据 → 然后直接返回给 GPU A
           → 2 次穿越 Fabric，节省 ~40% 带宽和延迟

6

Mem Dev B — DRAM 读取（若 BI 返回的数据非所需范围）
如果请求的 64B 与 BI 返回的 Dirty 数据完全匹配 → 直接使用 BI 返回的数据。否则需要从 DRAM 补充读取其余范围。DDR5 Read → ~45ns → 合并 BI 数据和 DRAM 数据形成完整 64B。

7

Mem Dev B — UIO Completion 返回 GPU A
设备事务层构造 CXL.io UIO Completion with Data：

UIO CplD: {Requester_ID=GPU_A, Tag=UIO_Tag, Data=64B, Status=Successful}
经过 PBR 路由返回 GPU A (路径: Leaf SW2 → Spine → Leaf SW1 → GPU A)

8

GPU A 接收数据 — 完成
GPU A 链路层接收 → 事务层匹配 UIO Tag → 数据交付给计算单元。P2P 读取完成。总延迟 ≈ 180-250ns（含 BI 流程）。

案例三各层报文处理对比（CXL 2.0 vs CXL 3.0 P2P）

层级 CXL 2.0 方式 (经 Host 中继) CXL 3.0 P2P + BI 方式
事务层 GPU → CXL.io MRd (→ Host) → Host CXL.mem MemRd (→ Dev) → Host CXL.mem Write (→ GPU) GPU → CXL.io UIO MRd (→ Dev 直接)；Dev → CXL.mem S2M BI (→ Host, 仅冲突时)；Dev → UIO CplD (→ GPU)
链路层 三段 68B/256B Flit (GPU→Host, Host→Dev, Dev→Host→GPU) 两段 256B Flit (GPU→Dev, Dev→GPU)，BI 是第三条独立流
网络层 单级/HBR 树形路由 多级 PBR 网状路由，最低延迟路径
物理层 NRZ 32GT/s PAM-4 64GT/s，双倍物理带宽
总数据穿越 Fabric 3 次 2 次 (+ BI 流，仅冲突时)

案例三关键要点

  • UIO (Unordered I/O): 使用独立 VC1 通道，break PCIe ordering 约束，支持非树形拓扑的 P2P 通信。
  • Back-Invalidate: CXL 3.0 的核心创新。Memory Device 可以直接失效 Host CPU 缓存，无需先经过 Host 中转。BI 使用 CXL.mem S2M 通道独立发送。
  • PBR 路由: 脱离树形拓扑限制，支持 Fat-Tree/Mesh/Dragonfly。每跳 ~10ns 额外延迟。
  • 256B Flit: 提供更大的 Header 空间（8×32B Slots），P2P DMA 无需担心 Header 空间不足。

8.4 案例四：CXL 4.0 捆绑端口 (Bundled Port) — 多端口流量喷射写入（128GT/s, 256B Flit Only）

项目 内容
场景 AI 加速器通过 CXL 4.0 捆绑端口向 Type 3 内存池写入 1KB AI 推理 KV Cache 数据（16 个 Cache Line，1KB）。
拓扑 Host → 3×CXL RP (捆绑) → 3×BPD 端口 → Type 3 SLD-B Device（1.5 TB/s 聚合带宽）
核心特性 128GT/s PAM-4, Bundled Ports (3×x16), SLD-B, 仅 256B Flit, Native x2, 4 Retimer

端到端完整流程（12 步）

1

应用层请求 — 1KB KV Cache 写入
AI 推理引擎请求将 1KB（16 条 64B Cache Line）KV Cache 写入 CXL 4.0 内存池。BPD 驱动接收请求并提供交织提示 (Traffic Hint) ：{Policy=Round-Robin, Granularity=64B}。

2

事务层 — 16 个独立 CXL.mem MemWr 事务
BPD 驱动将 1KB 分解为 16 个独立的 64B MemWr 请求。根据流量提示，分配到 3 个端口：

Port 0 (RP0, Full-Cap): Tag 0x100-0x105 → 6 Lines (Addr 0x900_0000_0000 + 0,192,384,576,768,960)
Port 1 (RP1, Streamlined): Tag 0x200-0x204 → 5 Lines (Addr + 64,256,448,640,832)
Port 2 (RP2, Streamlined): Tag 0x300-0x304 → 5 Lines (Addr + 128,320,512,704,896)

  Streamlined Port 特性: 不处理 CXL.io 配置事务，不包含 CXL.cache 支持，
  仅优化 CXL.mem 数据传输，硬件复杂度大幅降低。

3

事务层 — Credit 管理（每端口独立）
3 个端口各自独立管理 M2S RwD Credit + Data Credit。Port 0 有 6 个事务排队，Port 1/2 各 5 个。
信用不足时端口独立等待，不阻塞其他端口。

4

链路层 — 纯 256B Flit 打包（消除 68B 开销）

CXL 4.0 捆绑端口可优化为仅 256B Flit 模式（捆绑中至少一个端口须支持 68B 以保持向后兼容）。

Port 0 的 6 个 MemWr 打包过程:
  Flit 0: 256B, 8 Slots × 32B
    Slot 0 (H4): MemWr Header 0 (Tag=0x100, Addr+0)
    Slot 1: Data[0:31]
    Slot 2 (H4): MemWr Header 1 (Tag=0x101, Addr+192)
    Slot 3: Data[192:223]
    Slot 4 (H4): MemWr Header 2 (Tag=0x102, Addr+384)
    Slot 5: Data[384:415]
    Slot 6 (H4): MemWr Header 3 (Tag=0x103, Addr+576)
    Slot 7: Data[576:607]

  Flit 1: 同上打包剩余 2 Headers + 剩余 32B Data
    Slot 0-1: MemWr 4 (H4+Data)
    Slot 2-3: MemWr 5 (H4+Data)
    Slot 4-7: 空闲

  FEC (6B) + CRC (8B) 嵌入 270B 物理帧中
  PAM-4 @ 128GT/s: 2 bits/symbol, Nyquist Freq ×2 vs CXL 3.0

  Port 1/2 类似处理 5 个 MemWr 各自。

5

ARB/MUX — 3 端口并行发送
3 个物理端口独立通过各自的 ARB/MUX 提交到各自的链路层/物理层 → 并行发送 。无端口间串行化开销。

6

物理层 — 128GT/s PAM-4 + 4 Retimer 长距离传输

Port 0: 256B Flit → FEC 编码 → PAM-4（2 bits/symbol）→ 16 Lanes SERDES
  → 经过 4 个 Retimer（每个 Retimer 独立恢复时钟、重定时）→ 到达 BPD 设备。
  −36 dB 信道损耗，FBER < 1E-6。

Port 1, Port 2: 并行传输，各自独立物理层。

CXL 4.0 128GT/s 的 PAM-4 眼图开口约为 CXL 3.0 64GT/s 的 50%，
4 Retimer 确保长距离（>1m PCB 走线或光纤 Retimer）的信号完整性。

注意: CXL 4.0 支持 Native x2 宽度 — 未来可用于更灵活的小宽度链路汇聚。

7

BPD 设备端物理层 — 3 端口并行接收
3 个端口各自完成：CDR 恢复 → PAM-4 解码 → FEC 校正（如有错误）→ 256B Flit 重组 → CRC 校验。
3 端口并行处理，无串行化。

8

BPD 设备端链路层 — 合并与排序（可选）
3 个端口各自解包 Flit → 提取 16 个 MemWr 事务。BPD 内部根据 Tag 和 Address 排序（确保内存模型一致性）→ 提交给事务层。
SLD-B 抽象：主机侧看到的是 3 个物理端口，设备侧看到的也是 3 个（但 BPD 将它们聚合为单一逻辑设备）。

9

DPA Decoder + 内存交织写入
SLD-B 设备内部的 DPA Decoder 将 16 个 HPA 翻译为 DPA → BPD 内存控制器将 16 条 Cache Line 喷射 写入 3 个内部 DRAM 通道：

Channel 0 (从 Port 0 数据): Lines 0,3,6,9,12,15
Channel 1 (从 Port 1 数据): Lines 1,4,7,10,13
Channel 2 (从 Port 2 数据): Lines 2,5,8,11,14
→ 3 通道并行写入 DDR5, ~45ns DRAM 写入周期

10

S2M NDR 完成响应（逐端口返回）
设备事务层为 16 个 MemWr 各生成 S2M NDR (Cmp)。通过对应物理端口原路返回 Host：
Port 0 → 6 NDR, Port 1 → 5 NDR, Port 2 → 5 NDR。

11

Host 接收 — 事务匹配与完成
各端口独立接收 S2M NDR → Tag 匹配 TTE → 释放 Credit。16 个事务全部完成后，BPD 驱动向上层报告 1KB KV Cache 写入完成。
总延迟 ≈ 90-110ns（得益于 3 端口并行和 PAM-4 高带宽）。

12

RAS 监控 — Patrol Scrub 与 PPR
CXL 4.0 新增的 RAS 特性在后台运行：Patrol Scrub 在巡逻周期中细粒度检测并纠正内存错误；PPR (Post Package Repair) 在设备启动时主机可发起主动内存修复操作。Memory Sparing 支持启动时或延迟执行备用行替换。

案例四关键要点

  • 捆绑端口 (Bundled Ports): CXL 4.0 最重要的架构创新。通过逻辑聚合多个物理端口，实现带宽线性扩展而无需修改软件模型。
  • SLD-B: 软件仍然看到单一逻辑设备 （Single Logical Device），多个物理端口在硬件层透明聚合。对比 CXL 2.0 MLD（需要 LD-ID 管理）大幅简化。
  • 纯 256B Flit 模式: 消除 68B Flit 兼容的复杂性和开销。每 Flit 可承载更多 Header+Data。
  • 流量喷射: 设备驱动可向 BPD 提供交织提示，BPD 硬件在多个端口间均匀分配流量，最大化带宽利用率。
  • AI/ML 场景核心价值: 1.5 TB/s 双向带宽满足下一代 GPU/ASIC 的显存带宽需求，可与 NVLink/UALink 形成互补层次。

总结：CXL 各版本端到端流程的核心演进脉络

  1. CXL 1.1: 奠定基础。M2S/S2M 两通道模型、68B Flit、HDM-H 直连——最简洁的流程。
  2. CXL 2.0: 引入"池化"维度。LD-ID 使单个物理设备呈现为多个逻辑设备。HBR 交换机使数据流多了一级路由决策。IDE 在链路层加入了加/解密开销。
  3. CXL 3.0: 引入"分布式"维度。P2P DMA 使数据流从"必须经过 Host"变为"直接设备间流转"。Back-Invalidate 使一致性解决从"Host 居中"变为"设备自主"。
  4. CXL 4.0: 引入"聚合"维度。Bundled Ports 使多个物理端口透明组合，从"单路串行"变为"多路并行喷射"。纯 256B Flit 消除兼容开销。

第十章 · CXL 术语表

术语 全称 说明
CXL Compute Express Link 开放标准的缓存一致性互连技术，基于 PCIe 物理层
CXL.io — CXL 的 I/O 子协议，功能等价于 PCIe，负责设备发现、枚举、配置等
CXL.cache — CXL 的缓存一致性子协议，允许设备缓存主机内存
CXL.mem — CXL 的内存语义子协议，允许主机访问设备附加内存
HDM Host-Managed Device Memory 主机管理的设备内存，Type 3 设备的内存被主机作为主内存扩展
MLD Multi-Logical Device 多逻辑设备，单个物理 CXL 设备可呈现为多个逻辑设备
FM Fabric Manager 结构管理器，负责动态资源分配和管理 CXL Fabric
FAM Fabric-Attached Memory 结构附加内存，多主机可同时共享访问的内存
GIM Global Integrated Memory 全局互连内存，CXL 3.1 引入的主机间本地内存直接共享机制
IDE Integrity and Data Encryption 完整性与数据加密，CXL 2.0 引入的端到端安全机制
TSP Trusted-Execution-Environment Security Protocol 可信执行环境安全协议，CXL 3.1 引入
Tee Trusted Execution Environment 可信执行环境，机密计算的基础
PBR Port-Based Routing 基于端口的路由，CXL 3.1 引入，支持非树形拓扑
HBR Hierarchy-Based Routing 基于层次结构的路由，CXL 2.0 交换机使用的传统树形路由
FAST Fabric Address Segment Table 结构地址段表，CXL 3.1 引入，加速 GIM 内存访问
Flit Flow Control Unit 流控单元，CXL 传输的固定大小数据单元（68B 或 256B）
PAM-4 Pulse Amplitude Modulation 4-level 四电平脉冲幅度调制，PCIe 6.0+ 使用的信号编码方式
Retimer — 重定时器，重新生成高速数字信号以延伸传输距离
DVSEC Designated Vendor-Specific Extended Capability 指定供应商扩展能力寄存器，用于 CXL 设备枚举
CHMU CXL Hot-Page Monitoring Unit CXL 热页面监控单元，CXL 3.2 引入
Bundled Port — 捆绑端口，CXL 4.0 引入，将多个物理端口聚合为单个逻辑连接
NUMA Non-Uniform Memory Access 非一致性内存访问，CXL 内存在 OS 中表现为 NUMA 节点
VCS Virtual CXL Switch 虚拟 CXL 交换，H3 Platform 的多主机共享内存技术
