## 一、为什么要 KV Cache？

### 1.1 自回归推理的重复计算困境

大语言模型采用自回归（Autoregressive）方式逐 Token 生成文本。在标准 Transformer 架构中，每生成一个新 Token，注意力机制需要访问**之前所有 Token 的 Key 和 Value 向量**。如果不做缓存，每生成一个 Token 都要重新计算前面所有 Token 的 K/V，计算量随序列长度呈**平方级增长**（O(n²)）。

以 LLaMA-70B 为例，生成第 1000 个 Token 时，若不缓存，需要重新计算前 999 个 Token 的 K/V，这几乎等于把整个序列的 Prefill 重新做一遍。

### 1.2 KV Cache 的核心思想：以存代算

**KV Cache 的本质是"以空间换时间"**：将每个 Token 在每一层注意力中计算得到的 Key 和 Value 向量缓存下来，后续生成时直接读取，避免重复计算。

| 维度 | 无 KV Cache | 有 KV Cache |
| --- | --- | --- |
| 每步计算复杂度 | O(n²)（需重算所有历史 Token） | O(n)（仅算新 Token，读取缓存） |
| 内存需求 | 仅模型权重 + 激活值 | 模型权重 + **线性增长的 KV Cache** |
| 生成第 n 个 Token | 需重算前 n-1 个 Token 的 K/V | 仅计算第 n 个 Token 的 K/V，其余从缓存读取 |

### 1.3 KV Cache 带来的新矛盾

KV Cache 解决了重复计算问题，但引入了新挑战——**KV Cache 随上下文长度线性增长，最终成为显存的主要消耗者**：

以 LLaMA-70B 为例（64 层 × 64 头 × 128 维 × 2 字节）：

| 上下文长度 | KV Cache 大小（单请求） | 说明 |
| --- | --- | --- |
| 2K Token | ~2 GB | 常规对话 |
| 8K Token | ~8 GB | 长文档分析 |
| 32K Token | ~32 GB | 代码仓库分析 |
| 128K Token | ~128 GB | 超出单卡 H100 80GB |

**核心矛盾**：模型权重是固定常数（选定模型后不变），而 KV Cache 是**动态增长**的，当上下文足够长时，KV Cache 占用会远超模型权重本身，成为制约并发和长上下文的核心瓶颈。

业界因此从两个正交方向进行优化：

- **方向一：增加 KV 存储空间** —— 多级缓存扩展容量，Prefill-Decode 分离，跨节点共享
- **方向二：减小 KV 大小/数量** —— 注意力机制压缩（MQA/GQA/MLA）、稀疏注意力、量化

## 二、如何解决 KV Cache 容量越来越大、占据空间越来越多的问题

### 2.1 KV Cache 分级缓存方案

#### 2.1.1 主流分级缓存方案全景

KV Cache 分级缓存借鉴了 CPU 多级缓存（L1/L2/L3）的设计思想，将不同热度的 KV Cache 放置在不同速度和容量的存储介质上，在延迟和容量之间取得平衡。

**通用架构：HBM → DRAM → SSD → 分布式存储**

| 层级 | 介质 | 典型延迟 | 典型容量 | 角色 |
| --- | --- | --- | --- | --- |
| L1 | GPU HBM（显存） | 纳秒~微秒级 | 数十~数百 GB | 当前活跃推理的 KV Cache |
| L2 | CPU DRAM（主机内存） | 微秒~毫秒级 | 数百 GB ~ TB 级 | 近期完成的请求、热前缀缓存 |
| L3 | SSD（本地或共享） | 百微秒~毫秒级 | TB 级 | 冷 KV Cache、历史对话 |
| L4 | 分布式存储 / 对象存储 | 毫秒~秒级 | PB 级 | 跨节点共享、归档 |

**各厂商分级缓存方案详解：**

***

##### ■ NVIDIA：TensorRT-LLM + Dynamo 三级方案

**引擎层（TensorRT-LLM）：**

- **Paged KV Cache**：借鉴 OS 虚拟内存分页机制，将 KV Cache 切分为固定大小 page（如 16 tokens/page），非连续物理存储，消除内存碎片，利用率从 20-40% 提升至近 100%
- **量化 KV Cache**：支持 FP8/INT8 量化，直接将 KV Cache 大小减半或降至 1/4
- **KV Cache Reuse（Prefix Caching）**：自动识别公共前缀并共享 page，多轮对话场景节省 50%+ 显存

**集群层（Dynamo 框架，2025 GTC 发布）：**

- **三级 KV Cache 层级**：L1 GPU HBM → L2 CPU Host Memory → L3 SSD/对象存储
- **KV Cache Manager**：自动将低频访问的 KV Cache 卸载到更经济的存储层，支持 PB 级 KV Cache 存储
- **Prefill-Decode 分离**：Prefill 节点（计算密集）和 Decode 节点（内存密集）分离部署，各自独立扩展
- **NIXL（NVIDIA Inference Transfer Library）**：统一抽象 NVLink、InfiniBand、PCIe、SSD fabric，实现跨内存/存储层级的高速异步数据传输

**vAttention（学术研究，ASPLOS 2025，NVIDIA/微软联合提出）：**

- **用 CUDA 虚拟内存 API 替代 PagedAttention，在虚拟地址空间中保持 KV Cache 连续，物理内存按需分配**
- 修改 CUDA 驱动支持 **64KB-256KB** 细粒度物理页分配（原生最小 2MB）
- **无需重写 attention kernel，直接复用 FlashAttention/FlashInfer**，吞吐提升最高 1.23x，TTFT 降低 1.45x

***

##### ■ 华为：UCM 统一缓存管理（HBM→DRAM→SSD 三级）

**UCM（Unified Cache Manager，2025年8月发布，9月开源）构建三级缓存架构：**

| 层级 | 介质 | 角色 | 延迟 |
| --- | --- | --- | --- |
| L1 | HBM（昇腾 NPU 显存） | 当前活跃对话的 KV Cache | 毫秒级 |
| L2 | DRAM（CPU 内存） | 近期完成的请求、热前缀 | 十毫秒级 |
| L3 | 高性能 SSD（外置共享存储） | 历史对话、RAG 知识库缓存 | 百毫秒级 |

**三大核心组件：**

1. **Connector（推理引擎插件）**：对接 MindIE、vLLM-Ascend 等不同推理引擎
2. **Accelerator（功能库）**：包含多种 KV Cache 加速算法
3. **Adapter（适配器）**：高性能 KV Cache 存取，对接专业存储系统

**昇腾芯片层协同优化：**

- **AMLA（Ascend MLA）算子**：针对 DeepSeek **MLA 的 FlashAttention 算子**重构，直接在 Global Memory 上更新 O，无需进入 Vector core
- **权重预取**：通信算子进行过程中预取后续 MLA 权重矩阵和 KV cache 到缓存
- **MLA 前序算子融合**：Decode 阶段采用权重吸收，深度融合为 MLAProlog 算子

**效果指标**：首 Token 时延最高降低 90%，长序列 TPS 提升 2-22 倍

***

##### ■ Mooncake（月之暗面）：四级 KVCache 为中心的分离式架构

Mooncake 是 Kimi 的推理服务平台（FAST 2025 最佳论文），采用**以 KVCache 为中心的分离式架构**：

**四级 KV Cache 层级：**

1. **GPU VRAM**：当前活跃 Decode 的 KV Cache
2. **CPU DRAM**（节点本地）：Prefill 产出的 KV Cache，分页存储（paged blocks）
3. **SSD**（节点本地）：DRAM 溢出的冷 KV Cache
4. **分布式 KVCache 池**：跨节点共享，利用集群中未被充分利用的 CPU/DRAM/SSD 资源

**Prefill-Decode 分离架构：**

- Prefill 集群（计算密集）和 Decode 集群（内存密集）物理分离
- Prefill 阶段采用 Chunked Pipeline Parallelism（CPP）跨多节点处理单个长请求，减少 TTFT
- KV Cache 通过 **Transfer Engine** 从 Prefill 节点流式传输到 Decode 节点

**效果**：Kimi 处理量提升 75%（A800 集群 115%，H800 集群 107%），长上下文场景吞吐提升最高 525%

##### ■ 阿里：Tair KVCache + PolarKVCache + FlashKV 多产品矩阵

阿里在 KV Cache 分级缓存领域形成了多层次产品矩阵：

**(1) Tair KVCache（独立缓存服务）：**

| 层级 | 介质 | 功能 |
| --- | --- | --- |
| L1 | GPU 显存 | 活跃推理 KV Cache |
| L2 | CPU 内存 | 温热 KV Cache，毫秒级响应 |
| L3 | SSD（基于 3FS 存储系统） | 冷 KV Cache，大容量存储 |

**(2) PolarKVCache（PolarDB 集成方案，四级架构）：**

| 层级 | 介质 | 性能 | 容量 | 说明 |
| --- | --- | --- | --- | --- |
| L1 | 本地 GPU 显存（VRAM） | 最高 | 最小 | 当前计算的 KVCache Page |
| L2 | 本地主机内存（DRAM） | 较高 | 较大 | VRAM 扩展，换入/换出不活跃 Page |
| L3 | 分布式内存池（DMP） | 居中 | 巨大 | 核心存储层，PB 级扩展，跨节点共享 |
| L4 | 分布式磁盘池 | 最低 | 海量 | 冷 KVCache 持久化归档 |

- 容量从单节点 512GB 扩展到 10TB 级别
- 聊天场景 TTFT 降低 26.8 倍，吞吐提升 62%

**(3) FlashKV（PAI TokenWorks 2025 新发布）：**

- 分布式 KV-Cache 缓存服务，将 KV 张量分层持久化至内存、磁盘和远端
- 实现集群级跨实例共享，后续相同前缀的请求直接复用
- 热点前缀驻留内存保障低延迟，冷门数据自动下沉至磁盘或远端

**调度层（Llumnix + TokenWorks）：**

- **Llumnix 调度引擎**（OSDI 2024 论文）：支持请求在推理实例间实时迁移
- **KV Cache 感知路由**：感知推理引擎内部 Cache 分布，而非简单 Round Robin
- 千万级活跃用户场景下 KV Cache 命中率提升 10 倍以上

##### ■ 浪潮：InCloud AIOS 三级存储 + GPU Direct Storage

浪潮云海 InCloud AIOS 采用三级存储架构：

| 层级 | 介质 | 时延 | 角色 |
| --- | --- | --- | --- |
| L1 | GPU 本地显存（HBM） | 毫秒级 | 当前活跃对话 |
| L2 | CPU DRAM + NVMe SSD | 容量放大 3-5 倍 | 近期完成的请求 |
| L3 | 分布式存储 | 近乎无限容量 | 跨机房/跨节点共享 |

**核心技术特点：**

- **GPU Direct Storage**：L2 到 L1 采用 PCIe DMA，L3 到 L2 采用 RDMA，实现"内存-显存"零拷贝直接传输
- **数据按热度自动迁徙**：新生成内容先落 L1，请求结束后按频率下沉到 L2、L3
- **实测效果**（DeepSeek-8B，10K tokens）：TTFT 从 1.94s 降至 0.136s，时延下降 93%

##### ■ CXL 交换设备：XConn / MemVerge / Beluga 方案

CXL（Compute Express Link）技术为 KV Cache 提供了全新的**共享内存池**层级：

| 层级 | 介质 | 访问方式 | 延迟 |
| --- | --- | --- | --- |
| L1 | GPU HBM | 本地访问 | 纳秒级 |
| L2 | CPU DRAM | 本地内存访问 | ~100ns |
| L3 | **CXL 内存池**（共享） | CXL load/store 语义 | 200-500ns |
| L4 | SSD / 网络存储 | NVMe / RDMA | ~100μs / >10ms |

**核心优势**：CXL 内存池以 200-500ns 的延迟填补 HBM 与 SSD 之间的巨大鸿沟，支持 100TiB 级共享池化，提供硬件管理的缓存一致性。

- **XConn Apollo**：混合 CXL/PCIe 交换方案，Ultra IO Transformer 使 PCIe GPU 也能访问 CXL 内存池
- **MemVerge GISMO**：软件定义弹性 CXL 内存
- **Beluga**（学术，arXiv 2025）：相比 RDMA 方案 TTFT 降低 89.6%，吞吐提升 7.35 倍

#### 2.1.2 同一层级内如何增加 KV Cache 空间

在同一物理层级内扩展 KV Cache 容量是各厂商的核心竞争点，主要有以下技术路径：

##### (1) 内存碎片消除：PagedAttention / vAttention

**问题**：传统连续分配方式下，不同长度请求的 KV Cache 产生大量内存碎片，利用率仅 20-40%。

**NVIDIA PagedAttention（vLLM 实现）**：

- 将 KV Cache 切分为固定大小 page（如 16 tokens/page）
- 非连续物理存储，通过页表映射
- 利用率从 20-40% 提升至近 100%，**等效于同层级容量提升 2.5-5 倍**

**NVIDIA vAttention（ASPLOS 2025）**：

- 用 CUDA 虚拟内存 API（`cuMemAddressReserve` / `cuMemCreate` / `cuMemMap`）实现更底层的管理
- 虚拟地址连续 + 物理内存按需分配，支持 64KB-256KB 细粒度物理页
- 无需修改 attention kernel，比 PagedAttention 吞吐提升 1.23x

##### (2) 量化压缩：FP8/INT8/INT4

在相同显存内存储更多 KV Cache：

- **FP16 → INT8**：容量翻倍（2x），精度损失极小
- **FP16 → FP8**：容量翻倍（2x），NVIDIA TensorRT-LLM 原生支持
- **INT4 / 2-bit 量化**：KIVI 等方案实现 4-8x 压缩，需针对性校准

**厂商案例**：

- NVIDIA TensorRT-LLM：原生支持 FP8/INT8 KV Cache 量化
- 华为昇腾：配合 UCM 进行 KV Cache 量化
- 阿里 BladeLLM：内置混合精度量化

##### (3) 跨节点共享同一层级空间

将多个节点的同层级资源聚合为共享池：

| 方案 | 共享层级 | 机制 | 厂商 |
| --- | --- | --- | --- |
| 共享 DDR | L2（DRAM） | RDMA / CXL 内存池 | CXL（XConn 100TiB 池）、Mooncake（分布式 DRAM 池） |
| 共享 SSD | L3（SSD） | NVMe-oF / 分布式存储 | 阿里（3FS 存储系统）、浪潮（分布式存储）、Mooncake（P2P Store） |
| 共享 HBM | L1（显存） | NVLink / GPUDirect RDMA | NVIDIA（NIXL 跨 GPU 传输）、Mooncake（Transfer Engine GPUDirect） |

**CXL 共享内存池**是同一层级扩展的最新突破：

- XConn Apollo 支持 100TiB 级 CXL 内存池，多 GPU 节点共享同一物理内存池
- 通过 CXL load/store 语义直接访问，延迟 200-500ns，比 RDMA 低一个数量级
- 相当于在不增加单节点 DRAM 的情况下，将 L2 层容量扩展 10-100 倍

##### (4) Prefill-Decode 分离释放显存

将 Prefill 和 Decode 部署在不同节点，Decode 节点不需要存储 Prefill 产生的完整 KV Cache，而是按需从 Prefill 节点拉取：

- **NVIDIA Dynamo**：Prefill 节点产出 KV Cache 后，通过 NIXL 传输到 Decode 节点
- **Mooncake**：Prefill 集群和 Decode 集群物理分离，KV Cache 通过 Transfer Engine 流式传输
- **阿里 PAI-EAS**：负载感知的 PD 分离，首 Token 响应时间降低 92%，吞吐提升 91%
- **效果**：Decode 节点显存完全用于活跃请求，不再被 Prefill 阶段的长序列 KV Cache 占据

#### 2.1.3 分级缓存中的 KV Cache 生命周期管理与调度方案

KV Cache 的生命周期从生成到销毁经历四个阶段：**生成 → 存储分配 → 迁移/驱逐 → 复用/删除**。各厂商在每个阶段都有精细化的管理策略。

##### (1) 生成阶段：KV Cache 感知调度

| 厂商 | 调度策略 | 说明 |
| --- | --- | --- |
| **NVIDIA** | Smart Router（Radix Tree） | 追踪全集群 GPU 上 KV Cache 位置，计算请求与已有 KV Cache 的重叠分数，路由到命中率最高的 worker |
| **Mooncake** | Conductor 全局调度器 | 统一调度 Prefill/Decode 实例对，最大化复用已有 KV Cache |
| **阿里** | KV Cache 感知路由 | 感知推理引擎内部 Cache 分布，而非简单 Round Robin；千万级用户命中率提升 10x |
| **浪潮** | 负载感知弹性调度 | 实时对话高峰优先保障 L1，长文档分析高峰扩容 L2 至 100GB+ |

##### (2) 存储分配阶段：分层放置策略

### 2.2 减小 KV 容量的方案（MQA / GQA / MLA / LSA 等）

分级缓存从"增加空间"角度解决问题，而注意力机制压缩则从"减小 KV 本身"角度切入。两者正交互补。

#### 2.2.1 注意力机制演进谱系

从 MHA 到 MLA，KV Cache 压缩经历了从"暴力共享"到"智能压缩"的演进：

```
MHA（基准）→ MQA（极端共享）→ GQA（折中共享）→ MLA（低秩压缩）→ LSA/SLA（稀疏选择）
```

| 维度 | MHA | MQA | GQA | MLA | LSA |
| --- | --- | --- | --- | --- | --- |
| **策略** | 每头独立 K/V | 全头共享单组 K/V | 组内共享 K/V | 压缩到低秩隐空间 | 预测式稀疏选择 |
| **KV Cache 压缩** | 基准（1x） | H 倍（~32x） | H/G 倍（4-8x） | 任意倍（57x） | 缓存仅 13.5% |
| **逐头多样性** | 完全 | 无（全头相同） | 部分（组内共享） | 完全（上投影重建） | 选择性保留 |
| **质量** | 基准 | 略有下降 | 接近 MHA | 接近或超过 MHA | +0.6% 提升 |
| **代表模型** | GPT-3 | PaLM/Gemini | LLaMA-2/3 | DeepSeek-V2/V3 | FlashMemory-DeepSeek-V4 |
| **需重新训练** | - | 是 | 可 uptraining | 是 | 是（indexer 独立训练） |

***

#### 2.2.2 MQA（Multi-Query Attention，多查询注意力）

**提出**：Noam Shazeer, 2019, *Fast Transformer Decoding: One Write-Head is All You Need*

**核心机制**：

- 标准 MHA 中，每个注意力头都有独立的 K 和 V 投影矩阵，产生 H 组不同的 K/V
- MQA 让**所有注意力头共享同一组 K/V**，即只有 1 个 K 头和 1 个 V 头
- KV Cache 从 H 组降为 1 组，压缩比 = H 倍（如 32 头模型压缩 32x）

**效果**：

- KV Cache 存储**减少 10-100 倍**
- 解码推理速度**提升 12 倍**
- 质量有一定下降，但大部分任务损失有限

**代表模型**：PaLM、StarCoder、Gemini、Falcon

**局限**：

- 所有头共享相同 K/V，丧失逐头多样性，复杂上下文建模能力下降
- 必须从头训练，无法从 MHA 模型直接转换
- 张量并行时 K/V 必须在每个节点复制

***

#### 2.2.3 GQA（Grouped-Query Attention，分组查询注意力）

**提出**：Ainslie et al., 2023, *GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints*

**核心机制**：

- 将 H 个注意力头分为 G 个组，每组共享一对 K/V
- G=H 时退化为 MHA，G=1 时退化为 MQA
- GQA 提供了 MHA 和 MQA 之间的平滑过渡

**关键创新——Uptraining**：

- 已有的 MHA 模型可通过"uptraining"转换为 GQA：对组内的 K/V 头做 mean-pooling 合并，然后继续预训练约 5% 原始计算量
- 无需从头训练，可直接优化现有模型

**效果**：

- KV Cache 压缩 H/G 倍（如 LLaMA-2-70B: 64 头 / 8 组 = 8x 压缩）
- 质量接近 MHA，速度接近 MQA
- 天然适配张量并行：G 组数设为张量并行度，每卡恰好 1 个 K/V 头

**代表模型**：LLaMA-2-70B、LLaMA-3 全系列、Mistral 7B、IBM Granite 3.0、ChatGLM2/3、Yi

**LLaMA-2-70B 的 G=8 选择**：70B 模型需 8 卡部署，G=8 恰好每卡负责一组 K/V，在保证 K/V 多样性的同时最大化减少卡间通信。

***

#### 2.2.4 MLA（Multi-Head Latent Attention，多头潜在注意力）

**提出**：DeepSeek, 2024, DeepSeek-V2 技术报告

**核心思想**：不通过共享 K/V 头来减少 KV Cache，而是通过**低秩压缩**将 K/V 联合压缩为一个极小的共享隐向量。

**三层创新机制：**

**第一层：低秩联合压缩**

- 用下投影矩阵 $W^{DKV}$ 将输入压缩为极小的共享隐向量 $c\_{KV} \\in \\mathbb{R}^{d_c}$（$d_c \\ll 2 \\cdot H \\cdot d\_{head}$）
- 仅缓存隐向量（每位置仅 $2d_c$ 个标量）
- DeepSeek-V2 中 $d_c = 512$，相比原始 KV（8头 × 128维 = 1024），压缩约 57 倍
- **KV Cache 减少 93.3%**

**第二层：权重吸收（Absorption）**

- 利用矩阵乘法结合律：$q^{(s)}\_t {k^{(s)}\_i}^\\top = (x_t W^{(s)}\_q)(c_i W^{(s)}\_k)^\\top = x_t (W^{(s)}\_q {W^{(s)}\_k}^\\top) c_i^\\top$
- 在模型加载时提前合并上投影权重到注意力权重矩阵
- 推理全程**不需要显式解压高维 KV**，抵消全部额外算力开销
- 推理速度与 GQA 持平

**第三层：解耦 RoPE**

- RoPE（旋转位置编码）与低秩压缩天生冲突（RoPE 是位置相关的分块对角矩阵，无法折叠到隐空间）
- 将向量拆为"内容"（存入隐向量 $c\_{KV}$）和"位置"（单独的小旋转键 $k^R$）两部分
- 分开压缩、分开计算，保留 RoPE 位置区分能力

**效果**：

- KV Cache 压缩 **93.3%**，57 倍压缩比
- 推理速度提升 **2.3 倍**，推理成本降低 **5 倍**
- 质量接近或超过 MHA（DeepSeek 报告 MLA 略优于 MHA）
- 相同显存可支持**更大 batch size** 和**更长上下文**（1.7 倍）

**华为昇腾对 MLA 的硬件适配**：

- AMLA 算子针对 DeepSeek MLA 重构 FlashAttention，通过浮点二进制编码解析及原子累加实现乘性计算的加性等价转换
- 直接在 Global Memory 上更新 O，无需进入 Vector core
- Decode 阶段深度融合为 MLAProlog 算子，进一步降低延迟

**DeepSeek-V3.2-Exp 的进一步优化——DSA（DeepSeek Sparse Attention）**：

- 在 MLA 基础上引入稀疏方案，结合轻量级"indexer"进行细粒度 token 选择
- 注意力集中在最相关的 token/block 上，进一步降低 KV-cache 压力
- 长上下文场景获益最大

***

#### 2.2.5 LSA（Lookahead Sparse Attention，前瞻稀疏注意力）

**提出**：Tencent/FlashMemory 团队, 2026, FlashMemory-DeepSeek-V4（arXiv 2606.09079）

**核心机制**：

- 训练一个小型 **Neural Memory Indexer**（神经记忆索引器），预测当前 Token 实际需要哪些历史 KV chunk
- 推理时只加载预测相关的 KV 条目，大部分 KV Cache 从不进入显存
- 与 MiniMax MSA 等块稀疏方案不同：MSA 仍保留全量缓存但只计算部分，LSA 直接**避免持有大部分缓存**，节省的是物理显存占用

**关键创新——Backbone-free 解耦训练**：

- 索引器的训练不需要加载万亿参数的基座模型
- 独立训练索引器，大幅降低训练成本

**效果**：

- KV Cache 物理占用降至全量的 **13.5%**（500K 上下文从 ~40GB 降至 ~5.4GB）
- 精度反而提升 **+0.6%**

**对比 MLA vs LSA**：

- MLA 从"压缩每个 KV 的大小"入手（低秩压缩）
- LSA 从"减少加载的 KV 数量"入手（稀疏选择）
- 两者可叠加使用

***

## 三、KV Cache 如何解决命中率问题

KV Cache 分级缓存的核心价值在于"命中即省算"，命中率每提升 1% 都意味着可观的计算节省。但高命中率面临三大挑战：

1. **容量有限**：热数据无法全部放入高速层
2. **前缀匹配局限**：传统方案仅支持从头开始的前缀匹配
3. **跨节点缓存分散**：多副本部署时缓存被分散，命中率随扩容下降

各厂商从多个维度解决命中率问题：

### 3.1 前缀树/基数树索引：从精确前缀到任意子序列匹配

#### SGLang RadixAttention（基数树）

**问题**：传统前缀缓存只能共享从输入开头的完全相同前缀。但在 RAG 场景中，不同请求可能共享中间的文档片段：

```
请求1: [system_prompt] [doc_A] [question_1]
请求2: [system_prompt] [doc_A] [question_2]  ← 共享 system_prompt + doc_A
请求3: [system_prompt] [doc_B] [question_3]  ← 仅共享 system_prompt
```

**RadixAttention 方案**：

- 维护一棵基数树（Radix Tree），每个节点存储：token 序列、KV Cache 指针、引用计数、LRU 时间戳
- 查找复杂度 O(L)（L 为序列长度）
- 驱逐策略：LRU + 引用计数保护（使用中的节点不可驱逐）

**效果**：

- RAG 工作负载（固定文档库）：KV Cache 命中率 **40-70%**
- 多轮对话（持久会话）：命中率 **20-40%**
- 代码补全（独特文件上下文）：命中率 <10%
- 相比 vLLM 基础前缀缓存，SGLang RadixAttention 在多级共享结构下命中率高 **2-4 倍**

#### NVIDIA Radix Tree Smart Router

NVIDIA Dynamo 框架的 Smart Router 基于 Radix Tree 追踪全集群 GPU 上的 KV Cache 位置：

- 计算请求与已有 KV Cache 的**重叠分数**（overlap score）
- 智能路由到缓存命中率最高的 worker
- 内部基准显示缓存命中率提升约 **20%**

***

### 3.2 热度感知调度：HotPrefix

**SIGMOD 2025** 提出的 HotPrefix 方案解决了"哪些前缀应该被缓存"的问题：

**三大创新：**

1. **动态热度追踪（Dynamic Hotness Tracking）**：

    - 使用增强型布谷鸟过滤器（Cuckoo Filter）记录前缀树节点的热度信息
    - 低存储开销 + 高搜索效率
    - 动态更新机制持续追踪节点热度变化

2. **选择性 KV Cache 准入（Selective KV Cache Admission）**：

    - GPU 显存驱逐的 KV Cache **并非全部**进入主机内存
    - 仅保留高热度 KV Cache 到 CPU 内存，丢弃低热度的
    - 减少数据传输成本

3. **热度提升（Hotness Promotion）**：

    - 周期性将高热度前缀从 CPU 内存提升到 GPU 显存
    - 优先提升**深度更浅**（更通用）的高热度缓存
    - 配合 I/O-计算流水线策略掩盖传输延迟

**效果**：相比 vLLM（开启前缀共享）延迟降低、吞吐提升 **2.25x**；相比 SGLang 提升 **2x**

***

### 3.3 跨副本/跨节点缓存共享：LMCache 与集群级共享

**问题**：多副本部署时，每个副本独立缓存相同的前缀，造成 8 倍冗余。请求落在没有缓存的副本上就完全 miss。

#### LMCache（OSDI 2024）

三层分离式 KV Cache：

- **GPU HBM（热层）**：KV blocks 活跃使用中，亚毫秒访问
- **CPU RAM（温层）**：最近驱逐的 KV blocks，~1-2ms 传输延迟，容量比 HBM 大 6-8x
- **持久存储（冷层）**：S3 兼容对象存储，100ms-1s 加载时间

**缓存局部性路由（Cache-locality Routing）**：

- 负载均衡器维护哈希表：哪些前缀哈希在哪个副本的 HBM 中
- 请求优先路由到已有 HBM 命中的副本，其次 CPU RAM 命中的副本
- 10+ 副本时，Prefill 计算减少 **40-65%**；RAG 场景 TTFT 降低 **2-3x**

#### 阿里 FlashKV 集群级共享

- 所有推理副本共享同一份缓存，无论请求被路由到哪个副本均可命中
- **扩容不降命中率**：单副本扩展到多副本时命中率不下降
- 千万级活跃用户场景命中率提升 **10 倍**

#### 阿里 PolarKVCache 分布式内存池

- L3 层分布式内存池（DMP）提供 PB 级共享存储
- 跨节点、跨会话共享 KVCache
- 聊天场景 TTFT 降低 26.8 倍

***

### 3.4 非前缀片段复用：突破"从头匹配"限制

#### 浪潮任意片段精准复用

传统前缀缓存只能匹配输入序列开头的相同部分。浪潮为每个 KVCache Block 构建三重标签元数据：

1. **文本指纹**：token 序列哈希生成唯一标识
2. **存储位置**：层级/节点IP/路径/偏移量
3. **生命周期**：生成时间/访问时间/访问次数

即使文档中间某段重复出现（如合同标准条款），也能通过文本指纹精准匹配，复用率比传统前缀方案提升 **3-5 倍**。

#### CacheBlend（LMCache / PolarKVCache）

选择性重计算策略：

- 复用提示词中间任意位置的匹配块
- 即使前后文略有不同，也能通过选择性重计算保证输出质量
- RAG 场景冗余计算减少 **51%**

***

### 3.5 KV Cache 事件追踪与一致性管理

#### NVIDIA KV Cache 事件 API

- 实时追踪 KV Cache 块的**创建、存储、删除、更新**事件
- 提供最终一致性视图
- 支撑 KV-aware 路由决策——路由器实时知道哪些 KV Cache 在哪里

#### Mooncake 块级哈希去重

- 每个 KV Cache Block 附带哈希值（自身哈希 + 前缀哈希）
- 哈希值相同即去重
- 前缀哈希支持快速前缀匹配

## 四、KV Cache 分级缓存如何解决不同速率层级之间数据高效传递的问题

KV Cache 分级缓存的核心工程挑战是**层级间巨大的速度差异**：

| 层级跳跃 | 延迟差距 | 数据量 | 挑战 |
| --- | --- | --- | --- |
| L1→L2（HBM→DRAM） | 100x | GB 级 | PCIe 带宽瓶颈、CPU 拷贝开销 |
| L2→L3（DRAM→SSD） | 1000x | TB 级 | SSD IOPS 限制、网络延迟 |
| L1→L3（HBM→SSD/远端） | 10000x | 跨节点 | 网络带宽、协议开销 |

各厂商通过以下技术路径解决层级间数据高效传递问题：

### 4.1 零拷贝传输：绕过 CPU 的直接数据通路

#### NVIDIA NIXL（统一传输抽象层）

NIXL 是 NVIDIA Dynamo 的核心传输库，统一抽象多种硬件链路：

```
应用层：KV Cache Manager
    ↓
NIXL 统一 API
    ↓
后端选择：UCX | GPUDirect Storage | S3 | 自定义插件
    ↓
物理链路：NVLink | InfiniBand | PCIe | SSD Fabric
```

**核心能力**：

- **动态后端选择**：根据数据位置和目标层级，自动选择最优传输后端（UCX/GDS/S3/自定义插件）
- **跨层级优化**：统一 GPU HBM、CPU DRAM、本地 SSD、网络存储之间的数据传输
- **支持多种网络**：NVLink、NVLink Switch、Quantum InfiniBand、Spectrum-X Ethernet

**WEKA + NIXL 实测**（DGX 8×H100）：

- 零拷贝 RDMA 管道，数据从 NIC 直接 DMA 到 GPU 显存，绕过 CPU
- 读吞吐最高 **269.72 GB/s**，写吞吐最高 **123.44 GB/s**
- KV cache 以近内存速度传输（最高 252 GB/s/节点）

#### Mooncake Transfer Engine

Mooncake 自研的高性能数据传输库：

**统一接口支持多种协议**：

- TCP（基础）
- RDMA（InfiniBand/RoCEv2/eRDMA/NVIDIA GPUDirect）
- NVMe over Fabric (NVMe-oF)

**核心优化**：

- **多 RDMA NIC 设备聚合带宽**：支持使用多块 RDMA 网卡聚合传输带宽
- **拓扑感知路径选择**：基于 NUMA 亲和性选择最优设备和路径
- **容错重传**：传输失败时自动尝试替代路径

**实测性能**：

- 4×200Gbps RoCE：**87 GB/s**（比 TCP 快 2.4x）
- 8×400Gbps RoCE：**190 GB/s**（比 TCP 快 4.6x）
- 40GB 数据（128K Token 的 LLaMA-70B KVCache）可秒级传输

#### 阿里 PolarKVCache GPU Direct RDMA

- GPU 绕过 CPU，直接通过 RDMA 网卡读写远程分布式内存池
- 数据传输延迟降至**微秒级**，性能接近访问本地内存
- 消除 CPU 参与数据拷贝的开销

#### 浪潮 GPU Direct Storage

- L2→L1 采用 PCIe DMA，L3→L2 采用 RDMA
- 实现"内存-显存"零拷贝直接传输
- 避免 CPU 二次拷贝，减少 PCIe 带宽占用

***

### 4.2 分层流水线传输：计算与传输重叠

#### 阿里 PolarKVCache Layer-wise 流水线

**核心思想**：KV Cache 不是整体传输，而是按 Transformer 的\*\*层（Layer）\*\*粒度流水线传输。

```
时间线：
Layer 0 KV传输: ████
Layer 0 计算:       ████
Layer 1 KV传输:     ████
Layer 1 计算:           ████
Layer 2 KV传输:         ████
Layer 2 计算:               ████
...
```

**Scatter/Gather 流水线操作**：

- 当第 N 层的 KV Cache 正在通过 RDMA 网络传输时
- 计算单元可以**同时开始计算**第 N 层（用已到达的数据）
- 网络延迟被计算时间**掩盖**（overlapped）
- 端到端效率大幅提升

#### 浪潮异步预加载与跨层同步

**预加载触发**：

- 模型计算第 i 层注意力时，**提前触发**第 i+1 层所需 KVCache 的加载请求
- 利用计算时间掩盖下一层 KV Cache 的加载延迟

**跨层同步点**：

- 注意力层插入"同步点"，仅等待**当前层**缓存加载完成
- 不需要等待所有层加载完毕才开始计算

**零开销调度**：

- CPU 的调度决策逻辑与 GPU 上一个 batch 的执行重叠
- 避免因调度引入额外的流水线停顿

#### 阿里 Tair KVCache 异步缓存预取

**两阶段预取**：

1. **第一阶段（L3→L2）**：请求进入等待队列后，立即启动异步 I/O，将命中的 KV Cache 从 SSD 迁移至 Host DRAM。此过程在 CPU 后台进行，不影响 GPU 推理
2. **第二阶段（L2→L1）**：当调度器将该请求纳入下一批次时，检查 L2 缓存是否就绪。若就绪，启动从 Host DRAM 到 GPU HBM 的缓存加载

***

### 4.3 CXL 共享内存语义：消除数据拷贝

CXL 提供了不同于 RDMA 的范式——**不需要"传输"，而是"共享访问"**：

```
传统 RDMA 路径：
GPU → 本地 DRAM → NIC → 网络 → NIC → 远端 DRAM → GPU
（多跳拷贝，协议开销，微秒级延迟）

CXL 路径：
GPU/CPU → CXL 内存池（直接 load/store 访问）
（零拷贝，硬件一致性，200-500ns 延迟）
```

| 维度 | RDMA | CXL |
| --- | --- | --- |
| 访问语义 | 消息传递（Send/Recv） | 共享内存（Load/Store） |
| 延迟 | 微秒级（~1-10μs） | 纳秒级（200-500ns） |
| CPU 参与 | 需要协议栈处理 | 硬件透明 |
| 缓存一致性 | 软件维护 | 硬件管理（CXL.cache） |
| 容量扩展 | 网络存储池 | CXL 内存池（100TiB 级） |

**XConn Apollo 方案**：

- Ultra IO Transformer 使 PCIe GPU（不原生支持 CXL）通过混合交换直接访问 CXL 内存池
- 多 GPU 节点共享同一 CXL 内存池，KV Cache 天然共享，无需传输

**Beluga 方案**（学术验证）：

- 相比 RDMA：TTFT 降低 89.6%，吞吐提升 7.35 倍
- 相比 SSD 缓存：性能提升 5 倍以上

**MemVerge GISMO**：

- Global IO-free Shared Memory Objects
- 软件定义弹性 CXL 内存，支持动态扩缩容

***

### 4.4 S3 over RDMA：保持 API 兼容的高速数据面

**问题**：S3/HTTP 对象存储是业界标准接口，但基于 TCP 协议栈，在高并发推理场景下存在 CPU 税、尾延迟和抖动问题。

**VAST + NVIDIA 方案——S3 over RDMA**：

- 保留 S3 API 作为"句柄"（身份认证、多租户、运维工具链）
- 将传输"平面"从 TCP 替换为 RDMA
- GPUDirect RDMA 使 KV blocks 直接在 NIC 和 GPU 显存之间 DMA，绕过主机内存

**效果**：

- KV 传输被视为基础设施而非临时管道问题
- 与 NFS/RDMA 在训练中的演进路径一致

***

### 4.5 PD 分离场景的 KV Cache 传输优化

Prefill-Decode 分离架构中，KV Cache 必须从 Prefill 节点传输到 Decode 节点，这是最关键的层级间传递场景：

| 厂商 | 传输方案 | 带宽/延迟 | 核心优化 |
| --- | --- | --- | --- |
| **NVIDIA** | NIXL + GPUDirect RDMA | NVLink/IB 级别 | 动态后端选择 + 零拷贝 |
| **Mooncake** | Transfer Engine + GPUDirect | 190 GB/s（8×400G） | 多 NIC 聚合 + 拓扑感知 + 容错重传 |
| **阿里** | GPU Direct RDMA | 微秒级 | GPU 绕过 CPU 直接读写远端内存 |
| **浪潮** | PCIe DMA + RDMA | 零拷贝 | GPU Direct Storage |
| **CXL** | load/store 共享 | 200-500ns | 无需传输，直接共享访问 |

**关键设计原则**：

1. **流式传输**：KV Cache 不等全部生成完再传输，而是边生成边传输（Mooncake CPP）
2. **提前卸载**：Prefill 产出的 KV 可立即从 GPU 撤离，不必等待 Decode 节点就绪，释放 GPU 开始新 Prefill
3. **按层流水线**：按 Transformer 层粒度传输+计算重叠（PolarKVCache Layer-wise）
4. **预取重叠**：计算当前层时预取下一层 KV（浪潮异步预加载）
